WebView 환경처럼 제어권이 개발자에게 집중된 상황이라면, 일반적인 웹 서비스보다는 보안 리스크가 상대적으로 낮을 수 있습니다. 하지만 WebView 특유의 동작 방식 때문에 발생하는 한 끗 차이의 보안 이슈들이 있습니다.

---

### 1. `shouldOverrideUrlLoading` 가로채기 위험

WebView는 특정 URL 형식을 가로채서 앱의 네이티브 기능을 실행할 때가 많습니다.

- **리스크:** 만약 앱이 `?service=order`라는 문자열을 감지해서 네이티브 결제 모듈을 띄우도록 설계되어 있다면, WebView 내에 삽입된 악성 광고 스크립트나 XSS 공격을 통해 의도치 않은 네이티브 기능이 호출될 수 있습니다.
- **팁:** URL 파라미터를 파싱하여 네이티브 액션을 수행할 때는, 반드시 **도메인 체크(White-list)**를 먼저 수행하세요.

### 2. 브라우저 히스토리와 캐시 (Shared Cookie/Cache)

WebView는 시스템 브라우저의 엔진을 공유하는 경우가 많습니다.

- **리스크:** `?modern&service=order` 형태의 URL은 기기의 **방문 기록(History)**에 그대로 남습니다. 만약 공용 태블릿이나 루팅된 기기라면 다른 앱이나 사용자가 이 파라미터를 통해 사용자의 서비스 이용 패턴을 추적할 수 있습니다.
- **팁:** 민감한 상태 정보는 URL이 아닌 `WebStorage`나 `Session`을 활용하고, WebView 종료 시 캐시를 명시적으로 삭제하는 것이 좋습니다.

### 3. Referer 헤더 노출

WebView에서 외부 링크(예: 고객센터 카톡 연결, 광고 등)로 나갈 때, 이전 주소인 `서버주소/?modern&service=order`가 **Referer 헤더**에 실려 나갑니다.

- **리스크:** 외부 업체 서버 로그에 내 서비스의 내부 구조(`service=order`)가 고스란히 찍히게 됩니다.
- **팁:** 외부 링크로 이동할 때는 `rel="noreferrer"` 속성을 주거나, 네이티브에서 별도 브라우저로 띄우는 방식을 권장합니다.

### 4. JavaScript Interface 노출 (가장 중요)

WebView와 네이티브 앱 사이에 브릿지(`addJavascriptInterface`)를 사용하고 있다면 더욱 주의해야 합니다.

- **리스크:** URL 쿼리 스트링에 따라 특정 JS 인터페이스를 활성화하거나 값을 넘겨줄 경우, 공격자가 URL을 변조하여 앱의 권한(카메라, 연락처 등)을 획득하려 시도할 수 있습니다.
- **팁:** `@JavascriptInterface` 어노테이션을 사용하고, 파라미터로 넘어온 값은 절대로 그대로 실행(`eval()`)하지 마세요.

---

### 💡 WebView를 위한 보안 전략 요약

| **항목** | **권장 사항** |
| --- | --- |
| **도메인 검증** | `서버주소`가 본인이 소유한 안전한 도메인인지 매번 확인 |
| **POST 권장** | 데이터 변경(주문하기 등)이 일어나는 액션은 쿼리 스트링 대신 POST 요청 사용 |
| **인증 강화** | URL 파라미터에 의존하지 말고, 헤더에 별도의 `Access-Token`을 실어서 통신 |
| **인터페이스 보안** | 네이티브-JS 브릿지 호출 시 전달되는 파라미터를 엄격하게 검사(Validation) |

**결론적으로,** 단순히 주소창에 노출되지 않는 WebView 환경이라 하더라도 "URL은 언제든 변조될 수 있고 로그에 남는다"는 원칙을 지키는 것이 안전합니다.
