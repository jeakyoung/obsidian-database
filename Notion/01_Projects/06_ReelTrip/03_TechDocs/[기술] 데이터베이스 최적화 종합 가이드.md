## 🎯 1단계: 테이블 구조 설계

### 테이블 설계 원칙

#### 정규화 (Normalization)
```sql
-- ❌ 나쁜 예: 비정규화 (중복 데이터)
CREATE TABLE Orders (
  order_id INT PRIMARY KEY,
  user_id INT,
  user_name VARCHAR(100),  -- 중복 가능
  user_email VARCHAR(100), -- 중복 가능
  product_ids VARCHAR(500)  -- 배열을 문자열로 저장
);

-- ✅ 좋은 예: 정규화
CREATE TABLE Orders (
  order_id INT PRIMARY KEY,
  user_id INT NOT NULL,
  order_date DATETIME,
  FOREIGN KEY (user_id) REFERENCES Users(user_id)
);

CREATE TABLE OrderItems (
  order_item_id INT PRIMARY KEY,
  order_id INT NOT NULL,
  product_id INT NOT NULL,
  quantity INT,
  FOREIGN KEY (order_id) REFERENCES Orders(order_id),
  FOREIGN KEY (product_id) REFERENCES Products(product_id)
);
```

#### 데이터 타입 최적화
```sql
-- ❌ 비효율적
CREATE TABLE Users (
  user_id VARCHAR(100),  -- 큰 타입
  status VARCHAR(100),   -- 상태는 문자열로 저장
  created_date VARCHAR(20)  -- 날짜를 문자열로
);

-- ✅ 최적화
CREATE TABLE Users (
  user_id INT,           -- 정수 타입
  status TINYINT,        -- 0: ACTIVE, 1: INACTIVE
  created_date DATETIME  -- 날짜 타입
);
```

## 🎯 2단계: 인덱싱 전략

### 인덱스의 이해

#### 인덱스 선택 기준
```
높은 선택도 (Selectivity):
- ACTIVE, INACTIVE (선택도 ~50%) ❌ 부적합
- 특정 사용자 ID (선택도 ~0.01%) ✅ 적합

검색 빈도:
- WHERE 절에 자주 사용되는 컬럼 ✅
- 거의 사용되지 않는 컬럼 ❌

복합 인덱스 순서:
(equality, range, sort)
SELECT * FROM Orders 
WHERE user_id = ? AND order_date >= ? ORDER BY created_date
→ INDEX(user_id, order_date, created_date)
```

### 인덱스 설계

```sql
-- 1순위: 기본 조회 성능
CREATE INDEX idx_user_active 
ON Users(user_id, status);

-- 2순위: 범위 검색
CREATE INDEX idx_order_date 
ON Orders(order_date DESC);

-- 3순위: 정렬 최적화
CREATE INDEX idx_user_date 
ON Orders(user_id, order_date DESC);

-- 4순위: 커버링 인덱스 (SELECT 절 컬럼 포함)
CREATE INDEX idx_user_summary 
ON Orders(user_id, order_id, order_date, total_amount);
```

### 인덱스 모니터링

```sql
-- 인덱스 사용 통계 (PostgreSQL)
SELECT 
  schemaname,
  tablename,
  indexname,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
ORDER BY idx_scan DESC;

-- 미사용 인덱스 찾기
SELECT 
  indexname,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

## 🎯 3단계: N+1 쿼리 제거

### 패턴 1: Collection Fetch

```java
// ❌ N+1 쿼리
List<User> users = userRepository.findAll();  // Query 1
for (User user : users) {
  List<Order> orders = orderRepository.findByUserId(user.getId());  // Query N
}

// ✅ JOIN Fetch
@Query("""
  SELECT DISTINCT u FROM User u 
  LEFT JOIN FETCH u.orders
  LEFT JOIN FETCH u.address
""")
List<User> findAllWithOrders();
```

### 패턴 2: 배치 조회

```java
// ❌ 반복 조회 (N번)
List<User> users = userRepository.findAll();
for (User user : users) {
  Address address = addressRepository.findById(user.getAddressId()).orElse(null);
  user.setAddress(address);
}

// ✅ 배치 조회 (1번)
List<User> users = userRepository.findAll();
List<Long> addressIds = users.stream()
  .map(User::getAddressId)
  .distinct()
  .collect(Collectors.toList());

Map<Long, Address> addressMap = addressRepository.findByIdIn(addressIds)
  .stream()
  .collect(Collectors.toMap(Address::getId, Function.identity()));

users.forEach(user -> user.setAddress(addressMap.get(user.getAddressId())));
```

### 패턴 3: 프로젝션

```java
// ❌ 전체 Entity 조회 (불필요한 데이터)
List<User> users = userRepository.findAll();  // 모든 컬럼

// ✅ 필요한 컬럼만 조회
@Query("""
  SELECT new map(u.id as id, u.name as name, u.email as email)
  FROM User u
""")
List<Map<String, Object>> getUserSummary();
```

## 🎯 4단계: Mybatis 동적 SQL 마스터

### 조건부 쿼리

```xml
<!-- 기본 구조 -->
<select id="searchOrders" parameterType="SearchRequest" resultType="Order">
  SELECT * FROM orders
  <where>
    <!-- 조건 1: 사용자 ID -->
    <if test="userId != null">
      AND user_id = #{userId}
    </if>
    
    <!-- 조건 2: 주문 상태 -->
    <if test="status != null">
      AND status = #{status}
    </if>
    
    <!-- 조건 3: 날짜 범위 -->
    <if test="startDate != null">
      AND order_date >= #{startDate}
    </if>
    <if test="endDate != null">
      AND order_date <= #{endDate}
    </if>
    
    <!-- 조건 4: 금액 범위 -->
    <if test="minAmount != null">
      AND total_amount >= #{minAmount}
    </if>
  </where>
  
  <!-- 동적 정렬 -->
  <if test="orderBy != null">
    ORDER BY ${orderBy}
  </if>
  
  <!-- 페이지네이션 -->
  LIMIT #{limit} OFFSET #{offset}
</select>
```

### Set 태그 (UPDATE에서의 동적 필드)

```xml
<!-- 필요한 필드만 UPDATE -->
<update id="updateOrder" parameterType="Order">
  UPDATE orders
  <set>
    <if test="status != null">
      status = #{status},
    </if>
    <if test="totalAmount != null">
      total_amount = #{totalAmount},
    </if>
    <if test="notes != null">
      notes = #{notes},
    </if>
    updated_date = NOW()
  </set>
  WHERE order_id = #{orderId}
</update>
```

### Foreach (배치 처리)

```xml
<!-- 배치 INSERT -->
<insert id="insertBatch" parameterType="list">
  INSERT INTO order_items (order_id, product_id, quantity, price)
  VALUES
  <foreach collection="list" item="item" separator=",">
    (#{item.orderId}, #{item.productId}, #{item.quantity}, #{item.price})
  </foreach>
</insert>

<!-- 배치 UPDATE -->
<update id="updateBatch" parameterType="list">
  <foreach collection="list" item="order" separator=";">
    UPDATE orders SET status = #{order.status} WHERE order_id = #{order.orderId}
  </foreach>
</update>
```

## 🎯 6단계: 캐싱 전략

### Redis 활용

```java
@Service
public class OrderService {
  @Autowired
  private RedisTemplate<String, Order> redisTemplate;
  
  @Cacheable(value = "orders", key = "#orderId", unless = "#result == null")

    return orderRepository.findById(orderId).orElse(null);
  }
  
  @CacheEvict(value = "orders", key = "#order.id")
  public void updateOrder(Order order) {
    orderRepository.save(order);
  }
}
```

### 캐시 버전 관리

