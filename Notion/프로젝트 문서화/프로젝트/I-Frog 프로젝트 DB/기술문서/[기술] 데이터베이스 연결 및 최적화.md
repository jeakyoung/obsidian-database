## 🔌 데이터베이스 연결

### 1️⃣ Connection Pool 설정

#### HikariCP 설정 (권장)
```yaml
# application.yml
spring:
  datasource:
    url: jdbc:sqlserver://localhost:1433;databaseName=ifrog;encrypt=true;trustServerCertificate=true
    username: sa
    password: ${DB_PASSWORD}
    driver-class-name: com.microsoft.sqlserver.jdbc.SQLServerDriver
    hikari:
      maximum-pool-size: 20          # 최대 연결 수
      minimum-idle: 5                # 최소 유휴 연결
      connection-timeout: 30000      # 연결 대기 시간
      idle-timeout: 600000           # 유휴 타임아웃 (10분)
      max-lifetime: 1800000          # 최대 생명주기 (30분)
      auto-commit: true
      connection-test-query: SELECT 1
```

#### PostgreSQL 설정
```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/ifrog
    username: postgres
    password: ${DB_PASSWORD}
    driver-class-name: org.postgresql.Driver
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
```

### 2️⃣ 연결 풀 튜닝

#### 최적 풀 사이즈 계산
```
권장 공식:
pool_size = (core_count * 2) + effective_spindle_count

예시:
CPU 코어: 8개
디스크: 2개 (SSD)
pool_size = (8 * 2) + 2 = 18

I-Frog 권장값: 15-20
```

#### 모니터링 메트릭
```java
@Configuration
public class DataSourceMetricsConfig {
  @Bean
  public DataSourcePool metrics(DataSource dataSource) {
    HikariDataSource hikari = (HikariDataSource) dataSource;
    
    return new DataSourcePool(
      hikari.getHikariPoolMXBean().getActiveConnections(),
      hikari.getHikariPoolMXBean().getTotalConnections(),
      hikari.getHikariPoolMXBean().getIdleConnections()
    );
  }
}
```

## ⚡ 성능 최적화

### 1️⃣ 쿼리 최적화

#### N+1 문제 해결
```java
// 잘못된 예 (N+1 쿼리 발생)
List<OrderItem> items = orderItemRepository.findAll();
for (OrderItem item : items) {
  // 각 item마다 shop 조회 (N번 추가 쿼리)
  Shop shop = shopRepository.findByCode(item.getShopCode());
}

// 올바른 예 (JOIN Fetch)
@Query("""
  SELECT o FROM OrderItem o 
  LEFT JOIN FETCH o.shop s
  WHERE o.orderDate = :date
""")
List<OrderItem> findWithShopByDate(@Param("date") String date);
```

#### 배치 조회
```java
// 배치 조회로 성능 개선
@Query("""
  SELECT o FROM OrderItem o 
  WHERE o.orderDate = :date 
  AND o.shopCode IN :shopCodes
""")
List<OrderItem> findByDateAndShops(
  @Param("date") String date,
  @Param("shopCodes") List<String> codes
);
```

#### 인덱스 모니터링
```sql
-- 인덱스 사용 통계
SELECT 
  OBJECT_NAME(s.object_id) AS TableName,
  i.name AS IndexName,
  s.user_seeks,
  s.user_scans,
  s.user_lookups,
  s.user_updates
FROM sys.dm_db_index_usage_stats s
INNER JOIN sys.indexes i ON s.object_id = i.object_id
WHERE database_id = DB_ID()
ORDER BY s.user_seeks + s.user_scans + s.user_lookups DESC;
```

### 3️⃣ 캐싱 전략

#### Redis 캐싱
```java
@Service
public class OrderCacheService {
  @Autowired
  private RedisTemplate<String, OrderItem> redisTemplate;
  
  public OrderItem getOrderItem(Long seq) {
    String key = "order-item:" + seq;
    
    // 캐시에서 조회
    OrderItem cached = redisTemplate.opsForValue().get(key);
    if (cached != null) return cached;
    
    // DB에서 조회
    OrderItem item = orderItemRepository.findById(seq).orElse(null);
    
    // 캐시에 저장 (TTL: 1시간)
    if (item != null) {
      redisTemplate.opsForValue().set(key, item, Duration.ofHours(1));
    }
    
    return item;
  }
}
```

#### 캐시 무효화
```java
public void updateOrderItem(OrderItem item) {
  // DB 업데이트
  orderItemRepository.save(item);
  
  // 캐시 무효화
  String key = "order-item:" + item.getSeq();
  redisTemplate.delete(key);
}
```

## 🐛 문제 해결

### 문제 1: Connection Timeout
```
에러: Connection timeout expired
원인: 풀 사이즈 부족 또는 느린 쿼리
해결:
1. 풀 사이즈 증가
2. 느린 쿼리 최적화
3. DB 서버 리소스 확인
```

### 문제 2: Connection Leak
```
에러: Connection is still open when closed
원인: 연결 반환 누락
해결: 모든 쿼리에서 try-with-resources 사용
```

```java
try (Connection conn = dataSource.getConnection()) {
  // 쿼리 실행
  PreparedStatement stmt = conn.prepareStatement("SELECT ...");
  // 자동으로 close됨
}
```

### 문제 3: Deadlock
```
에러: Deadlock detected
원인: 동시성 제어 문제
해결:
1. 트랜잭션 범위 최소화
2. 락 순서 일관화
3. READ COMMITTED SNAPSHOT 활성화
```
