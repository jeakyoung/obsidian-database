# 이메일 인증 코드 발송·검증 기능 구현

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **요청자** | 본인 (BE 팀장) |
| **요청일** | 2024-08 |
| **대상 시스템** | `4th_GraduationBack` — `EmailAuthService`, `EmailAuthSendController` |
| **관련 화면·프로그램** | `POST /PTU/Auth/CodeSend`, `POST /PTU/Auth/VerifyCode` |

> 회원가입 중 이메일 소유 확인을 위해 6자리 인증 코드를 Gmail SMTP로 발송하고, 3분 내에 입력하지 않으면 만료시키는 기능.

## 🔍 현상 및 원인

### 재현 조건

회원가입 시 입력한 이메일이 실제로 본인 소유인지 확인할 방법이 없었다.

### 원인

별도 인증 서비스 없이 Spring Mail만으로 처리해야 했고, 인증 코드의 유효 시간을 관리할 별도 스케줄러/캐시(Redis 등)를 두지 않았다.

## 🔧 조치 내용

| 구분 | 대상 | 변경 내용 |
|:--|:--|:--|
| 서비스 | `EmailAuthService.sendVerificationCode` | `stu_info`에서 `MEMB_ID`로 사용자 조회 → 6자리 랜덤 코드 생성 → `JavaMailSender`로 발송 → `CRE_CODE`/`CRE_CODE_TIME` 저장 |
| 서비스 | `EmailAuthService.verifyCode` | 저장된 코드·생성 시각을 현재 시각과 비교해 3분(`CODE_EXPIRATION_TIME`) 초과 시 만료 처리, 일치 시 `CRE_CON = "Y"`로 인증 완료 표시 |
| 모델 | `EmailAuthModel` | `stu_info` 테이블을 `membId`/`email`/`creCode`/`creCodeTime`/`creCon` 필드만으로 매핑한 전용 엔티티로 분리 |
| 만료 처리 | `EmailAuthService.sendVerificationCode` | `java.util.Timer.schedule`로 3분 뒤 `CRE_CODE`를 null로 재저장 |

```java
new java.util.Timer().schedule(new java.util.TimerTask() {
    @Override
    public void run() {
        user.setCreCode(null);
        userRepository.save(user);
    }
}, CODE_EXPIRATION_TIME * 60 * 1000);
```

이 방식은 애플리케이션 프로세스가 살아있는 동안에만 유효하다 — 서버가 재시작되면 예약된 `Timer` 작업이 사라지므로, 재시작 시점에 발급된 코드는 `verifyCode` 쪽의 시각 비교 로직(코드 생성 시각 + 3분 경과 여부)에만 의존하게 된다. 즉 만료 자체는 `verifyCode` 호출 시점에도 다시 검사하기 때문에 보안적으로 뚫리진 않지만, "3분 후 자동으로 코드가 지워진다"는 보장은 서버 재시작 여부에 따라 깨질 수 있다.

## ✅ 검증 및 결과

- [x] 코드 발송 후 이메일 수신 및 6자리 숫자 형식 확인
- [x] 정상 코드 입력 시 `RSLT_CD 00` + `CRE_CON = Y` 반영 확인
- [x] 3분 경과 후 입력 시 `RSLT_CD 02`(만료) 확인
- [ ] 서버 재시작 시나리오에서 `Timer` 유실 여부에 대한 자동화된 테스트는 없음 (수동 확인만 진행)
