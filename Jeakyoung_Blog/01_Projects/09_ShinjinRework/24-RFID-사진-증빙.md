# RFID 사진 증빙

## 📋 개요

D2 RFID·파렛트 화면에 합성 사진의 조회·미리보기·첨부를 추가했다. 구현 기준은 main `2b54fc3`, 문서 기준은 vault `20e3510`다. 공용 App과 게시된 M1 파일은 기준 소스와 동일하다.

## 📖 상세 내용

- WinForms `FrmPalletBox`의 파렛트 확인 사진과 `FrmTagInOutList` → `FrmPhoto`의 입출고 이력 사진을 구분한다. 데모는 읽기 전용 파렛트 확인 기록과 로그인 범위의 이동 이벤트를 구분해 보여준다.
- Spring demo에서 사업장·단말·작업자 범위의 사진 이력을 조회한다. 미리보기는 데모 세션에서 서버가 생성한 색 패턴 PNG 두 종류만 제공한다.
- 이동 이벤트에서 샘플을 미리 본 뒤 명시적으로 확인해 첨부한다. 서버에서 이벤트 범위, 현재 revision, 샘플 존재와 중복 여부를 검사한다. 첨부와 재시도 키는 RFID 작업공간 잠금에서 함께 반영하며 재고와 이동 이력을 보존한다. 동일 키·본문은 기존 성공을 반환하고 키의 다른 본문이나 중복 샘플은 거절한다.

## ✅ 검증 및 인수

- `release-2b54fc3/d2-handoff.md`와 `d2-manifest.json`에 구현 범위와 배치 파일 SHA-256이 기록돼 있다.
- 구현 로그에서 웹 빌드와 HTTP 통과를 확인했다. HTTP는 인증·작업자와 사업장 범위, 읽기 전용 이력, PNG, 명시 확인, 실패 무변경, 동일 명령 재생·중복 및 revision 경합을 검증했다. 재고·계획의 기존 hooks lint 경고가 각 1건 기록됐다.
- 구현 Chrome에서 첫 성공 응답 유실, 실제 401, 이벤트·작업자 격리, 동일 본문 재생 뒤 첨부 한 건 유지와 003/103 메뉴 왕복을 확인했다. API의 demo 프로필 한정도 검증했다. 실배치 Maven·웹 빌드도 통과했다.
- 실제 카메라 촬영·FTP, 실제 사진·원본 업로드, 운영 보존 정책, 실물 장비·DB는 후속 인수 범위다.
- 첨부 전 원 키와 본문을 탭 저장소에 보존한다. 같은 단말·작업자·이벤트에서만 복구하며 서버의 확정 응답은 저장 본문이 일치할 때만 보류를 해제한다.

### 최종 독립 검증

- `release-2b54fc3/d2-review.md`는 P2 수정본 통과를 기록했다. 배치 SHA-256 5개를 대조했고 별도 Java·Vite 빌드와 Spring HTTP·Chrome 158 검증을 마쳤다.
- Chrome에서 첨부의 첫 성공 응답을 유실시킨 뒤 실제 401을 거쳐 원 작업자가 재생했다. 세 요청 본문의 바이트 일치와 서버 상태 200 → 401 → 200을 대조했다. 재생 결과는 `PHOTO_REPLAYED`였고 첨부는 한 건이었다. 다른 작업자·이벤트에 보류 요청이 표시되지 않았고 003/103 메뉴 왕복 뒤에도 첨부가 유지됐다.
- HTTP에서 이벤트 범위 밖 직접 첨부, 읽기 전용 기록 변경, 미확인·없는 샘플·중복·다른 본문·오래된 revision을 거절했다. 동시 요청은 200과 409 각 한 건이었고, 실패 전후 첨부·이동 이력·재고를 대조했다. 합성 PNG 두 종류는 인증된 데모 세션에서 조회할 수 있으며 이벤트 권한은 별도로 검사한다. demo 비활성에서 조회는 404였다.

## 2026-11-26 원본 폼과 웹 동선 대조

비교 기준은 `MainMenu/frmMenu.cs`의 다섯 클릭 핸들러(924, 942, 960, 978, 996행), `POPRFID`의 폼·Designer·RESX이다. 아래 캡처의 왼쪽은 운영 C# 폼이고 오른쪽은 실제 React와 격리 Spring demo 세션이다. 1280×800 업무 폼을 비교할 때 웹 공통 상단바를 제외했다. 원본 화면 캡처가 1920×1080인 경우 원본이 사용한 좌상단 1280×800을 잘랐다. 팝업은 각 창 크기를 보존했다. 포장 사진은 Chrome 가상 카메라가 만든 JPEG다.

### Spring demo API

| 요청 | 결과와 원본 연결 위치 |
|---|---|
| `GET /api/pop/rfid/forms` | 로그인 단말/작업자 기준 사업장·등록자, 한국 현재일과 이전 달, 다음 관리번호, 권한 내 태그·파렛트·거래처·포장·입출고 목록. 태그/입출고 대상 기간은 00:00:01부터 23:59:59까지다. |
| `POST /api/pop/rfid/tags` | `requestId, action, rows[{id,code,enabled}]`. register는 체크행, edit는 사용여부가 바뀐 행. 전체 유효성 확인 후 반영하며 동일 키·본문 재생을 지원한다. 원본은 TMA815 행별 INSERT 또는 UPDATE, 월 관리번호는 `SP_POP_RFID_NOSCAN_01_LIST`. |
| `POST /api/pop/rfid/commands` | `matchScan`은 원본 매칭 저장에 따라 필요하면 신규 ID 등록과 기존 파렛트 연결을 함께 처리한다. `unmatch`는 해당 파렛트에 표시됐던 ID를 검증하고 연결만 해제한다. 기존 합성 명령 register/match/load/in/out의 호출 경로도 유지한다. |
| `POST /api/pop/rfid/boxes` | 요청 ID·파렛트·RFID ID·포장일·출고처·확정 JPEG 배열. 저장 시점의 관리번호, 날짜, 순번으로 파일명을 만들고 포장건에서 마지막 사진을 찾는다. 실제 카메라는 단말 브라우저의 권한을 요청한다. 데모 사진은 Spring 메모리에서 관리한다. |
| `POST /api/pop/rfid/movements` | 요청 ID·포장건·입출일·거래처·IN/OUT. 포장건과 현재의 매칭 및 작업자, 마지막 방향을 검사한다. 동일 요청 재실행 시 전표 증식 방지. 원본은 TMA823, `SP_POP_RFID_TAGINOUTREG_02/03_LIST`로 포장 이력과 직전 방향을 확인한다. |
| `GET /api/pop/rfid/boxes/{id}/picture` | 포장한 당사자에게만 마지막 확정 JPEG를 제공한다. 현황 사진 도장은 각 이력의 방향을 사용하여 과거 화면을 보존한다. |

### 운영 인수 경계

태그·현황 조회의 원본 호출 인수는 일시 범위와 사업장이다. 폼 안에서는 사진을 열거나 매칭을 해제할 때 작업자 조건을 직접 전달하지 않는다. 원본 메뉴의 타일 활성화, 로그인 단말/공정, 프로시저 안의 권한 및 사업장 운영 범위는 각각 별도 근거가 필요하다. 현재 합성 데이터는 기존의 사업장·단말·작업자 격리를 유지한다. 다른 작업자의 목록과 사진에 접근할 수 없는지 실제 HTTP로 확인했다.

데모의 메모리 요청 보존과 현장 영구 보존은 별도로 인수한다. 실제 RFID 리더·카메라·단말 권한·컬러/해상도·FTP 계정/서버·원본 DB 번호 할당 경쟁 및 입출고 중 장애 복구는 실장비/운영팀 검증 대상이다. 현장 MSSQL/FTP에 접속하거나 객체를 생성·수정·삭제하는 작업은 수행하지 않았다.

### 2026-11-26 폼 화면 증빙

[원본·웹 좌우 대조와 실측 좌표](</E:/ajk/devgit/shinjin/.team/screen-review/web-parity/RFID-관리-화면대조.md>)를 참조한다. 원본 관리 3폼과 RFID 9폼, 최종조회 2행 같은 상태를 비교했다.

출고처 필드를 누르면 원본과 같이 작업지시번호를 스캔한다. 별도 데이터셋 `src/api/src/main/resources/demo/rfid-forms.json`의 DEMO-A/DEMO-W01, 파렛트 26000001·26000002, 출고처 스캔 20261125201로 검증했다. 원본 `SP_POP_RFID_PALLETBOX_01_CUSTOMER(@PRODPLAN_SEQ)`에 전달하는 스캔 문자열을 데모에서 매핑한다. 카메라 모드에서는 같은 ZXing 계열 디코더를 브라우저에서 동적으로 읽어 원본처럼 단말 내에서 해독한다. Spring으로 사진이 전송되는 시점은 촬영본 확정 후 적재 저장이다. 포장/입출고 번호는 발행일 기준 각각 yyyyMMdd0001부터 할당하고 동일 requestId를 재전송하면 재발번하지 않는다. 실장비의 카메라 목록 순서와 USB 스캐너의 키 종결자는 현장 인수 대상이다.
