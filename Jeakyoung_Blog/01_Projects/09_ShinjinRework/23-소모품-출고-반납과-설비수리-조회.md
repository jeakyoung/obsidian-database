# 소모품 출고·반납과 설비수리 조회

## 📋 개요

관리 M1의 소모품 원장과 설비수리 조회를 다룬다. 문서 기준은 `3328e91`, 구현 인계 기준은 `44c751a`다. 최신 통합본은 독립 Chrome·HTTP 검증을 통과했다.

## 📖 상세 내용

- WinForms `POPMANAGEMENT/frmExpendables`의 소모품 요청 화면에는 `outBtn_Click` → `ExpendablesOut` 출고와 수불 이력이 있다. `frmRepair`의 설비수리 이력은 별도 조회다.
- 합성 출고는 품목·LOT·창고·위치와 정수 수량을 사용하며 최근 출고를 재사용할 수 있다. 세션의 사업장·작업장과 작업자·단말 범위를 확인하고 출고·반납 또는 재고 변경과 이력 갱신을 함께 반영한다.
- 반납은 원 출고와 항번을 참조한다. 누적 반납량은 원 출고량 이하여야 하며 합성 재고는 원 위치에 복원한다. 범위 오류·초과·경합에 따른 거절은 실패 전 상태를 보존한다. 동일 작업자·단말의 동일 요청은 원 영수증을 반환한다. 출고의 401 복구는 원 본문을 재전송하며 늦은 완료가 다른 보류 명령을 지우지 않는다.
- 설비수리는 기간·상태를 사용하는 합성 읽기 전용 조회다. 설비수리 등록·완료, 운영 승인과 ERP 반납, 실제 수불·권한 대사는 별도 인수다.

## ✅ 검증 및 인수

- `m1-review.md`의 독립 통과는 `3939666` 출고·설비수리 범위다. Java·HTTP로 실패 무변경과 공유 재고 경합, Chrome으로 응답 유실·같은 작업자 401 복귀·늦은 응답을 확인했다.
- `release-7a85b43` 인계와 로그에서 통합 App Chrome의 출고·수리, 원 출고 연계 반납·부분/전량·초과 거절, 계획 화면 회귀를 확인했다.
- `release-44c751a/verification/integration.log`에서 웹 빌드와 출고·수리 및 반납 HTTP 통과를 확인했다. 재고·계획의 기존 hooks lint 경고가 각 1건 기록됐다. 같은 로그에서 실제 App Chrome의 출고 확인·최근 출고 재사용, 화면 재진입과 401 복구, 늦은 응답의 새 보류 명령 보존, 읽기 전용 수리 조회를 확인했다. 반납은 원 출고 연계, 초과 거절, 부분·전량 잔량과 영수증 2건을 확인했다. 단말 설정과 작업지시가 열리고 생산계획·최종생산조회에서 복귀해도 반납 잔량이 유지됐다. 실배치 Maven·웹 빌드도 통과했다.

- m1-return-manifest.json은 독립 파일 6개와 App 파일의 SHA-256을 기록한다. m1-App.patch에는 공유 App 변경만 담았다.

### 최신 독립 검증

`release-44c751a/m1-return-review.md`는 분리된 합성 App·HTTP 실행의 통과를 기록한다. 독립 빌드의 App SHA-256 앞 16자리는 `092AC15C322CEAB0`이다.

- HTTP에서 원 출고·이동 항번과 영수증, 부분·전량 반납, 원 위치 재고 복원을 대조했다. 잘못된 다중행은 재고·이력·revision을 보존했고 동시 반납은 한 건만 성공했다. 미인증, 범위 밖 원 출고, 타 작업자 성공 키 재생은 각각 401, 404, 403으로 거절됐다. 순수 Java에서는 100행 대량 출고·반납 및 101행 거절과 동일 키 재생을 확인했다.
- Chrome에서는 출고와 반납 각각의 성공 응답 유실 후 화면 재진입과 실제 401 뒤 동일 본문 재생을 확인했다. 늦은 출고 응답은 새 보류 사본을 보존했고, 반납 재생은 반납 사본만 정리했다. 초과 입력 차단, 영수증 두 건, 수리 조회와 기존 메뉴 진입 후 반납 잔량 유지도 확인했다.

## 소모품 화면 기능과 API

기준 폼은 `POPMANAGEMENT/frmExpendables`다. Designer 604–608행의 탭 추가 순서와 1158–1165행, 1609–1616행의 그리드 연결을 함께 확인했다.

| 탭 | 원본 조회·이벤트 | 웹의 작업 순서 |
|---|---|---|
| 소모품 목록 | `ExpendablesSearch` 415행, `gv1_RowCellClick` 1226행 | 품목분류·대분류·중분류에서 코드와 명칭을 보고 선택한다. 대분류 변경 시 중분류를 전체로 재설정한다. 원하는 품목을 체크한 뒤 수량과 출고를 확인한다. |
| 소모품 신청재고 | `ExpendablesQTY` 470행, `gv3_RowCellClick` 1330행 | 작업장 신청 잔량에서 반납량을 정하고 해당 행의 반납을 터치한다. 확인 창에 품목명과 수량이 표시된다. |
| 최근 1개월 신청내역 | `ExpendablesHistory` 521행, `gv2_RowCellClick` 1278행 | 이전 신청 품목을 선택하고 해당 재고의 현재 가용량 범위에서 재출고한다. 상단 소모품 출고는 목록과 최근 내역의 체크 행을 함께 처리한다. |

각 수량 칸은 터치 수치 키패드와 한 개씩 증감하는 버튼을 사용한다. 입력량은 0부터 해당 행의 가용량까지다. 체크와 수량은 각각 입력한다. 원본 탭 재진입은 해당 그리드를 다시 조회한다. 웹은 동일 재고 버전에서 재조회 대상 탭의 편집을 초기화하고, 버전 변경 시 이전 재고에서 편집한 값을 비운다.

### 세션 기반 API

| 메서드·경로 | 입력 | 결과 |
|---|---|---|
| GET `/api/pop/management/expendables/screen` | 선택 조회 조건 `materialFlag`, `kind1`, `kind2`. 전체는 생략 | `revision`, 분류 마스터 `masters`, 현재 사업장 품목 속성 `items`, 필터된 `catalog`, 작업장의 최근 재출고 후보 `recent`, 반납 잔량 행 `held`. 같은 시점의 수량을 반환한다. |
| POST `/api/pop/management/expendables/issues` | `requestId`, `expectedRevision`, 체크하고 수량을 지정한 행의 `origin`, `stock`, `quantity`. 재출고 행은 `priorRequest` 포함 | 출고 영수증과 새 버전. 체크한 행의 수량이 모두 0이면 수불 등록 없이 재조회한다. |
| POST `/api/pop/management/expendables/returns` | `requestId`, `expectedRevision`, 해당 행의 원전표 `issue`, `movementId`, `quantity` | 반납 영수증. 원 위치 재고가 증가하고 해당 행의 반납 가능량이 감소한다. |

데모 재고와 분류·품목 속성은 `src/api/src/main/resources/demo/expendables.json`에 있다. 초기 기본 POP A에서 소모품 목록의 샘플 장갑 첫 행은 6개다. 2개 출고 후 신청재고에서 1개 반납하면 해당 원출고의 잔량은 1개, 원 위치 재고는 5개다. 최근 1개월 신청내역에서 1개 재출고하면 원 위치 재고는 4개가 된다.

Chrome 1280×800 터치에서 세 탭, 분류 연동과 빈 조회, 키패드 상한, 출고·반납 확인 취소와 저장, 최근 행 재출고, 다른 세션의 선행 출고 뒤 충돌 재조회를 확인했다. 웹 빌드·lint와 격리한 동일 소스의 Maven verify가 통과했다. 운영 프로시저의 월 경계와 결과 정렬, 실제 창고 표시명 및 수불 전표 대사는 운영 연결 시 확인할 항목이다.

## 설비 수리내역 화면과 조회 API

관리 메뉴의 설비 수리내역은 `MainMenu/frmMenu.cs:842`에서 `frmRepair`를 연다. 별도 설비 수리의뢰의 부모 패널은 `MainMenu/frmMenu.Designer.cs:1325`에서 숨겨져 있다. 조회는 로그인 세션의 사업장을 사용한다.

- 처음 들어오면 수리 요청일을 오늘과 한 달 전으로 채우고 완료여부 전체로 조회한다. 날짜 역전은 수정 시점에 취소되어 직전 날짜와 조회 결과가 유지된다. 완료여부 팝업은 코드 000 전체, 001 완료, 002 미완료를 표시하고 조회 버튼으로 결과를 갱신한다. `POPMANAGEMENT/frmRepair.cs:37, 98, 158, 174, 186`.
- 표시 열은 순번, 설비명, 이슈 번호, 이슈 내용, 이슈 발생자, 경과 시간, 이슈 발생일시, 이슈 해결내용, 이슈 해결자, 이슈 해결일시 순이다. 열 제목 정렬과 행 선택이 가능하고, 해결일시가 비어 있으면 경과시간을 빨간색으로 표시한다. `POPMANAGEMENT/frmRepair.Designer.cs:466–1028`.
- 원본 프로시저는 `SP_POP_CALL_01_LIST`의 `REPAIR_LIST`다. `PLANT_CODE`는 세션 사업장, `EQUIP_SYS_CD`는 빈 문자열, `CLEAR`는 선택한 한글 완료표시다. `SDATE`에는 시작일 00:00:01, `EDATE`에는 종료일 23:59:59를 보낸다. 실제 사업장 권한 및 해결코드·경과시간 계산식은 연결 시 원본 결과셋을 대조한다. `POPMANAGEMENT/frmRepair.cs:191–217`.

GET `/api/pop/management/repairs`의 `from`, `to`는 ISO 날짜이고 `status`는 ALL, COMPLETE, OPEN이다. 응답은 적용한 기간과 행 배열이다. 기존 날짜·설비 식별자·사유·결과 필드에 `detail`이 추가되어 순번, 설비 표시명, 발생자·해결자명, 시간, 경과시간 표시값을 제공한다. 기간 역전은 422, 로그인 만료는 401이다.

데모 결과셋은 `src/api/src/main/resources/demo/repairs.json`이다. POP A에서 기본 기간은 2026-10-25부터 2026-11-25까지다. 전체 2행, 완료와 미완료 각각 1행이다. POP B에서는 별도 사업장의 1행을 확인할 수 있다. 격리된 Spring 데모와 1280×800 Chrome 터치에서 조회, 세 상태, 날짜 역전 두 방향, 빈 결과, 정렬, 행 선택 및 미완료 경과시간 색상을 확인했다.

### 세 탭의 공통 숫자패드

원본 `frmExpendables.FnKeyPadCall`은 정수용 `ComNumericKeyPad`의 적용 결과만 현재 셀에 넣고 취소하면 기존 값을 보존한다. 재고 또는 보유량을 넘는 입력은 각 탭의 행 클릭 처리에서 상한으로 되돌린다. 웹의 소모품 목록·신청재고·최근 1개월 신청내역 수량 셀이 `CommonNumericPad`의 정수 모드를 사용한다. 체크와 수량은 독립적이다. 0으로 출고 확인 시 이동을 만들지 않고, 0 반납 버튼은 비활성이다. 2026-11-26 격리 Spring/Chrome에서 취소, 상한 6과 2, 0, 출고·반납·최근 재신청, 타 사용자 선처리 버전 충돌, 미로그인 조회 차단을 확인했다.

## 소모품·설비수리의 터치 및 긴 이름

1280×800, 1366×768, 1024×768의 Chrome에서 분류, 소모품 3탭, 출고·반납 확인과 수리내역의 기간·완료여부·행 선택을 긴 합성 품목명과 사유로 검증했다. 1024 화면에서 수량 버튼이 셀 경계의 안쪽에 있고 긴 품목·규격은 해당 셀에서 줄바꿈된다. 공용 정수 키패드의 마지막 행과 적용·취소가 동시에 보이며 직접 눌러 동작했다. 재질·창고 설정의 긴 명칭도 원본 폭과 터치 버튼을 유지하면서 셀 안에 표시한다. 출력 이미지와 픽셀 측정은 기존 원본 저장소 `.team/screen-review/web-parity/관리-입고-다중해상도/검증.md`에 있다.


## 수리기간 터치 달력

frmRepair.Designer.cs 266–268·389–390의 시작일·종료일은 직접 편집이 차단된 Fluent 달력이다. 웹의 각 필드를 터치하면 공용 달력이 열린다. 날짜를 바꾼 후 조회를 눌러야 GET `/api/pop/management/repairs`가 호출된다. 종료일보다 늦은 시작일과 시작일보다 빠른 종료일은 기존 값을 보존한다. 세 화면 크기에서 취소·선택·역전 경고·상태별 조회를 확인했다.
