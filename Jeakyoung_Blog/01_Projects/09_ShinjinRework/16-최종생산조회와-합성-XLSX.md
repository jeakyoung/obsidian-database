# 최종생산조회와 합성 XLSX

## 현재 기능 및 API

관리 메뉴에서 최종생산조회를 열면 빈 표가 나타난다. 작업지시번호를 스캔하고 Enter를 누르면 앞 8자리 계획일과 뒤의 순번으로 조회한다. 세션의 사업장에 속한 결과 행을 반환 순서로 누적하고 전체 순번을 유지한다. 이미 표시된 계획이나 조회 결과가 없으면 표가 유지된다. Clear는 입력만 지우고 All Clear는 표와 입력을 함께 비우며 포커스는 스캔 입력란으로 돌아온다. 조회 조건은 작업지시번호 하나다. 원본의 숨김 입고일자·사업장은 복원 대상 입력 필드에 포함되지 않는다. `POPMANAGEMENT/frmProduction.cs:104,196,203`.

| 위쪽 | 아래쪽 |
|---|---|
| No | 세로 병합 |
| 수주번호 | 작업지시번호 |
| 작업순번, 공정명, 재질명 | 각각 세로 병합 |
| 품목코드 | 규격 |
| 수주량 | 생산량, 불량 |
| 입고창고, 작업자명 | 각각 세로 병합 |

표와 저장 파일은 같은 열 배치를 공유한다. 데이터 원천에 시작·종료시간이 있으나 표시 밴드는 이 두 열을 사용하지 않는다. 작업순번은 `PROD_SEQ`다. 원본 폼의 확정 XLSX에는 합계 행이 없다.

GET `/api/pop/production-report?date=YYYY-MM-DD&sequence=N`은 인증 세션의 사업장·계획일·순번에 해당하는 행 배열을 반환한다. 각 행에 수주·작업지시번호, 작업순번, 공정명, 재질명, 품목·규격, 수주·생산·불량량, 창고 및 작업자명이 들어 있다. 빈 조회는 빈 배열, 로그인 만료는 401, 잘못된 날짜와 순번은 400이다. 원본 SP는 `SP_POP_MNG_PRODUCTION_01_LIST`로 `PRODPLAN_DATE`와 `PRODPLAN_SEQ`를 받는다. 운영의 데이터 범위와 행 순서는 연결 시 검증한다.

엑셀저장은 빈 표에서 종료한다. 파일 선택 지원 브라우저에서는 저장 파일명과 위치를 선택하며 기본명은 `ProductionData.xlsx`다. 취소하면 표를 그대로 유지한다. 저장 성공 알림은 쓰기와 닫기가 끝난 뒤 표시한다. 파일 선택 API가 없는 브라우저는 브라우저 다운로드 설정을 따른다.

### 재현과 대조

- `src/api/src/main/resources/demo/final-production.json`에 검증용 3개 작업지시를 보관했다. POP A에서 `20261125201`을 스캔하면 2개 행, `20261125202`를 추가하면 총 3개 행이다. POP B는 `20261125203`으로 1개 행을 조회한다. 운영 메뉴에 스캔 예제와 테스트 값을 표시하지 않는다.
- 원본 로컬 POP의 frmProduction을 열어 합성 2행을 바인딩하고 DevExpress WYSIWYG 내보내기를 수행했다. 2개 행을 조회한 웹 XLSX와 대조하여 셀 77개의 주소와 스타일 ID, 머리글 텍스트, 병합 25개, 11개 열 폭과 7개 행 높이가 일치함을 확인했다. 통합문서 시트 이름은 Sheet고 눈금선을 표시한다.
- 데모 Spring과 Chrome에서 빈 결과, 중복 조회, 터치 선택, 입력/전체 지우기, 계획 누적, 사업장·세션 범위를 확인했다. 파일 선택기의 취소 응답과 브라우저 저장소의 쓰기 핸들로 저장 로직을 검증했다. 브라우저의 다운로드로 받은 실제 파일과 쓰기 핸들의 바이트가 같았다. 운영 Windows 저장 대화상자의 경로 선택과 실제 업무 결과셋 대사는 현장 검증 항목이다.

## 📖 상세 내용

### 소스와 합성 계약

`POPMANAGEMENT/frmProduction.cs`의 `textEdit1_KeyDown`은 Enter에서 작업지시의 앞 8자리를 계획일, 나머지를 순번으로 사용한다. 이미 그리드에 있는 계획은 추가하지 않으며, 조회 결과를 반환 순서대로 기존 행 뒤에 붙이고 전체 행 번호를 다시 매긴다. 입력 지우기와 전체 지우기는 별도다. Designer는 업무 열의 정렬을 막으며, `excelSaveBtn_Click`은 빈 결과의 내보내기를 건너뛰고 표시 그리드를 XLSX로 저장한다.

합성 구현은 유효한 달력 날짜와 양의 순번을 확인하고, 계획일·순번의 정확히 일치하는 행만 조회한다. 다른 조회의 행은 추가하지 않는다. 화면과 내보내기가 같은 15개 열, 선택 순서, 원천 행 순서 및 번호를 공유한다. 수주량·생산량·불량의 합계 행은 08 인수 목표를 반영한 합성 규칙이며, 레거시 조회의 운영 집계 공식은 확인되지 않았다.

### 인증된 실적 원천

React의 조회는 Spring demo 읽기 API를 사용한다. 서버는 기존 008 세션의 사업장 범위에서 계획일·순번을 검증하고, 기존 합성 도메인의 최종 2차 포장 완료 기록과 출하 인계를 함께 조회한다. 008 가공 완료만으로는 행이 생기지 않는다. 최종 확정 수량, 품목, 출하 위치, 작업자와 시간을 응답에 사용한다. 수주량·불량처럼 이 이벤트에서 제공하지 않는 값과 해당 합계는 공란이다. 독립 데이터는 조회·XLSX 단위 테스트에 사용한다.

### 검증

| 확인 항목 | 결과 |

| Spring HTTP | 미인증 401, 다른 사업장 격리, 완료 전 빈 결과, 2차 포장 완료 후 기존 이벤트 기반 행, 반복 조회 무변경을 확인했다. 실제 응답 행을 메모리 XLSX로 내보내 완성 수량과 공란을 재열기로 검증했다. |

### 최종 독립 검증

독립 빌드와 실행에 사용한 App·실적 컨트롤러 해시를 배치 사본과 대조했다. Spring HTTP는 미인증 401, 타 사업장 빈 결과, 잘못된 날짜·순번 400을 확인했다. 008 가공 완료 시점까지 결과가 비어 있었고, 2차 포장 완료와 출하 인계 이후 실적 한 행이 생겼다. 반복 조회 전후 008·출하 상태는 같았다.

실제 Chrome에서 008부터 2차 포장까지 수행하고 최종생산조회 화면을 열었다. 같은 계획을 다시 조회해도 행은 한 건이었다. `ProductionData.xlsx` 다운로드 이벤트를 확인하고, 디스크 저장을 차단한 뒤 메모리 바이트의 15개 셀과 생산량 합계를 화면과 대조했다. 미확정 수주량·불량과 그 합계는 공란이었다. 게시된 생산계획을 포함한 기존 메뉴 접근도 확인했다. 실배치 웹 빌드는 통과했다.

## ⚠️ 주의사항

컴포넌트는 파일명과 XLSX 바이트를 `onExport`에 전달한다. 별도 App 사본에서 다운로드를 연결했다. 검증 하네스는 Chrome 다운로드 시작 이벤트를 확인한 뒤 디스크 저장을 막고 메모리 바이트를 검사했다. 운영 서버 필터·행 순서와 실제 합계, 원본 XLSX 외형은 별도 확인 대상이다. 웹 빌드는 통과했고 게시된 재고이동·생산계획 화면의 ref cleanup lint 경고 2건은 그대로다.
