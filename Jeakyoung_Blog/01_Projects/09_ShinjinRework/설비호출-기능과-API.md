## Spring demo HTTP

기본 경로는 `/api/demo/machine-calls`다. 로그인은 기존 HttpSession을 사용한다. 아래의 key는 합성 명령 UUID다. 같은 단말·작업자의 같은 키와 정규화된 같은 본문은 최초 결과를 반환한다. 스캔 토큰은 해당 세션의 설비·이슈·조치에 귀속된다.

| 메서드와 상대 경로 | 입력과 결과 |
|---|---|
| GET / | 로그인 단말에 설정한 설비 id/name/openCount |
| GET /{machine} | 설비, issues, callReasons, actions. 각 이슈에 발생자·시간·사유와 해결자·시간·조치 |
| POST /{machine}/issues | key와 reasons 배열. 모든 코드를 먼저 검사하고 사유마다 발급한 이슈 ID 배열 반환 |
| POST /{machine}/issues/{issue}/scan | action과 employeeNo. 원문 사번을 합성 근무자 명단에서 확인한 임시 token |
| DELETE /scans/{token} | 현재 세션의 일치하는 스캔 취소 |
| POST /{machine}/issues/{issue}/close | key와 token. 선택 이슈의 해결자와 조치 결과 기록, 해당 ID 배열 반환 |

미로그인은 401, 다른 단말의 설비 또는 유효한 스캔 확인이 없는 제출은 403이다. 없는 이슈는 404, 잘못된 사유나 사번은 400, 완료 이슈의 재조치 또는 기존 명령 키와 다른 본문은 409다. 데모는 서버 메모리 안에서만 원자성을 검증한다. 실제 SP 정의, 트리거, 현장 권한·경과시간 산식은 호출부만으로 확정할 수 없다.

## 화면과 이관 경계

로그인 후 하단 설비 버튼 → 호출 상세 → 사유/등록/예 → 이력의 미완료 행 → 조치자 → 담당자 입력 → 예 → 같은 이력 행에서 결과를 본다. 원본 Designer의 스핀들·베드·에러코드 숫자 0과 가동시간 대시는 초기 면판 표시다. 설비 실측값이 아니다. 별도 설비 수리내역 조회, 소모품 교체 및 장비 실시간 수집은 이 호출 API에 포함되지 않는다. 실제 공용 셸 마운트와 현장 장치 연결은 독립 검증 이후의 작업이다.


## 조치자 스캔의 취소와 재시도

ComIssue.cs 391의 담당자 스캔을 단말 하단 설비 → 호출 사유 등록 → 미조치 호출행 → 조치자 → 등록 순으로 확인했다. 미등록 합성 사원은 알림 뒤 입력창으로 복귀하고, 유효 사원 확인의 아니오는 조치 입력을 유지한다. 재시도 후 예를 눌렀을 때 완료 알림과 부모 복귀를 확인했다. 세 화면 크기의 터치 검증 기록은 [[32-공통팝업-기능명세]]에 있다.

## 두 작업자가 같은 호출을 조치할 때

하단 설비의 호출사유는 여러 행을 골라 등록할 수 있다. 조치내용 창은 한 행을 선택하고 등록 시에만 사원 스캔을 요청한다. 관리의 수리내역 화면은 조회용이고, 관리의 소모품 화면은 별도의 세 탭으로 동작한다. 설비 소모품 신청은 하단 설비의 소모품 교체 탭에서 열린다.

다른 세션이 먼저 완료하면 담당자 스캔 POST 또는 조치 확정 POST가 409를 반환한다. 웹은 해당 호출의 조치창·스캔창을 닫고, 도크 집계와 선택 설비의 이력을 다시 조회한다. 완료행에는 먼저 조치한 담당자가 표시된다. 통신 응답 유실 시에는 같은 키로 재전송해 처음의 호출번호·조치 결과를 조회한다. 격리된 실제 Chrome 두 세션으로 선완료 두 시점, 호출·조치 응답 유실 후 재시도, 같은 설비 재진입을 검증했다. 빈 이슈번호에 대한 원본의 처리 안내는 별도 인수 항목이다.
