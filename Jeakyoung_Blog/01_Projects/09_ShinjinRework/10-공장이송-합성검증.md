# 공장이송 합성 검증

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **용도** | 공장이송 의뢰·출고·입고와 역순 취소의 인수 기준 |
| **대상 시스템** | POP·ERP를 분리한 로컬 합성 메모리 모델 |
| **확인 상태** | 워커 합성 통합 검증 통과, 독립 P2 재검토 통과 |

## ⚙️ 환경 및 전제

레거시 호출부를 정적으로 읽고, 회계는 합성 재고 수량과 전표 연결로 검증한다. 오케스트레이션은 ERP 발행과 POP 발행을 독립 커밋처럼 모의한다. 문서의 수량과 상태는 합성 예시다.

## 📖 상세 내용

### 합성 회계와 상태 전이

POP는 의뢰 상태·상세·위치별 재고와 ERP 연결을 보존한다. ERP는 의뢰·출고·입고의 헤더와 상세, 출고 확정 상세, 명령 영수증을 보존한다. 활성 전표는 의뢰·종류당 하나이며 재발행은 새 회차를 사용한다. 상세는 전표·항번으로 식별하고 입고 각 행은 원출고 전표와 항번을 참조한다. 재고 반영은 품목별 합계를 쓰며 입고와 역처리는 출고 확정 상세를 기준으로 한다.

| 명령 | POP 상태 | 재고 및 활성 전표 |
| --- | --- | --- |
| 의뢰 | 신규 → `REQUESTED` | 재고 유지, 의뢰 전표 생성 |
| 출고 | `REQUESTED` → `SHIPPED` | 출발 차감, 출고 전표 추가 |
| 입고 | `SHIPPED` → `RECEIVED` | 도착 증가, 입고 전표 추가 |
| 입고 취소 | `RECEIVED` → `SHIPPED` | 도착 차감, 입고 전표 제거. 도착 가용량 부족 시 거절 |
| 출고 취소 | `SHIPPED` → `REQUESTED` | 출발 복원, 출고 전표 제거 |
| 의뢰 취소 | `REQUESTED` → `CANCELLED` | 재고 유지, 의뢰 전표 제거 |

합성 품목 X를 두 항번에서 2와 1, Y를 한 항번에서 1 요청한다. 출발 X/Y 5/2와 도착 0/0에서 완료하면 출발 2/1과 도착 3/1이다. 역순 취소를 완료하면 초기 잔액으로 돌아오며 활성 전표가 남지 않는다.

### 보류·재시도

- ERP 발행 전 실패는 두 저장소를 보존한다. ERP 발행 직후 실패는 POP 상태·재고를 그대로 두고 ERP 결과와 보류 영수증을 남긴다.
- 보류 중인 의뢰는 같은 키와 동등한 입력으로만 재개한다. 다른 단계는 `RECONCILIATION_REQUIRED`로 거절한다. 동일 키에 다른 수량을 보내면 충돌 처리한다. 상세 행 순서를 동등성에 포함할지는 인수 전에 확정한다.
- 보류 출고량은 다른 의뢰의 가용량에서 제외한다. 입고 보류량은 목적지 상한 여유를 예약한다. 같은 명령을 재개할 때 자기 예약을 중복 계산하지 않고 POP를 한 번만 적용한다. 완료된 명령의 재전송은 응답을 재생한다.
- 간편이송 합격 기준은 ERP 세 전표의 일괄 발행, 중단 중 POP 무변경, 동일 명령 재개 후 POP 최종 상태와 재고의 일괄 반영이다.

### 명령 재시도 격리

공장별 메모리 저장소에서 문서와 재고를 조회한다. 같은 공장의 다른 세션이 문서를 조회할 수 있어도 보류 명령의 본문과 기존 키 재생은 원래 단말·작업자에게만 허용한다. 브라우저는 명령을 송신하기 전에 단말·작업자별로 키와 합성 본문을 보존한다. 응답 유실 뒤 401이 발생하면 재인증 후 같은 단말·작업자만 사본을 읽어 동일 요청을 재생할 수 있다. 다른 세션의 화면에는 사본이 표시되지 않고 서버 재생 요청은 403으로 거절된다. 모의 실패 필드는 생략하면 false로 처리한다.

### 검증 결과와 남은 인수 항목

| 근거 | 확인 범위 |
| --- | --- |
| 워커 Java 도메인 하네스 | 8개 시나리오 통과. 정상 단계와 역순 취소, 간편이송 세 문서의 ERP 일괄 발행, ERP 상세 불일치 차단, 예약과 공유 재고 경합, 같은 키의 재생을 확인했다. |
| 워커 Spring HTTP | 실패 모의 필드를 생략한 일반·재개 요청, 공장 격리와 다른 작업자의 재생 거절, 간편 경로의 ERP 선커밋 후 보류 응답 및 역순 취소를 확인했다. |
| 워커 웹 빌드·Chrome | 웹 빌드가 통과했다. Chrome에서 순차 의뢰·출고·입고 및 역순 취소, 부분 커밋 후 동일 명령 재시도, 응답 유실·401 뒤 재인증, 다른 작업자 격리와 전표 한 건 유지, 작업이력·LOT·단일 008 화면 접근을 확인했다. 간편이송 배치 검증의 근거는 도메인·HTTP다. |
| 독립 리뷰 | 기존 독립 검증은 합성 도메인 범위에서 간편이송 배치와 상세 대사 및 행 순서 정규화를 확인했다. 최종 P2 재검토에서는 최신 수정본 해시를 대조하고 루프백 HTTP와 Chrome으로 두 항목의 통과를 확인했다. 필드 생략 요청은 정상 도메인 응답을 받았고, 같은 브라우저 탭에서 응답 유실과 401 이후 원래 작업자의 재생만 허용됐다. 성공 후 보존 사본이 제거되고 전표는 한 건이었다. |

## ⚠️ 주의사항

검증은 별도 합성 통합 스냅샷에서 실행됐다. 기준 코드에는 이후 게시된 008 생산그룹 변경이 포함되지 않았다. 운영 데이터의 재고·권한·실제 ERP 트리거와 채번, 독립 저장소의 지속성, 프로세스 재기동·장애 후 영속 복구는 미검증이다. 별도 창고이동은 후속 범위다.
