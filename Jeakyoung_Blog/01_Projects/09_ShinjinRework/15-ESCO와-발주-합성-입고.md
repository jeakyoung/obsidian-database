# ESCO·발주 합성 입고

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **용도** | L4 ESCO와 L5 발주입고의 원문서·잔량·권한·재시도를 확인한다. |
| **기준** | 코드 `cb30568`, vault `b8fea31` |
| **확인 상태** | 독립 모듈·공용 App 검증과 P2 독립 재검토 통과. |

## 📖 상세 내용

### 서로 다른 원문서

| 단위 | WinForms 진입과 조회 | 합성 계약 |
| --- | --- | --- |
| L4 ESCO | `POPLGS/frmLogistics4`에서 출하번호와 조회 기간을 사용한다. 출하 품목·수량과 입고수량을 각각 표시한다. | `ESCO_SHIPMENT`의 출하 문서와 항번을 조회한다. 선택 항번의 일부 또는 남은 수량을 입고한다. |
| L5 발주입고 | `POPLGS/frmLogistics7`에서 회사·사업장과 선택일로 조회·저장한다. 입고번호·품목·수량·창고·MES 반영 표지가 있다. | `PURCHASE_ORDER`의 발주 문서와 항번을 조회한다. 부분 입고와 잔량 소진을 발주 문서 상태에 반영한다. |

합성 조회는 유형과 선택 번호·날짜로 좁힌다. 번호가 같아도 ESCO와 발주는 별개다. 입고는 항번과 양수 수량을 받으며, 품목·창고·작업자는 서버가 확정한다. 선택 행의 검증, 잔량·버전·이력·재고·영수증 갱신을 한 잠금에서 반영한다. 초과·중복·완료 행, 오래된 버전 또는 다중 행의 일부 오류는 기존 상태를 보존한다.

### 권한과 401 복귀

인증 단말에 할당된 문서·재고만 조회한다. 같은 사업장의 다른 단말도 원문서 조회·저장을 할 수 없다. 같은 단말의 인증 작업자는 새 입고를 실행할 수 있지만, 성공 키는 원래 작업자만 같은 본문으로 재생할 수 있다. 바뀐 본문은 충돌이며 정규화된 행 순서와 같은 수치 표현은 기존 요청으로 처리한다.

최신 App은 최초 전송 전에 같은 탭의 단말·작업자별로 합성 키와 직렬화한 본문을 보존한다. 최초 보존이 실패하면 전송을 시작하지 않는다. 응답 유실과 401 이후 원래 작업자가 같은 요청을 복구하고, 성공이나 확정 거절에서 사본을 지운다.

### 검증 범위

| 근거 | 확인한 내용 |
| --- | --- |
| 초기 독립 리뷰 | Java·HTTP에서 두 유형의 번호·필터·항번 분리, 부분·전량 입고, 단말 범위, 요청 충돌·권한, 경쟁 요청 한 건 반영 및 실패 시 무변경을 확인했다. 검증용 Chrome 화면에서 같은 화면 내 응답 유실 후 재시도를 확인했다. 이때 401 이후 재인증 복구와 공용 App 연결은 미완이었다. |
| 최종 공용 App과 P2 실행 | `cb30568` 기반 Chrome에서 ESCO·발주 행 분리, 부분 잔량·초과 방지, 응답 유실과 401 이후 동일 키·본문 복구, 타 작업자 격리와 수량 무중복을 확인했다. 함께 실행한 기존 업무 메뉴와 출력 PDF 벡터의 회귀도 통과했다. |
| 최종 P2 독립 재검토 | 독립 화면과 공용 App을 각각 실행했다. 발주 최초 성공 응답을 유실시킨 뒤 실제 401과 재로그인을 거쳐 원래 작업자만 동일 키·본문을 재생했다. 다른 작업자에게 복구 항목이 표시되지 않았고 직접 재생은 403이었다. 재생 후 revision·잔량·영수증은 한 번 반영된 상태 그대로였다. ESCO는 부분 입고·동일 키 재생·타 작업자 403을 HTTP에서 확인했다. |

## ⚠️ 주의사항

실제 ERP의 조회·잔량 산식, 원문서 상태와 채번, 매입·정산, 취소·보정, 운영 공유 재고 및 영속 복구는 미검증이다. 합성 원문서의 상태와 항번은 데모 계약이다. 재시도 사본의 범위는 같은 브라우저 탭·오리진과 단말·작업자이며, 탭 종료·저장소 삭제·서버 재시작 이후 복구는 미검증이다.
