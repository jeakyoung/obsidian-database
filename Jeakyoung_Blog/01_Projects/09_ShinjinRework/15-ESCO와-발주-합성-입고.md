# ESCO·발주 합성 입고

## 현재 화면 및 API 명세

발주입고는 선택 날짜의 사업장 단위 일괄 반영이고 ESCO 입고는 출하 전표 1건의 처리다. 운영 화면에는 행별 임의 부분입고 수량이나 LOT 편집 필드가 없다. 원본에서 LOT와 창고 코드를 SP 내부 처리에 참조하는 것과 작업자가 화면에서 입력하는 것은 별도다.

### 발주입고

`POPLGS/frmLogistics7.cs:26,56,61,154,229`. 생성자의 오늘 날짜 설정과 날짜 변경 이벤트가 목록을 조회한다. 조회 버튼은 Designer에서 숨겨져 있다. 날짜와 저장 버튼 아래에 No, 입고일자, 입고번호, 입고품목, 입고수량, 입고일시, 입고창고, 반영여부가 표시된다. 저장은 확인 추가 팝업 없이 수행한다.

| 구분 | 원본 호출 또는 웹 요청 | 처리 |
|---|---|---|
| 조회 | `SP_POP_DZ_PO_VIEW` / GET `/api/pop/procurement/forms/purchase?date=YYYY-MM-DD` | 회사 1000, 로그인 사업장이 000001이면 ERP 사업장 2000, 그 외 원본 분기는 1000. 선택 날짜를 시작·종료일로 함께 전달한다. 웹에는 현재 세션의 `date`, `rows`가 반환된다. 날짜 생략 시 데모 기준일이다. |
| 저장 | `SP_POP_DZ_PO_AUTO` / POST `/api/pop/procurement/forms/purchase` | 서버가 세션 사업장을 정한다. 입력은 `requestId`, `date`. 단일 POP DB 트랜잭션에서 호출하며 helper가 false를 반환하면 rollback, 성공하면 commit 뒤 조회를 다시 수행한다. 데모는 별도 데이터셋의 반영 후 행을 원자적으로 제공한다. |

### ESCO 입고

`POPLGS/frmLogistics4.cs:28,127,208,227,415`. 화면 진입 시 조회하지 않는다. 출하번호를 스캔하고 Enter로 조회한다. 출하·입고 일자, 번호, 품목, 수량, 일시를 위/아래 두 줄로 보여주고 입고창고를 함께 표시한다. 조회 결과가 0행이면 원본은 현재 그리드를 그대로 둔다. Clear는 입력과 그리드를 모두 비운다.

| 순서 | 원본 | 계약 |
|---|---|---|
| 조회 | `NEOE.UP_CZ_SM_ESCO_GI_SM_PU_IN_A_POP` | 회사 1000, POP DB 기준 당월 1일~오늘, 입력 출하번호. 웹 GET `/api/pop/procurement/forms/esco?number=...`에서 `number`, `rows`를 반환한다. |
| ERP 생성 | `NEOE.UP_CZ_SINJINSM_CRT_PU_IN_AUTO_ESCO` | 원본 저장은 입력 길이 14자, 회사 1000, 오늘에서 2개월 전~오늘, 입력 출하번호를 사용한다. |
| ERP 월재고 | `NEOE.CZ_SINJINSM_UP_PU_MM_OHSLINVM_UPDATE_YM` | 표시 행마다 창고코드·사업장·회사·입고품목·시작일·종료일을 전달한다. 앞의 ERP 생성과 같은 ERP 트랜잭션이다. |
| POP 반영 | `SP_POP_ESCO_AUTO` | 회사·출하번호·작업자·부서·시각을 별도 POP 트랜잭션에 전달한다. 결과 행을 그리드에 바인딩한 후 ERP, POP 순으로 commit한다. 빈 결과에는 성공 메시지와 명시적인 commit이 없다. ERP 생성/월재고 호출 실패는 두 트랜잭션을 rollback한다. |
| 웹 저장 | POST `/api/pop/procurement/forms/esco` | `requestId`, `number`, `displayedNumber`. 일치하는 합성 전표의 전 행을 처리하며 같은 요청 재전송 결과는 재사용한다. 오류 시 새 성공 행을 만들지 않는다. |

원본은 이전 전표 행이 남아 있어도 새 입력번호의 저장 절차를 시도할 수 있다. 정상 경로의 인수는 조회 성공한 번호와 저장 번호가 일치하는 경우다. 서로 다른 번호 처리 정책은 별도 운영 결정이 필요하다. 현재 데모의 불일치 응답은 409다.

### 합성 검증 및 운영 대사

`src/api/src/main/resources/demo/receiving-forms.json`을 사용한다. 발주 POP A에서 2026-11-25의 2행을 저장하면 반영여부가 N에서 Y로 바뀐다. 같은 사업장 POP A2 조회에 반영되고 POP B에는 반영되지 않는다. 2026-11-23은 저장 실패 후 상태 유지 사례다. ESCO의 정상 출하번호는 POP A에서 TESTESCO000001, POP B에서 TESTESCO000002다. POP A의 끝자리 3·4·5는 각각 ERP 생성 실패, 월재고 실패, POP 결과 0행 사례다.

격리한 Spring과 1280×800 Chrome에서 날짜 자동 조회, 일괄 저장, 날짜별 빈 결과와 실패, ESCO 스캔과 Clear, 전표 2행 전체 저장, 단계별 오류, 동일 요청 재전송, 사업장 분리 및 로그인 만료를 확인했다. 합성 저장은 별도 사전·사후 데이터셋과 메모리 상태를 사용한다. ERP/POP의 두 실제 commit 사이 장애, DB 재처리 가능 여부, 내부 LOT 채번·수불·월재고와 운영 SP 버전은 연결 전 계약 대사가 필요하다.

합성 조회는 유형과 선택 번호·날짜로 좁힌다. 번호가 같아도 ESCO와 발주는 별개다. 입고는 항번과 양수 수량을 받으며, 품목·창고·작업자는 서버가 확정한다. 선택 행의 검증, 잔량·버전·이력·재고·영수증 갱신을 한 잠금에서 반영한다. 초과·중복·완료 행, 오래된 버전 또는 다중 행의 일부 오류는 기존 상태를 보존한다.

### 권한과 401 복귀

인증 단말에 할당된 문서·재고만 조회한다. 같은 사업장의 다른 단말도 원문서 조회·저장을 할 수 없다. 같은 단말의 인증 작업자는 새 입고를 실행할 수 있지만, 성공 키는 원래 작업자만 같은 본문으로 재생할 수 있다. 바뀐 본문은 충돌이며 정규화된 행 순서와 같은 수치 표현은 기존 요청으로 처리한다.

최신 App은 최초 전송 전에 같은 탭의 단말·작업자별로 합성 키와 직렬화한 본문을 보존한다. 최초 보존이 실패하면 전송을 시작하지 않는다. 응답 유실과 401 이후 원래 작업자가 같은 요청을 복구하고, 성공이나 확정 거절에서 사본을 지운다.

## ⚠️ 주의사항

실제 ERP의 조회·잔량 산식, 원문서 상태와 채번, 매입·정산, 취소·보정, 운영 공유 재고 및 영속 복구는 미검증이다. 합성 원문서의 상태와 항번은 데모 계약이다. 재시도 사본의 범위는 같은 브라우저 탭·오리진과 단말·작업자이며, 탭 종료·저장소 삭제·서버 재시작 이후 복구는 미검증이다.

## 단말 해상도별 입고표 확인

발주입고와 ESCO 입고의 원본 Designer는 상단 80px과 나머지 조회표로 배치한다. 표시순서, 마지막 빈 밴드, 10.2pt 열 글꼴과 수량·품목·일자의 원래 비율을 적용했다. 길이가 긴 합성 전표 42자로 시험한 결과 1280×800, 1366×768, 1024×768에서 본체와 입고표의 가로 넘침이 0px이고 오른쪽 반영여부까지 동시에 확인됐다. ESCO는 조회번호 14자와 두 행의 출하·입고 대조를 유지한다. 원본 작업트리의 `.team/screen-review/web-parity/관리-입고-다중해상도/검증.md`에 조작 경로와 합성 이미지가 있다.


## 발주일 터치 달력

frmLogistics7.Designer.cs 166·170 및 작업실적조회 Fluent DateEdit에 맞춰 발주입고 상단 날짜를 누르면 일·월·연도 선택 달력이 열린다. 날짜를 선택하면 GET `/api/pop/procurement/forms/purchase?date=YYYY-MM-DD`로 목록을 즉시 갱신한다. 이전·다음 이동 후 Escape는 현재 조회일을 유지한다. 1280×800·1366×768·1024×768에서 날짜 버튼 42개, 선택 후 실제 조회, 기존 일괄 입고와 실패 경로를 검증했다.
