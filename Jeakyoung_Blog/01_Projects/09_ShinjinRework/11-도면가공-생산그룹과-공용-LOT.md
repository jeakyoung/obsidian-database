# 도면가공 생산그룹과 공용 LOT

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **용도** | 008 생산그룹의 자재 후보, 공용 재고 차감, 묶음 완료 인수 기준 |
| **기준** | 게시된 단일 계획 소스 `cde892b`, 작업 노트 09의 문서 기준 `832e0eb` |
| **확인 상태** | 합성 그룹 처리와 계획별 투입 이력 검증 통과 |

## ⚙️ 환경 및 전제

09에서 확인한 단일 계획 상태·버전·단말 소유권과 1차 포장 → 008 → 2차 포장 인계를 기준으로 삼는다. 11에서는 같은 생산그룹의 여러 계획과 서로 다른 그룹이 공유하는 재고를 분리해 검증한다. 수량과 식별자는 합성 입력을 사용한다.

## 📖 상세 내용

### 기존 패턴과 합성 경계

| 항목 | WinForms 소스 근거 | 합성 인수 기준 |
| --- | --- | --- |
| 그룹과 계획행 | `POPREG/frmProcess7.cs`의 `WorkStart`는 선택된 작업행을 처리하면서 기존 `prod_group_no`를 읽고, 비어 있으면 그룹번호를 얻는다(3326–3511행). 완료에서도 계획행과 그룹 참조를 함께 사용한다. | 그룹 키에 속한 계획행 집합을 명시한다. 명령은 그룹 범위와 참여 계획행의 버전·상태·소유권을 검증한다. 그룹 키를 계획행 키 대신 사용하지 않는다. |
| 자재 후보 | 같은 파일의 `gv3_FocusedRowChanged`는 기존 투입을 조회하고 투입 그리드가 비어 있으면 그리드 전체 작업행의 후보를 모은다. `FnSearchGrid1_1`은 시스템 LOT·창고·품목 기준으로 중복 후보를 걸러 작업자가 선택하게 한다(1027행, 10141행 이후). | 후보 표시용 중복 제거와 재고 차감 키를 구분한다. 하나로 표시된 후보를 여러 계획에 배정할 때는 같은 재고 키의 요청량을 합산한다. 위치를 구분하는 재고라면 선택한 위치까지 보존한다. |
| 공용 기록과 항번 | `WorkEnd`의 완료 분기는 같은 생산그룹의 008 실적에서 일보번호와 수불번호를 찾아 재사용하고 다음 수불항번을 계산한다. 1차 포장 일보와는 별도다(8764행 이후). 해당 경로의 마지막에는 ERP와 POP의 순차 커밋이 있다(9444행). | 한 묶음은 합성 008 일보 참조와 합성 수불 참조를 공유한다. 각 계획행은 같은 수불 참조 아래 고유 항번을 가진다. 이 관계는 합성 기록에서 검증하며 실제 ERP 채번, 실적·작업시간·일보·수불·출하 헤더와 명세의 행 대조는 별도다. |

### 구현과 검증 결과

합성 그룹 명령은 참여 계획 전체와 각 계획의 버전을 받는다. 정상 1차 포장을 마친 구성원만 함께 시작할 수 있다. 창고가 다르면 같은 LOT라도 재고를 분리한다. 공유 재고 키는 공장·사업장·LOT·창고·품목이다. 묶음과 단일 명령이 같은 메모리 잠금을 사용하며, 작업 복사본에서 모든 구성원을 검증한 뒤 함께 반영한다. 2차 포장과 출하 인계는 기존 계획별 경로를 사용한다.

| 항목 | 판정과 근거 |
| --- | --- |
| 후보·배정·동시 차감 | 워커 HTTP와 독립 리뷰에서 동일 LOT·창고·품목 후보를 한 번 표시하고 다른 창고 후보를 분리했다. 독립 리뷰에서 가용량 5를 두 계획에 2와 3으로 배정해 선택 재고만 0이 됐다. 두 묶음이 같은 재고에 3씩 경합하자 한 건만 성공해 2가 남았다. |
| 묶음 원자성과 재시도 | HTTP에서 두 번째 구성원 실패 후 재고·상태·버전·감사 이력 보존을 확인했다. 독립 리뷰의 두 번째 완료 기록 직전 예외에서도 전체 스냅샷이 보존됐고, 실패 명령을 같은 키로 다시 제출해 성공했다. 성공 명령 재전송은 동일 응답을 반환했고, 같은 키로 수량을 바꾸면 거절됐다. |
| 공용 기록 | 완료한 두 계획은 2차 포장 대기로 전이했다. 그룹 응답과 계획 감사의 합성 일보·수불번호는 같고 수불항번은 계획별로 달랐다. |
| 화면과 회귀 | 워커의 Java 회귀 6건과 React 빌드·lint, Spring HTTP, Chrome 그룹 화면이 통과했다. Chrome에서 후보 중복 제거, 계획별 입력, 전체 시작·완료를 확인했다. 단일 008, LOT, 작업이력 회귀도 통과했다. 독립 리뷰는 Java·HTTP·TypeScript로 확인했다. |
| 계획별 투입 이력 | P2 재검토에서 동일 재고의 중복 투입 행을 합산해 계획별 수량 2와 3을 기록했다. 그룹 상세와 계획 감사의 `drawingInputs`에서 같은 LOT·창고·품목·수량을 확인했다. 완료 후 재조회와 동일 요청 재생에서도 보존됐다. |
| 실패 시 무변경 | 초과 배정·잘못된 후보·오래된 버전·재고 경합으로 시작이 실패하면 그룹 상세와 감사에 새 배정이 남지 않았다. 두 번째 완료의 수량 오류와 기록 직전 예외에서는 기존 배정과 상태가 유지됐다. |

### 별도 미완 인수

- **혼합 묶음** — 정상 1차 포장과 생략 승인이 섞인 묶음의 자동 잔재 배정은 후속 범위다.
- **현장 연동** — 실제 ERP 채번과 작업시간·실적·일보·수불·출하 행의 대조, 취소·보정, 운영 공유 재고와 장애 후 복구는 별도 검증 대상이다.

## ⚠️ 주의사항

판정 범위는 합성 그룹 처리이며 저장소와 성공 영수증은 프로세스 메모리에 있다. 독립 리뷰의 HTTP는 생성된 클래스로 검증했으며, 로컬 컴파일러의 JAR 종료 접근 진단은 전체 배포 빌드 통과로 집계하지 않았다.
