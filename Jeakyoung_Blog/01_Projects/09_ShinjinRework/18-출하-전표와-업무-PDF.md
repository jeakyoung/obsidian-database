# 출하 전표와 업무 PDF

## 📋 개요

18번 작업 노트. 코드 기준 `f2d9f0d`, vault 기준 `60ff7d1`. 최신 통합과 독립 Spring HTTP·Chrome 검증을 통과했다. 매니페스트와 검토 화면 해시를 대조했다.

## 📖 상세 내용

14의 출력 메뉴는 고정 합성 예제를 렌더링한다. 이 흐름은 서버에서 확정한 합성 출하 전표를 읽어 업무 문서 참조와 PDF를 구성한다. 브라우저가 LOT·수량·전표 내용을 제출해 PDF를 바꾸는 경로와 구분된다.

| 계약 | 확인 범위 |
| --- | --- |
| 권한 | 미인증 문서·PDF는 401. 같은 사업장의 다른 단말과 타 사업장은 각각 범위 오류로 403. 활성 전표가 만들어지기 전은 404, 취소 후 새 미리보기와 다운로드는 409다. |
| 재출력 | 재출력 명령은 버전과 횟수를 한 번 갱신한다. 같은 키 재생은 같은 결과를 반환한다. 출하 문서 참조와 PDF의 업무 데이터는 재출력 전후 동일하다. |
| 다운로드 | 미리보기·PDF 읽기는 횟수, 전표 버전이나 상태를 변경하지 않는다. 성공 PDF는 출하번호 기반 첨부 파일명과 PDF 응답을 사용한다. |

## 검증

`app-integration-f2d9f0d/verification/integration.log`에서 출하 미리보기·재출력의 동일 참조와 데이터, 업무 PDF의 실제 Chrome 다운로드, HTTP의 단말·사업장 권한, 읽기 시 무변경과 취소 이후 차단이 통과했다. 기존 화면과 14의 고정 PDF 벡터 회귀도 확인했다. 독립 리뷰에서 PDFBox로 문자를 추출해 출하번호·품목·LOT·수량·합계·포장 참조·확정 시각을 서버 값과 대조했다. 업무 PDF 한 건 다운로드와 재출력 전후 문서 데이터 보존을 Chrome에서도 확인했다. 문서 권한은 사업장과 지정 단말 범위이며 작업자별 문서 소유권은 이 데모 계약에 포함되지 않는다.

실배치 Maven·웹 빌드도 통과했다(배치 확인 기준).

## ⚠️ 주의사항

합성 출하 전표만 사용한다. 실제 ERP 전표·운영 데이터·물리 인쇄와 영속 복구는 후속이다. 공용 문서에는 게시 시점의 최신 HEAD를 기준으로 반영한다.

## 2026-11-26 출하 작업 화면과 LOT 전표

원본 `POPLGS/frmLogistics6.cs`의 열 표시, 조회, 적용, 저장·취소·인쇄를 `ShippingForm.tsx`, `ShippingGrid.tsx`, `ShippingOptions.tsx`, `ShippingDemoController.java`에서 대조했다. 화면 선택기의 경로는 **물류 → 출하**다. 구버전 프리뷰 15175에서는 포장 인계별 작업 메뉴가 표시된다. 15176·15177은 두 그리드 버전이지만 별도의 상단 검색 API는 포함하지 않았다. 15177에는 다전표 미리보기 API도 없었다. 아래 내용은 전환 작업 트리와 격리된 합성 Spring 기준이다.

| 원본 조작 | 연결된 동작 |
| --- | --- |
| 시작과 날짜 | 두 그리드는 처음에 비어 있다. 포장 시작일은 3일 전, 포장 종료일과 출하 완료일은 오늘이다. 출하일자는 오전 8시 전에는 전날이다. 자동인쇄는 선택 상태다. |
| 상단 조회 | 거래처, 포장일 범위, 재질·품목유형·작업반 선택 목록, 수주담당자와 이월 체크를 서버에 보낸다. 선택 행 수와 포장 수량을 표시하고 하단 초안을 비운다. |
| 선택창 | 거래처는 `COMMON/ComCustomer`에서 검색어 입력·Enter·Clear·키보드·적용·닫기를 쓴다. 재질은 `POPPRINT/frmMaterialOption`, 품목유형과 작업반은 `POPLGS/frmItemKind3`, `frmWorkcenter`다. 원본 선택창의 타이틀 이미지와 닫기 이미지를 사용한다. 적용·저장 시에만 값을 바꾼다. 품목유형·작업반의 이전 저장 시점 이후 신규 코드는 원본처럼 초기 선택하고, 재질은 저장한 목록을 따른다. 웹은 동일 브라우저의 단말 키로 저장한다. |
| 포장 선택 및 적용 | 행을 누르면 수주번호가 같은 포장 행들이 함께 바뀐다. 선택 머리글은 전체 선택/해제다. 적용·수주번호 스캔이 하단 초안에 해당 LOT를 추가한다. 16자리 스캔은 앞 12자리를 사용한다. 중복 적용을 막고 기존 초안을 유지한다. 같은 포장번호에 여러 LOT가 있으면 상단 1행에서 하단 여러 행으로 확장한다. |
| 하단 행 및 삭제 | 초안에서는 같은 포장번호를 함께 선택하며 삭제는 로컬 초안만 변경한다. 하단 조회는 완료일과 거래처로 완료 상태의 LOT들을 읽는다. 완료내역의 개별 행 터치는 같은 전표만 선택하고 다른 전표를 해제한다. 머리글 선택은 여러 전표에 적용된다. 완료내역 삭제는 확인 후 선택한 전표 전체를 취소하고 하단을 다시 조회한다. |
| 저장 | 하단의 체크 여부와 관계없이 모든 초안 행을 검사한다. 포장일 이전 출하 및 LOT 재고 초과는 중단한다. 부족 행은 빨간 글씨다. 확인 취소는 상태를 보존한다. 성공하면 상단을 재조회하고 하단 초안을 비운다. |
| 전표와 인쇄 | 거래처, `ETC_COL1` 제품군 또는 품목유형 우선순위(SA/SL/SS 대 나머지)가 달라지면 번호를 나눈다. 거래처 그룹은 초안의 최초 등장 순서를 따른다. 우선순위 0은 제품군·재질·두께·폭·길이 순, 1은 제품군·재질·포장번호 순이며 동률 행의 초안 순서를 유지한다. 같은 키로 묶인 여러 LOT의 전표 한 장에 LOT와 합계가 모두 들어간다. 원본의 수동·자동·메일 보고서가 15행씩 묶는 규칙을 따른다. 선택된 여러 전표의 수동 미리보기·PDF는 합쳐서 표시하고 합성 프린터 2에 한 번 전달한다. |

`ComShipplanSeq`를 만드는 문장은 원본 2665–2690행에서 주석 처리되어 있어 출하 조작으로 등록하지 않았다. 숨김 완료/완료삭제 버튼도 노출하지 않는다. 거래처 선택기의 원본 키보드는 OS의 `osk.exe`다. 웹 키보드 버튼은 입력에 초점을 주고 기기가 지원하면 터치 키보드를 연다.

### Spring 요청과 실제 SP 인수

| 요청 | 입력과 응답 |
| --- | --- |
| `GET /api/pop/shipping/form?includeRows=false` | 로그인 단말과 작업자, 사업장 범위의 선택 목록을 읽는다. 첫 화면에서는 인계 행을 읽지 않는다. |
| `POST /api/pop/shipping/queries/packing` | `dateFrom,dateTo,customerCode,matquality[],itemKind3[],workcenterCode[],opmanName,carryOverFlag`. 마지막 값은 문자열 0 또는 1이다. 원본 `SP_POP_LGS_LOGISTICS6_01_LIST`의 회사·사업장 값은 세션에서 결정한다. 원본은 조회 후 ERP 수주번호·순번 쌍이 실제로 존재하는지도 검사한다. |
| `POST /api/pop/shipping/queries/completed` | `optime,customerCode`와 세션 사업장. 원본 `SP_POP_LGS_LOGISTICS6_05_LIST(@PLANT_CODE,@OPTIME,@CUSTOMER_CODE)`의 완료일 바인딩을 유지한다. |
| `POST /api/pop/shipping/batch` | `requestId,action,rows:[{id,version}]`. CONFIRM은 `shippingDate,printChecked`도 보낸다. 서버가 현 세션의 LOT와 수량·포장일·재고·그룹 키를 읽고 모든 행을 검사한 뒤 반영한다. CANCEL은 전표에 속한 행 전체를 요청해야 한다. 동일 요청 재시도는 같은 결과를 반환하고 버전 충돌/재사용 값 충돌은 409다. |
| `GET /api/pop/shipping/{number}/document[/pdf]`, `/{number}/print-jobs` | 단건 출력 계약을 유지한다. 번호 하나에 속한 전체 LOT의 미리보기·PDF·합계, 합성 출력 호출 결과를 읽는다. |
| `POST /api/pop/shipping/documents/{preview,pdf,print}` | `numbers[]`의 순서로 여러 전표를 확인한다. preview는 장치·페이지와 대표 행 버전을 반환한다. pdf는 여러 거래명세서를 합친 PDF다. print는 같은 번호 목록·대표 버전·미리보기 장치·요청 ID를 받아 전체 상태를 검사한 뒤 합성 장치 호출 한 번을 기록한다. `GET /api/pop/shipping/documents/print-jobs/{requestId}`에서 해당 사용자·단말이 단일 제출의 전표 목록·총 페이지·장치를 확인한다. |
| 기존 `POST /api/pop/shipping/commands` | 기존 1건 CONFIRM/CANCEL/REPRINT의 인수·문서 접근 범위와 재시도 계약을 유지한다. 여러 LOT에 걸친 전표는 한 LOT만 취소할 수 없다. |

원본에서 LOT 상세는 `SP_POP_LGS_LOGISTICS6_02_LIST`, 거래처는 `06_LIST`, 품목유형은 `04_LIST`, 작업반은 `08_LIST`, 재질은 `SP_POP_ORDER_COMMON(MATERIAL_LIST)`를 사용한다. 실제 저장은 MES와 더존에 각각 트랜잭션을 열고 원전표·상세·LOT 순번을 발급받은 뒤 ERP와 MES 상세를 만든다. 원본은 더존을 먼저 커밋하고 MES를 커밋한다(1566, 1570, 2501–2502행). 완료 취소에서도 같은 커밋 순서를 쓴다(3126, 3129, 3316–3317행). 두 DB 사이의 중간 실패 복구, ERP 수주 대조, 운영 단가·금액·주소·인쇄/발송 이력은 실제 연결 시 각각 검증한다.

**운영 연결 전 확인할 값.** 호출부는 이월 체크 시 1, 해제 시 0을 보내고, 하단 완료일을 `@OPTIME`으로 보낸다. 운영 SP 본문이 없는 상태에서 1이 이월만인지 이월 포함인지, 완료일이 실제 생성일인지 업무 출하일인지는 확정할 수 없다. 합성 자료의 `carryQueryFixtures`는 0의 결과에 일반 건, 1의 결과에 일반·이월 건을 지정하고 완료일은 테스트에서 지정한 업무 출하일로 채운다. 운영 의미는 배포된 SP와 동일 입력의 반환 행을 대조해야 한다.

### 분리된 검증 데이터와 화면 근거

일반 데모에서는 포장 완료 인계가 생길 때만 출하 후보가 생긴다. 단독 검증 서버에 `--pop.demo.shipping-fixture=classpath:demo/shipping-form-verification.json`를 추가하면 2026-11-25 포장 5행이 생긴다. DEMO-A에서 로그인해 해당 날짜를 포장 범위에 넣고 **조회**를 누른다. 상단 첫 수주를 선택하고 적용하면 2개의 LOT가 들어간다. 저장 후 출하 완료일로 조회하고 전표 한 행을 선택해 인쇄를 누르면 미리보기와 PDF를 확인할 수 있다. PDF 검증 서버는 로컬 한글 글꼴을 지정하고 로그인 세션의 프린터 2를 합성 장치로 설정한다. 위 자료에는 운영 거래처·직원·실적이 없다.

같은 데이터로 비어 있는 화면과 선택 후 상태를 원본 `OUTPUT/POPLGS.dll` 및 선택창 DLL에서 캡처했다. 원본 DB 조회 이벤트는 연결하지 않고 같은 합성 행을 그리드에 주입했다. 전체 자식 화면은 1380×800, 재질·품목유형·작업반은 798×868, 거래처는 800×753이다. 두 실행 환경의 텍스트 렌더링과 달력·터치 키보드는 플랫폼 차이가 있다. 좌우 이미지, 좌표, 검증 시점은 분석 저장소 `.team/screen-review/web-parity/출하-화면대조.md`에서 확인할 수 있다.

같은 1380×886 운영 MDI의 경우 상단 86px, 미등록 설비 하단도 70px을 예약하며 출하 자식은 (3,88) 1374×725였다. 자식 단독 비교와 함께 분석 저장소에 별도의 전체 화면 증거를 보관했다.

공용 셸 보정 후 Chrome에서도 미등록 단말의 제목바 (0,0,1380,86), 출하 자식 (3,88,1374,725), 빈 설비 도크 (0,816,1380,70)가 일치했다. 더 작은 뷰포트에서도 원본 포장 표 높이와 가운데 조작부의 시작 위치를 유지한다.


## 출하 하위 선택창 터치 검증

frmLogistics6.cs 2690·2876·2892·2907에 따라 거래처·재질·품목유형·작업반을 실제 출하 폼에서 열었다. 거래처는 검색 입력에, 나머지 세 창은 첫 체크 항목에 포커스를 준다. 체크 변경 후 취소/재진입, 저장/재진입, 거래처 Enter 검색과 닫기/적용을 검증했다. 긴 합성 명칭이 인접 열로 침범하지 않도록 행 안에서 줄바꿈한다. 세 해상도 결과는 [[32-공통팝업-기능명세]]에 연결했다.
