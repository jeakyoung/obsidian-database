# 기술 스택 전체 구성(백엔드·프론트엔드·배포)

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | Scheduler-Service 백엔드+프론트엔드 전체 |
| **적용 범위** | 기술 스택 전수 정리 |
| **관련 모듈** | `backend/pom.xml`, `frontend/package.json`, `db/migration/*`, `.team/PLAN.md` |

> `backend/pom.xml`·`frontend/package.json`·Flyway 마이그레이션 파일을 직접 열어 확인한, 2026-11-20 기준 실제 기술 스택 전체 정리. 다른 기술문서들이 각 주제를 깊게 다루는 반면, 이 문서는 전체 그림을 한 번에 보기 위한 색인 성격.

## 🎯 배경 및 요구사항

사용자가 "기술스택은 어떤걸썼는지 전부 정리해봐"라고 직접 요청. 기억이나 추정이 아니라 실제 설정 파일(`pom.xml`/`package.json`/Flyway 디렉터리)을 그 자리에서 다시 읽어 버전까지 정확히 확인한 뒤 정리했다.

## 🏗 설계 및 구현

### 백엔드

| 영역 | 기술 | 비고 |
|:--|:--|:--|
| 언어/런타임 | Java 17 | |
| 프레임워크 | Spring Boot 3.5.16 | WAR 패키징(외부 Tomcat 배포용). 4.x가 이미 나왔지만 3.x 세대에 의도적으로 고정 |
| 웹 | Spring Web (REST API) | |
| 인증 | Spring Security + JJWT 0.13.0 | 세션이 아닌 stateless JWT (2026-11-13 결정) |
| DB 접근 | Spring JDBC (`NamedParameterJdbcTemplate`) | ORM(JPA/Hibernate) 미사용, SQL 직접 작성 |
| 스케줄링 엔진 | Quartz 2.3.2 (JDBC JobStore) | DB에 저장된 스케줄 정의를 동적으로 등록/해제 — [[01_Projects/08_MINI/01_SchedulerService/02_TechDocs/[기술] Quartz 기반 동적 스케줄 등록·해제 구조\|상세]] |
| 마이그레이션 | Flyway (vendor-split: `sqlserver`/`h2`) | V1~V4 (코어 → Quartz 테이블 → 대상DB 다중선택 → 멀티테넌시) |
| 대상 업무 DB | MSSQL (`mssql-jdbc`, runtime scope) | SP 호출 전용, 멀티 DBMS 지원 안 함(의도적 범위 제한) |
| 메타 DB(로컬 dev) | H2 (파일 기반 fallback, runtime scope) | `DB_URL` 미설정 시만 사용, 업무 DB와 무관 |
| 암호화 | AES-256-GCM (자체 `CredentialCipher`) | 자격증명 값 암호화 저장 |
| 테스트 | JUnit5 + Spring Boot Test + Testcontainers(MSSQL) + spring-security-test | 실제 MSSQL 컨테이너로 통합 테스트 |
| 빌드 | Maven + `frontend-maven-plugin` 2.0.2 | `prepare-package` 단계에 프론트 빌드를 묶어 `mvn test`는 영향 없음 |

### 배포/인프라

- 단일 WAR → 외부 **Tomcat 10.1**(Jakarta EE), `ROOT.war`로 배포(상대경로 API 설계상 필수) — [[01_Projects/08_MINI/01_SchedulerService/02_TechDocs/[기술] Tomcat 단일 WAR 배포 구조\|상세]]
- 프론트는 빌드 시 `target/classes/static`에 번들되어 백엔드와 한 프로세스/한 배포로 서빙(SPA 폴백 라우팅 포함)
- 비밀값은 부트스트랩 단계(`JWT_SIGNING_KEY`/`MASTER_ENCRYPTION_KEY`/`DB_URL` 등) 환경변수 주입, 운영 자격증명은 DB 암호화 저장 — [[01_Projects/08_MINI/01_SchedulerService/02_TechDocs/[기술] 비밀값 2계층 설정 주입 구조\|상세]]

### 아키텍처 요약

- **멀티테넌시**(2026-11-19 §0 재검토로 추가): `company` 1급 엔티티, 업체별 데이터 격리(대상DB/자격증명/스케줄), credential 이름 유일성이 `(company_id, name)` 복합으로 전환
- **실행 패턴**: SP 호출(파라미터화 지원) → 결과행 → `API_CALL`(외부 HTTP, 헤더/바디 템플릿 치환) 또는 `DISPLAY_ONLY`(웹 표시만) → 다중 대상DB 순차 실행(부분실패 허용) — [[01_Projects/08_MINI/01_SchedulerService/02_TechDocs/[기술] 스케줄당 대상DB 다중 선택과 부분실패 처리\|상세]]
- **반복주기**: CronBuilder(구조화 UI) + Quartz CronTrigger — [[01_Projects/08_MINI/01_SchedulerService/02_TechDocs/[기술] 반복주기 구조화 입력(CronBuilder)과 Quartz cron 변환\|상세]]
- **실행이력**: 영속 저장 없음(설계상 "감시 서버"이지 "백업 서버" 아님) — 현재는 인메모리 최신 1건만 캐시, 영구 이력 테이블은 범위 밖(future task)
