# 비밀값 2계층 설정 주입 구조

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | Scheduler-Service 백엔드 |
| **적용 범위** | 보안 · 설정관리 |
| **관련 모듈** | `CredentialCipher`, `target_db_config`, `credential`, `application.yml` |

> 레거시 `Config.java`의 6개 상수(DB 접속정보 3개+FCM 접속정보 3개)를 재컴파일 없이 바꿀 수 있게, "부트스트랩 비밀값=환경변수"/"운영 비밀값=관리자 웹 CRUD+DB 암호화" 2계층으로 분리했다.

## 🎯 배경 및 요구사항

레거시 `Config.java`는 운영/개발 두 세트의 DB·FCM 접속정보를 자바 상수+주석 스왑으로 관리했다 — 환경을 바꾸려면 코드를 고치고 재컴파일해야 했다. 요구사항은 "어떤 업체에 적용해도 재컴파일 없이 동작"하는 것. 멀티테넌시(한 프로세스가 여러 업체를 동시 서빙)까지는 필요 없다고 확인됐다 — "1프로세스=1배포=1업체" 전제를 유지하면서 재배포 유연성만 확보하면 충분했다.

## 🏗 설계 및 구현

### 구조

| 계층 | 값 | 주입 방식 |
|:--|:--|:--|
| 부트스트랩 | 메타DB 접속정보, 암호화 마스터키(`MASTER_ENCRYPTION_KEY`), JWT 서명키 | **환경변수**(재시작 필요하지만 기동 자체에 필요한 최소값이라 허용) |
| 운영 비밀값 | `target_db_config`(대상DB 접속정보), `credential`(다운스트림 API 키 등) — 레거시 `Config.java` 6개 상수에 대응 | **관리자 웹 CRUD + DB 암호화 저장**, 메모리 캐시 후 저장 시 무효화 → **재시작 없이 즉시 반영** |

- **AES-256-GCM 암복호화**(`CredentialCipher`): 매 암호화마다 랜덤 IV를 생성해 `IV+ciphertext`를 base64 한 문자열로 저장. 마스터키가 없거나 base64가 아니거나 32바이트(AES-256)가 아니면 생성자에서 즉시 fail-fast — 운영 비밀값이 평문으로 샐 틈을 기동 단계에서 막는다.
- **도메인 경계에서는 평문**: `TargetDbConfig`/`Credential` 값객체의 필드명을 `password`/`value`(평문)로 두고, Repository 구현체(RowMapper)가 저장 시 암호화·조회 시 복호화를 담당한다 — DB 컬럼명(`encrypted_password`)만 실제로 암호문을 담는다.
- **응답 마스킹**: 관리자 웹 API 응답에서 비밀값은 항상 끝 4자만 노출하고 나머지는 `*`로 마스킹(`Masking.lastFour`).

> [!warning] 짧은 비밀값 마스킹 실패 — 1차 리뷰에서 발견
> `Masking.lastFour`가 길이 4 이하인 값은 `"*".repeat(0)`이 되어 평문 그대로 반환되는 경계버그가 있었다(레거시의 4자리 `FCM_SECURITY_CODE` 같은 실제 사례가 있었음). 길이 4 이하면 전체를 마스킹하도록 수정.

### 주요 로직

```java
// CredentialCipher 생성자 — fail-fast
byte[] key = Base64.getDecoder().decode(masterKeyBase64); // 비-base64면 즉시 예외
if (key.length != 32) throw new IllegalStateException("MASTER_ENCRYPTION_KEY must be 32 bytes");
```

```java
static String lastFour(String value) {
    int visible = Math.min(4, value.length());
    if (visible == value.length()) return "*".repeat(value.length()); // 수정: 짧으면 전체 마스킹
    return "*".repeat(value.length() - visible) + value.substring(value.length() - visible);
}
```

## ✅ 검증

- [x] 저장 시 암호화된 값이 DB에 들어가고 조회 시 평문이 올바르게 복원됨(DB 원본 컬럼을 직접 조회해 평문과 다름을 확인)
- [x] 마스터키 미설정/비-base64/길이오류 3가지 fail-fast 케이스 전부 확인
- [x] 평문이 로그에 출력되지 않음(코드 전체에 해당 값을 로깅하는 경로 없음을 확인)
- [x] 4자리 비밀값(`"4002"`)으로 재현 후 전체 마스킹(`"****"`) 되는 것 확인
