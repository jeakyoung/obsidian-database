# 모노레포 기반 설정

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | Web / Mobile / API 공통 |
| **적용 범위** | 아키텍처 |
| **관련 모듈** | `turbo.json`, `packages/types`, `apps/web/eslint.config.mjs` |

> Turborepo로 세 앱을 하나의 저장소에서 굴리면서, 타입만 공유하고 나머지는 각자 알아서 하도록 최소한으로만 묶어둔 구조

## 🎯 배경 및 요구사항

Web/Mobile/API가 API 응답 형태(`ApiResponse<T>`)를 공유해야 하는데, 세 앱이 완전히 다른 런타임(Next.js / Expo / Spring)이라 코드를 직접 공유할 수는 없다. 그래서 "타입만" 패키지로 뽑고, 빌드/린트/타입체크는 Turborepo 태스크 그래프로 묶는 선에서 정리함.

## 🏗 설계 및 구현

### Turborepo 태스크

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "env": ["API_URL", "NEXT_PUBLIC_API_URL", "NEXT_PUBLIC_APP_URL"],
      "outputs": [".next/**", "!.next/cache/**", "dist/**", "target/*.jar"]
    },
    "dev": { "cache": false, "persistent": true }
  }
}
```

`dependsOn: ["^build"]`는 "내가 빌드되기 전에 내가 의존하는 패키지(`packages/types` 등)부터 먼저 빌드"라는 뜻. `outputs`에 `target/*.jar`까지 들어있는 걸 보면 원래는 `api-spring` 빌드도 turbo 태스크 그래프에 태우려던 흔적인데, 실제 루트 스크립트는 `--filter=!./apps/mobile`만 있고 api-spring 자체는 Maven으로 따로 빌드(Railway Dockerfile에서 직접 `mvn clean package`)한다 — Turborepo는 사실상 Web + 타입 패키지 조합에서만 쓰이는 셈.

### 왜 mobile은 항상 필터링해서 뺐는가

```json
"build": "turbo run build --filter=!./apps/mobile",
"dev": "turbo run dev --filter=!./apps/mobile"
```

Expo/Metro는 자체 번들러 캐시·워치 방식이 turbo의 캐싱 모델과 안 맞고, `npx expo start`는 애초에 "빌드 산출물"이라는 개념이 없는 장기 실행 프로세스다. 그래서 mobile은 turbo 그래프 밖에 두고 `apps/mobile` 안에서 직접 `npm run dev`로 돌리는 쪽으로 정리돼 있음.

### 공유 타입 (`packages/types`)

```
packages/types/
├── api-response.types.ts   # ApiResponse<T> — 모든 API 클라이언트 공통 응답 shape
├── auth.types.ts
├── document.types.ts
├── recommend.types.ts
└── index.ts
```

Web(`@reel-trip/types` import)과 Mobile 둘 다 이 패키지를 그대로 가져다 쓴다. API 서버(Spring)는 별개 언어라 타입을 공유할 방법이 없어서, `ApiResponse<T>`의 필드(`success`/`data`/`message`/`errorCode`/`timestamp`)가 Java `ApiResponse` DTO랑 어긋나지 않게 수동으로 맞춰야 한다 — 이 부분은 자동 검증 수단이 없는 게 현재 구조의 약점.

### ESLint 커스텀 규칙 (Web)

`apps/web/eslint.config.mjs`에 기본 `next/core-web-vitals` 위에 두 가지를 얹었다.

```javascript
// _ 접두사 변수/인자는 "의도적 미사용"으로 간주
"@typescript-eslint/no-unused-vars": [
  "error",
  { argsIgnorePattern: "^_", varsIgnorePattern: "^_", caughtErrorsIgnorePattern: "^_" },
],
// 영상 썸네일 등 동적 외부 URL 이미지가 핵심 기능이라 <img>를 구조적으로 사용.
// next/image는 임의 외부 도메인에 부적합하므로 규칙을 끈다.
"@next/next/no-img-element": "off",
```

두 번째 규칙이 특히 이 서비스 특성 때문에 생긴 것 — URL 파서로 유튜브 쇼츠/인스타 릴스 썸네일을 그때그때 외부 도메인에서 받아오는 게 핵심 기능이라, `next/image`의 도메인 화이트리스트 방식이랑 안 맞아서 아예 껐다.
