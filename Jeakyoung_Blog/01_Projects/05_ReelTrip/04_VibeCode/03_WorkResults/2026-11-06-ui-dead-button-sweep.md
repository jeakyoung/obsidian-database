## 변경 사항 상세

### 묶음 A — 프런트 단독 빠른 승리 (8건)

가장 눈에 잘 띄던 문제들: 헤더/사이드바 검색창 4곳이 전부 `value`/`onChange` 없는 장식용 입력창이었고, "여행 드롭다운"은 거의 모든 대시보드 페이지에 반복 노출되면서도 클릭이 안 됐다. AI 추천 결과의 "추가" 버튼은 로컬 state로 초록색 "담김" 표시만 하고 실제로는 `console.log`만 찍어 사용자가 속을 수 있는 기만적 UI였다. 전부 실제 동작으로 연결했다.

**[2] 여행 드롭다운 작업 중 발견한 설계 이슈**: TASKS.md가 지시한 "전역 store 갱신"이 가리키는 `store/space.ts`는 실제로 모바일 전용 zustand store였고, 웹에는 대응하는 전역 상태가 없었다. 지정된 2개 파일만 고치면 `DashboardLayout`을 공유하는 5개 화면(AI/채팅/멤버/알림/설정)은 전환 UI만 생기고 데이터는 안 바뀌는 반쪽 기능이 되는 문제가 있어, 범위를 확장해 신규 `apps/web/src/lib/space.ts`(localStorage 기반)를 추가하고 5개 화면 모두 전역 선택 상태를 공유하도록 완전히 연동했다.

### 묶음 B — 저장/삭제 연동 + 플랫폼 격차 (3건)

설정 화면의 "여행 스페이스" 탭은 이름/이모지 입력창이 React state조차 없는 uncontrolled input이었고 저장/삭제 버튼 모두 미연동이었다(지난 사이클 로그에 "범위 밖"으로 명시적으로 남겨졌던 항목). 이번에 실제 API 연동 + 삭제 확인 절차(`window.confirm`) + 오너 전용 권한(클라이언트 UI 숨김 + 서버 `checkOwner` 양쪽)까지 완성했다. 모바일 알림 모달은 읽기 전용이었는데, 읽음 처리와 삭제(웹에는 없던 기능)를 추가했다.

### 묶음 C — 채팅 알림 토글 (1건, DB+백엔드+웹+모바일)

알림 설정 화면에 "채팅" 항목 자체가 없어 채팅 알림을 끌 방법이 UI에 없었다. `V10` 마이그레이션으로 컬럼을 추가하고, 기존 member/schedule/place 알림 억제 로직은 한 글자도 건드리지 않은 채 `chat` 분기만 추가했다. 웹/모바일 토글 UI는 지난 사이클에 이미 만들어둔 범용 저장/조회 로직에 항목 하나만 추가하는 것으로 자동 연결됐다.

### 묶음 D — 프로필 사진 업로드 (1건 + 리뷰 후속 1건)

클라우드 스토리지(S3/Cloudinary 등)가 전혀 설정되어 있지 않아, 사용자 승인을 받아 **DB에 base64로 저장**하는 방식으로 구현했다(2MB 용량 제한, 서버/클라이언트 양쪽 검사).

**리뷰에서 발견·수정된 문제:**
- 최초 구현은 `GET /api/user/profile` 응답에 항상 avatar를 포함시켜, 아바타를 전혀 표시하지 않는 `CalendarScreen.tsx`(플랜 표시용으로만 `getProfile()` 호출)까지 매번 최대 ~2.7MB를 받는 성능 문제가 있었다. → `UserProfileResponse`에서 `avatar`를 제거하고, 아바타가 실제로 필요한 화면(프로필/설정)만 쓰는 전용 `GET/PUT /api/user/avatar` 엔드포인트로 분리했다(커밋 `4e83b86`).
- 서버가 base64 디코딩과 용량만 검사하고 실제 이미지 파일인지는 검증하지 않아, 임의의 바이너리를 업로드할 수 있는 데이터 무결성 취약점이 있었다. → JPEG/PNG/WebP 매직 바이트 검증을 추가해 비이미지 데이터는 기존 `INVALID_AVATAR_FORMAT` 에러코드로 거부하도록 수정했다(같은 커밋).

  - "Pro로 업그레이드" 버튼 — 유료 플랜 운영 여부·가격·차등 기능 자체가 미정(상품/결제 정책).
  - "계정 탈퇴" 버튼 — 처리 절차·보관기간 등 법적/개인정보 정책 필요.
  - 장소 상세화면 공개 동의(`onConsent`) — 동의 문구/철회/보관기간 등 법적/약관 정책 필요.
  - `users.role` → 관리자 기능 — 누가 관리자인지, 권한 범위를 정하는 운영 정책 필요.
- **백로그(설계 선택 필요, 이번엔 보류)**: "비슷한 장소" 추천과 documents 자동 적재 파이프라인은 옵션 A(기존 documents 벡터검색 재사용)/옵션 B(places 전용 embedding 컬럼 신설) 중 선택이 필요해 이번 사이클에서는 제외했다.
- 프로필 사진 base64 저장은 트래픽이 커지면 S3 등 외부 스토리지로 마이그레이션할 여지를 남겨둔 임시 방안이다. 현재 JPEG/PNG/WebP만 허용(GIF/BMP/HEIC는 거부).
- 전체 커밋은 로컬에서만 생성되었고, push 여부는 사용자 확인 후 진행한다.

## 특이 사항

- 이번 사이클은 지난 "기능 격차" 사이클에서 백로그로 미뤄둔 항목(G3-2/G2-1/G3-3/E1/E2)을 재검토 리드로 이어받아 시작했다. 리서처가 모바일 TouchableOpacity 54곳을 전수조사해 0건(기존 두 사이클에서 이미 다뤄짐)을 확인하고, 웹에서 신규로 다수(11건)를 찾아낸 것이 이번 사이클의 핵심 발견이었다.
- 작업 중 [2](여행 드롭다운) 항목에서 워커가 지시 범위와 실제 구조(모바일 전용 전역 store) 사이의 불일치를 발견해 범위 확장 여부를 직접 확인받는 과정이 있었다 — 이 판단·승인 경로의 기록이 100% 명확하지는 않았지만, 리뷰어가 최종 구현을 독립적으로 재검증해 원래 의도(크로스 페이지 전환 유지)를 정확히 달성했음을 확인했다.
- 묶음 D(프로필 사진)에서는 "기능이 동작하는가"를 넘어 "모든 호출부에 불필요한 대용량 데이터가 실리지 않는가", "서버가 신뢰 경계로서 입력을 검증하는가"라는 두 가지 비기능 요구사항을 리뷰어가 적극적으로 찾아낸 사례였다 — 앞으로 바이너리/대용량 데이터를 다루는 기능은 이 두 관점(응답 분리, 입력 검증)을 체크리스트에 포함하는 것이 유효해 보인다.
