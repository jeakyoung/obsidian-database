# 발주-입고 강제등록 구분 처리 (WMA202)

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | iPlusERP (`iPlusERP_DONGBANG`) |
| **적용 범위** | 구매관리 - 발주관리 - 발주등록(WMA202) |
| **관련 모듈** | `jvWMA202_01_LIST.java`, `WMA202_VW.js`, `WMA202_CT.js`, `SP_WMA202_01_LIST` |

> 입고등록 화면에서 발주 없이 임의로 등록한 품목이 발주현황 조회에 같이 섞여 나오는 문제를 `DT_ORDER_FLAG` 조회조건으로 구분하는 작업.

## 🎯 배경 및 요구사항

입고등록에는 발주 내용과 상관없이 담당자가 임의로 품목을 추가해서 입고 처리하는 케이스가 있다. 이렇게 강제 등록된 항목이 발주현황(WMA202) 조회에 발주 건과 섞여서 나오면, 실제 발주 건만 보고 싶을 때 방해가 된다. 요구사항은 "입고에서 강제등록된 항목을 발주현황 조회에서 제외할 수 있는 체크박스를 추가"하는 것.

## 🏗 설계 및 구현

### 조회조건 체크박스

`WMA202_VW.js`의 조회조건 영역에 체크박스 하나가 추가되어 있다 (`WMA202_VW.js:132~141`):

```js
{
    xtype: 'checkboxfield',
    itemId: 'cfOrderFlag',
    boxLabel: '입고품목추가제외',
    value: true,
}
```

`WMA202_CT.js`의 조회 함수(`onView`, 889~920행)가 이 체크박스 값을 읽어 `'1'`/`'0'` 문자열로 변환해서 `DT_ORDER_FLAG` 파라미터로 서버에 넘긴다:

```js
var DT_ORDER_FLAG = me.getView().down('#cfOrderFlag').getValue();
if (DT_ORDER_FLAG) {
    DT_ORDER_FLAG = '1';
} else {
    DT_ORDER_FLAG = '0';
}
// ...
store.load({
    params: {
        FROM_DATE, TO_DATE, BASE_NAME, ORDER_NO,
        MATERIAL_NAME, MATERIAL_SPEC,
        DT_ORDER_FLAG,
        OPMAN_CODE: gUserId,
        CUSTOMER_NAME,
    },
});
```

### 서버 - `jvWMA202_01_LIST.java`

`SP_WMA202_01_LIST`를 9개 파라미터로 호출한다(실제 코드 순서 기준):

```java
String sql = "EXEC SP_WMA202_01_LIST"
        + " '" + FROM_DATE + "'"
        + ", '" + TO_DATE + "'"
        + ", '" + MATERIAL_NAME + "'"
        + ", '" + MATERIAL_SPEC + "'"
        + ", '" + ORDER_NO + "'"
        + ", '" + CUSTOMER_NAME + "'"
        + ", '" + OPMAN_CODE + "'"
        + ", '" + BASE_NAME + "'"
        + ", '" + DT_ORDER_FLAG + "'";
```

`DT_ORDER_FLAG`는 마지막 파라미터로 넘어간다. 원본 작업노트에 있던 `PLANT_CODE` 파라미터는 코드에서 주석 처리되어 있어(`jvWMA202_01_LIST.java:48`) 실제로는 서버에 전달되지 않는다.

> [!note] DT_ORDER_FLAG 값의 의미
> 원본 작업노트 기준(SP 내부 로직, DB 재검증 안 됨): 발주에서 저장한 건은 `DT_ORDER_FLAG = 0`, 입고에서 강제(임의)로 등록한 건은 `1`. 체크박스 기본값이 `true`(→ 전송값 `'1'`)인데, 화면 체크박스 라벨이 "입고품목추가제외"인 것을 보면 기본 조회 시 강제등록 건을 제외하는 쪽으로 필터링하려는 의도로 보인다 — 다만 SP 내부에서 `DT_ORDER_FLAG` 파라미터를 어떤 조건식으로 쓰는지는 코드베이스에서 확인 불가(SP 소스가 DB 안에만 존재).

### 화면 그리드에 직접 대응되는 컬럼은 없음

`WMA202_VW.js`의 발주 목록 그리드(`OrderMainList`)에는 `DT_ORDER_FLAG`를 표시하는 컬럼이 없다 — 이 조회조건은 필터링 용도로만 쓰이고 화면에 값 자체를 노출하지는 않는다. 대신 `FAKE_INPUT_FLAG`(가입고여부)라는 별도 hidden 컬럼이 존재하는데(`WMA202_VW.js:341`), 이름은 비슷해 보이지만 `DT_ORDER_FLAG`와 같은 컬럼인지는 코드만으로 확인 불가 — 미확인.

> [!warning] 원본 작업노트의 TMA108 / TMA206 트리거 / SP_WPR313_03_IUD 언급
> 원본 노트에 "TMA108 → 트리거 → TMA206", "SP_WPR313_03_IUD" 같은 메모가 있었지만, 코드베이스 전체를 grep해도 `TMA108`(주석 처리된 무관한 `BIGO_TMA108` 컬럼명 한 건 제외), `TMA206`, `SP_WPR313_03_IUD` 어느 것도 실제로 나오지 않는다. DB 트리거는 애초에 이 코드베이스(SVN)에 소스가 없는 DB 객체라 검증 자체가 불가능하고, 나머지 두 개는 오탈자이거나 다른 화면의 참조일 가능성이 있다 — 미확인으로 남긴다.
