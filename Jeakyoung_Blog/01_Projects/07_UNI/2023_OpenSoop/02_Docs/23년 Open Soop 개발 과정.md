# 23년 Open Soop 개발 과정

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **프로젝트** | 대학프로젝트 |
| **기간** | 2023-03 ~ 2023-09 |
| **역할** | BE 팀원 — 관리자용 게시판 모니터링 API(`admin` 패키지) 담당 |
| **기술 스택** | Java 11, Servlet 3.1, MyBatis 3.5.6, MariaDB |

> `OpenSoopBack` 저장소는 커밋이 `3th_OpenSoopBack` 1개로 뭉쳐 있어 git 로그로는 순서를 못 살린다. 대신 코드 곳곳에 남아있는 작성자·날짜 주석(`2023.05.17 안재경 <생성>` 식)과, 당시 남겨둔 개인 학습 메모를 근거로 "무엇을 왜 이렇게 했는지"를 정리한 문서. [[23년 Open Soop 프로젝트 개요]]가 "지금 상태" 스냅샷이라면 이건 "어쩌다 이렇게 됐는지" 쪽.

## 🎯 목표 및 범위

Servlet/MyBatis 기반 API 서버를 처음 다뤄보면서, BE 팀장 김도원이 짜둔 회원/게시판 구조 위에 관리자용 모니터링 기능을 얹는 게 내 몫이었다. 프레임워크(Spring 등) 없이 순수 Servlet + MyBatis로 짜인 프로젝트라, 구조를 이해하는 과정 자체가 작업의 절반이었다.

## 🏗 진행 내용

### 1. Servlet·MyBatis 기초부터 시작

Spring 없이 `@WebServlet` 애노테이션과 MyBatis `SqlSession`만으로 짜인 구조라, 초반에는 Controller/Biz/DAO 역할 구분, `BufferedReader`로 요청 바디를 직접 읽는 방식, `SqlSessionFactory`를 요청마다 새로 만드는 방식 같은 걸 하나씩 따라가며 익혔다. 자세한 구조는 [\[기술\] Servlet-Process-MyBatis 계층 구조](<../03_TechDocs/[기술] Servlet-Process-MyBatis 계층 구조.md>).

### 2. 게시판 모니터링 API — 기존 목록 쿼리 재사용에서 시작

김도원이 이미 만들어둔 자유/건의/장터/질문 게시판의 일반 목록 조회 쿼리(`select*BubInfo`, 학교코드·페이지네이션 조건 포함)를 관리자용으로 그대로 재사용해서 `FreeAdmin`(자유, 05-15) → `RequestAdmin`/`MarketAdmin`(건의·장터, 05-17) → `AskAdmin`(질문)까지 같은 패턴으로 만들었다. `MarketAdmin`은 05-19에 게시글당 여러 장 등록되는 이미지 목록을 2차원 배열로 조회하는 부분을 추가로 붙였다. 자세한 진행은 [[게시판 모니터링 페이지 구현]].

### 3. 학교코드 필터링 — 시행착오

`FreeAdminSrv`에 `SC_CD_IN`이라는 파라미터를 추가해 프론트에서 학교코드를 입력받아 필터링하려 시도했는데(05-19), 재사용한 매퍼 쿼리는 애초에 `MEMB_SC_CD` 파라미터로 필터링하는 구조여서 이 값은 실제로 쓰이지 않았다. 당시 코드에 "근데 이 방식이 아닌거같다는 생각이 많이듬,," 이라고 남겨둔 주석이 그 시행착오의 흔적이다.

### 4. 뒤늦게 코드를 다시 읽으며 발견한 것들

이번에 문서를 다시 정리하면서 당시 코드를 처음부터 다시 읽어보니, `FreeAdmin`/`RequestAdmin`/`AskAdmin` 세 곳 모두 조회 결과를 `for` 루프로 돌면서 같은 `JSONObject` 필드에 계속 덮어쓰는 구조였다 — 게시글이 여러 건이어도 응답에는 마지막 한 건만 남는다. `MarketAdmin`의 이미지 목록도 조회는 하지만 메인 응답 객체에 붙이는 코드가 없어 실제로는 응답에 포함되지 않는다. 자세한 내용은 [\[기술\] 게시판 모니터링 API 응답 구조와 한계](<../03_TechDocs/[기술] 게시판 모니터링 API 응답 구조와 한계.md>).

## ✅ 결과 및 회고

- **Servlet+MyBatis 구조를 로우레벨부터 익힌 건 남았다.** 프레임워크가 처리해주는 걸 직접 손으로 짜보면서, Controller-Service-DAO 분리가 왜 필요한지를 반대로(분리가 안 된 코드를 짜보고) 체감했다.
- **기존 쿼리 재사용은 속도는 빨랐지만 파라미터 불일치를 남겼다.** 게시판 CRUD용으로 만들어진 `select*BubInfo` 쿼리를 그대로 가져다 쓰면서, 그 쿼리가 원래 요구하던 페이지네이션 파라미터(`REQ_PAGE`/`LIST_UNIT_CNT`)를 관리자 모니터링 쪽에서는 전달하지 않은 채로 남겨뒀다.
- **다건 응답 처리를 검증 없이 넘어갔다.** `for` 루프 안에서 매번 같은 필드를 덮어쓰는 실수는 게시글이 1건뿐인 상황에서는 드러나지 않았을 것 같다 — 여러 건으로 테스트했다면 바로 보였을 문제.
- **테스트 코드가 없다.** `src/test/java`에는 스텁 파일 하나만 남아있고, 실제 서블릿·쿼리 테스트는 수동 호출로만 확인했다.
- **DB 계정이 평문으로 커밋돼 있다.** 학생 프로젝트라 프로필 분리나 `.gitignore` 처리를 하지 않았던 게 그대로 남았다 — 이후 사내 프로젝트([[01_Projects/02_iFrog|I-Frog]] 등)에서는 `appsettings.json`을 아예 gitignore 처리하는 방식으로 이 문제를 피하고 있다.
