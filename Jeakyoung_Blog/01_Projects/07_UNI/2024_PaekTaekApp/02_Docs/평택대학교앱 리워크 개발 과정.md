# 평택대학교앱 리워크 개발 과정

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **프로젝트** | 대학프로젝트 |
| **기간** | 2024-03 ~ 2024-12 (중단) |
| **역할** | BE 팀장 · PL — API 서버(`4th_GraduationBack`) 전담 |
| **기술 스택** | Spring Boot 3(Java 17), Spring Data JPA, MariaDB |

> `4th_GraduationBack` 저장소는 커밋이 `4th_Graduation_backend` 1개로 뭉쳐 있어 git 로그로는 순서를 못 살린다. 대신 실제 코드 구조와, 당시 남겨둔 개인 메모(Notion)를 근거로 "무엇이 왜 이렇게 됐는지"를 정리한 문서. [[평택대학교앱 리워크 프로젝트 개요]]가 "지금 상태" 스냅샷이라면 이건 "어쩌다 이렇게 됐는지" 쪽.

## 🎯 목표 및 범위

BE 팀장으로서 API 서버(회원가입, 로그인, 게시판 4종, 이메일 인증, 이미지 업로드)를 처음부터 설계하고 구현하는 게 목표였다. 팀 프로젝트라 코드 스타일이 완전히 통일되진 않았고, 기능 우선으로 진행하다 보니 뒤에 남은 흔적들이 있다 — 그 판단 과정과 흔적을 기록해둔다.

## 🏗 진행 내용

### 1. 회원가입 로직 — 한 번에 처리 → 단계별 분리

처음엔 회원가입을 한 번의 요청으로 처리하려 했으나, ID/학번/이메일 중복 확인을 마지막에 한꺼번에 처리하면 사용자가 뒷단에서야 중복 에러를 보고 처음부터 다시 입력해야 하는 문제가 있었다. 그래서 `RegiController`를 `/PTU/Register/ID`, `/StdNum`, `/Mail`, `/basic-info-save`, `/StdInfo` 5개 엔드포인트로 쪼개고, 서비스도 `IdRegiService`/`StdRegiService`/`MailRegiService`/`RegiService`로 단계별로 분리했다. 이후 `basic-info-save` 단계에서 학과명→학과코드 변환과 SALT 발급까지 붙으면서 지금 구조로 자리잡았다. 자세한 진행 경위는 [[회원가입 절차 다단계 분리 및 SALT 발급 구조 도입]].

### 2. 게시판 4종 — 복붙 기반 확장

공지사항(`NoticeModel`/`ListController`)을 먼저 만들고, 학사안내(`Bachelor`)·입학안내(`Entrance`)·장학안내(`ScholarCheck`)를 같은 패턴으로 복사해서 만들었다. 컨트롤러·서비스·DAO 구조가 네 게시판 전부 거의 동일한 코드로 반복되고, 이미지 첨부(Base64 → `.webp` 저장)도 공지사항에서 먼저 붙인 뒤 나머지 세 게시판에 그대로 이식했다. 자세한 내용은 [[게시판 이미지 첨부 Base64→WebP 저장 구조 구현]], 패턴 자체의 구조는 [\[기술\] 게시판 4종 CRUD 패턴과 예외·CORS 처리](<../03_TechDocs/[기술] 게시판 4종 CRUD 패턴과 예외·CORS 처리.md>).

이 복붙 확장 과정에서 다섯 번째 게시판(`Schorolship`, 장학금 안내)이 끼어들었는데, 엔티티의 `@Table` 값을 `NoticeModel`에서 그대로 복사해오고 테이블명만 못 고친 채 남아 `notice_List`(= `notice_list`, MariaDB 테이블명 대소문자 무시)를 그대로 참조하고 있다 — `ScholarCheck`(정상 동작하는 장학안내)와 별개로 존재하는, 미완성 상태로 남은 두 번째 장학 관련 게시판이다.

### 3. SALT 기반 로그인 — 클라이언트 해싱 + 서버 단순 비교

로그인은 애초부터 세션/토큰 없이 `MEMB_ID`+`PASS`를 그대로 비교하는 구조였다. 여기에 최소한의 안전장치로, 회원가입 시 서버가 16바이트 SALT를 발급해 저장하고(`RegiService.basicRegiUserData`), 프론트(React Native, `crypto-js`)가 로그인 직전 `/getSalt`로 그 SALT를 받아와 비밀번호를 해싱한 뒤 전송하도록 붙였다. 다만 `LoginService`는 받은 값을 저장된 값과 `equals()`로 비교만 할 뿐이라, 네트워크상으로는 평문 비밀번호가 안 돌아다닌다는 정도의 방어이지 저장된 해시 자체가 탈취되면 그대로 재사용(replay) 가능한 구조다. 자세한 내용은 [\[기술\] SALT 기반 로그인 인증 흐름](<../03_TechDocs/[기술] SALT 기반 로그인 인증 흐름.md>).

### 4. 이메일 인증 — Gmail SMTP + 인메모리 타이머 만료

회원가입 중 학교 이메일 인증을 위해 `EmailAuthService`에서 6자리 코드를 생성해 Gmail SMTP로 발송하고, `java.util.Timer`로 3분 뒤 DB의 인증 코드 필드를 지우는 방식으로 만료를 구현했다. 서버가 재시작되면 이미 예약된 Timer가 다 날아가기 때문에, 재시작 시점과 맞물리면 코드가 만료 시간이 지나도 DB에 남아있을 수 있다는 걸 나중에 인지했다 — 자세한 내용은 [[이메일 인증 코드 발송·검증 기능 구현]].

### 5. 그 밖의 실무 이슈

- DB FK 제약조건(RESTRICT/CASCADE/SET NULL)을 처음 설정할 때 개념이 헷갈려서 정리해둔 기록이 있다 → [[DB Foreign Key 제약조건(RESTRICT·CASCADE·SET NULL) 정리]]
- Eclipse에서 GitHub로 커밋할 때 `non-fast-forward` 에러를 겪고 fetch 경로를 재설정해서 해결한 기록 → [[Eclipse-GitHub non-fast-forward 병합 오류 해결]]

## ✅ 결과 및 회고

- **회원가입을 단계별로 쪼갠 판단은 맞았다.** 한 번에 처리했다면 마지막에서야 중복 에러를 보여주는 UX가 됐을 텐데, 단계별 중복확인으로 사용자가 입력 도중 바로 피드백을 받게 했다.
- **복붙 기반 확장은 속도는 빨랐지만 흔적이 남았다.** 공지사항 코드를 계속 복사해서 학사/입학/장학/장학금(Schorolship) 게시판을 만들다 보니, 마지막 게시판에서 `@Table` 이름을 못 고친 채 남는 실수가 생겼다 — 테스트/리뷰 없이 "복사 → 이름만 바꾸기"로 확장한 대가.
- **SALT를 붙인 건 배운 게 있었지만 절반짜리 개선이었다.** 평문 전송은 막았지만, 서버가 저장된 해시를 그대로 비교하는 구조라 세션 토큰/nonce 없이는 진짜 replay 방어는 안 된다는 걸 나중에야 알게 됐다.
- **테스트 코드가 없다.** `LeeApplicationTests`가 스프링부트 기본 생성 스텁 그대로 남아있고, 실제 서비스/컨트롤러 테스트는 하나도 없다 — 기능 붙이는 속도를 우선했기 때문.
- **`application.properties`에 DB 계정·SMTP 앱 비밀번호가 평문으로 커밋돼 있다.** 학생 프로젝트라 프로필 분리(`application-{profile}.properties`)나 `.gitignore` 처리를 안 했던 게 그대로 남았다 — 이후 사내 프로젝트([[01_Projects/02_iFrog|I-Frog]] 등)에서는 `appsettings.json`을 아예 gitignore 처리하는 방식으로 이 문제를 피하고 있다.
- **프로젝트 자체는 외부 요인(샘플 DB 유출)으로 중단됐다.** 기능적으로는 게시판·회원가입·이메일 인증까지 붙은 상태였고, 스토어 정식 출시까지는 못 갔다.
