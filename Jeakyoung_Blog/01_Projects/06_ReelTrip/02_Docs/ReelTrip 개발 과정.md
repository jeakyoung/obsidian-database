# ReelTrip 개발 과정

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **프로젝트** | ReelTrip |
| **기간** | 2026-02 ~ 진행중 |
| **역할** | 풀스택 (Web / Mobile / API 전체) |
| **기술 스택** | Next.js, React Native(Expo), Spring Boot, PostgreSQL |

> git 로그(242 커밋)를 처음부터 다시 훑어보고 실제로 어떤 순서로, 왜 그렇게 바뀌어왔는지 정리한 문서. [[ReelTrip 프로젝트 개요]]가 "지금 상태" 스냅샷이라면 이건 "어쩌다 지금 상태가 됐는지" 쪽.

## 🎯 목표 및 범위

혼자(+합류한 팀원들) 힘으로 Web/Mobile/API 세 개를 다 굴리면서 서비스 하나를 완성까지 가져가는 게 목표였다. 처음부터 지금 구조로 시작한 게 아니라 중간에 백엔드 프레임워크도, DB도 갈아엎었던 이력이 있어서 그 판단 과정을 남겨둔다.

## 🏗 진행 내용

### 1. 초기 세팅 — NestJS 기반 (2026-02 ~ 04)

첫 커밋은 2026-02-25. 백엔드 기반설정 → 인증 → 벡터 검색용 DTO(`CreateDocumentRequest`, `SearchDocumentRequest` 등)까지 붙이면서 시작했다. 이 시점엔 Next.js 쪽에 API 서버 역할까지 같이 태우려던 흔적(`Fix Ahn / BE 리펙토링 Next.js`)이 있는데, 곧바로 Vercel 배포 이슈로 발목을 잡혔다.

### 2. Vercel/CORS 삽질 구간 (2026-04-30 ~ 05-08)

하루 동안 `Vercel Error HotFix#1`부터 `#10`까지 찍은 기록이 남아있다. Next.js 서버리스 함수 위에서 백엔드를 같이 돌리려다 CORS·API 라우팅이 계속 깨졌고, 결국 `Fix Ahn / FE, BE 역활 분리` → `API, Was서버 역활 분리`로 프론트와 백엔드를 완전히 분리하는 쪽으로 정리했다. 이후로도 5월 8일 하루에만 CORS/스칼라(API 문서) 설정을 열 번 가까이 고친 기록이 있는데, 이건 배포 환경(로컬 ↔ 배포 서버)마다 허용 오리진이 달라서 생긴 문제였다.

> 여기서 배운 것: 프론트/백엔드를 같은 서버리스 런타임에 억지로 태우는 것보다, 처음부터 물리적으로 분리하고 CORS를 한 번에 제대로 설계하는 게 낫다. 지금 Web이 쓰는 rewrites 프록시 구조([[개발 환경 구성 및 협업 가이드]] 참고)도 결국 "브라우저가 백엔드를 직접 모르게 하자"는 이 시기 교훈의 연장선.

### 3. NestJS → Spring Boot 마이그레이션 (2026-05-20 ~ 21)

`Refactor Ahn / Nest.js -> Spring-Boot 마이그레이션 #1` ~ `#11`. 이틀에 걸쳐 백엔드 프레임워크 자체를 갈아엎었다. NestJS 쪽 인증/벡터 검색 로직을 Spring Boot + MyBatis 조합으로 다시 짠 구간. 마이그레이션 직후 바로 `Feat Ahn / Application 개발 환경 세팅`, `FE Web Page #1`, `BE Web Page #1`로 이어지는 걸 보면, 프레임워크를 바꾼 다음에야 실제 화면 기능 붙이기가 본격적으로 시작된 셈이다.

### 4. 통합 개발 & 모바일 상태관리 정착 (2026-05-28 ~ 06-02)

`Feat Ahn / 통합 개발 app, web, BE` 커밋들로 세 앱을 같이 굴리기 시작했고, `버전 충돌 해결, App 가배포 완료`를 거쳐 `mobile 전역 상태·서버 캐싱 도입 및 feature 구조 완성`으로 이어진다. 이 시점에 Mobile이 지금의 `features/` 단위 구조 + Zustand(클라이언트 상태) + TanStack Query(서버 상태) 조합으로 자리를 잡았다 — 자세한 내용은 [[Mobile 전역 상태·서버 캐싱 도입]].

같은 날 `Apify Test`, `Gemini API Test`가 연달아 찍혀있는데, URL 파서(유튜브 쇼츠/인스타 릴스 크롤링)를 Apify로, 크롤링한 콘텐츠에서 여행 정보 추출을 Gemini로 붙이는 실험이 이 무렵 진행됐다. 원래 이 자리는 Claude(Anthropic)로 설계했던 흔적이 `AiService` 인터페이스 주석과 `ErrorCode.ANTHROPIC_API_KEY_MISSING`에 남아있는데, 실제로는 Gemini로 스왑됐다 — 이름만 안 바뀐 상태로 지금까지 남아있음 ([\[기술\] 모노레포 기반 설정](<../03_TechDocs/[기술] 모노레포 기반 설정.md>) 참고).

### 5. 리프레시 토큰 도입 (2026-06-04)

커밋 메시지는 `Fix Ahn / DB 이관 Neon -> Supabase`인데, 실제로 diff를 열어보면 내용 대부분이 리프레시 토큰(DB 저장 + rotation) 도입이다 — 커밋 메시지가 실제 변경 내용과 안 맞는 케이스. 액세스 토큰 수명을 24시간 → 30분으로 줄이고, 대신 DB에 저장한 리프레시 토큰(30일)으로 재발급받는 구조로 바꿨다. 자세한 구현은 [\[기술\] 리프레시 토큰 회전 구조](<../03_TechDocs/[기술] 리프레시 토큰 회전 구조.md>).

이후 문서·주석 곳곳에 `Neon`이 남아있는 진짜 이유는 이 커밋이 아니라 별도 DB 호스팅 이관 작업 — 코드/설정값은 Supabase로 바뀌었는데 커넥션 풀 튜닝 관련 주석(HikariCP `max-lifetime` 설정 등)에 Neon 타임아웃 기준 값이 그대로 남아있어서 아직 완전히 정리되진 않은 상태다.

### 6. 안정화 & 코드 정리 (2026-06-15 ~ 06-17)

EAS 빌드 스테이지 분리, UX 리팩토링/AI 파서 연동에 이어 `feat: ESLint 도입, 중복코드 통합 및 죽은 라우트 정리, 로그인 화면 재구현`(06-17)으로 한 차례 정리 구간을 거쳤다. Web의 `next/img` 관련 커스텀 ESLint 규칙도 이 시점 전후로 자리잡음. 자세한 내용은 [[ESLint 도입 및 로그인 화면 재구현]].

### 7. 더미데이터 → 실 DB 전환 (2026-07-22 ~ 진행중)

`일부 더미데이터 실DB화 작업`(07-22) → `필요하지 않은 컴포넌트 제거, 실 데이터 연동`(09-02, 09-17)으로 이어지는 최근 흐름. Dashboard의 BookingStatus 하드코딩 섹션은 제거하고 실 API 집계로 바꿨고, AiScreen의 AI 추천 섹션(`DUMMY_AI_RECS`)만 아직 추천 API가 없어서 더미로 남아있다.

## ✅ 결과 및 회고

- **프레임워크를 중간에 바꾼 건 손해가 아니었다.** NestJS→Spring Boot 마이그레이션은 "일단 붙여보고 안 맞으면 갈아탄다"는 식으로 판단했고, 실제로 마이그레이션 이후 개발 속도가 붙었다. DB 호스팅(Neon→Supabase)도 비슷한 시기에 갈아탔는데, 정작 그 이름이 붙은 커밋의 실제 내용은 리프레시 토큰 도입이었다 — 커밋 메시지랑 실제 변경 내용이 따로 노는 사례.
- **CORS/배포 이슈는 초반에 시간을 제일 많이 먹은 부분.** 프론트/백엔드 런타임을 처음부터 분리했으면 5월 초의 반복적인 핫픽스 사이클은 줄었을 것.
- **이름이 안 바뀐 채 남은 흔적들**(Neon 주석, Claude→Gemini 스왑, README의 Java 21+/ANTHROPIC_API_KEY 등 stale 기록)이 여러 군데 있다 — 기능 구현 우선으로 진행하다 보니 리네이밍/문서 동기화가 항상 뒤로 밀렸다는 방증. 옵시디언 문서화 작업([[ReelTrip 프로젝트 개요]])을 계기로 하나씩 걷어내는 중.
- **테스트 코드가 아직 없다.** `Dockerfile`도 `-DskipTests`로 빌드한다 — 기능 붙이는 속도를 우선했기 때문인데, 다음 단계에서 최소한 서비스 레이어 단위 테스트부터 넣을 필요가 있음.
