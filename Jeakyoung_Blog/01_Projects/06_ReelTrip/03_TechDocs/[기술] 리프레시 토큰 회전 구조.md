# 리프레시 토큰 회전 구조

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | API (Spring) |
| **적용 범위** | 인증 |
| **관련 모듈** | `AuthServiceImpl`, `RefreshTokenMapper`, `V6__add_refresh_tokens.sql` |

> 커밋 메시지는 "DB 이관 Neon -> Supabase"인데 실제 diff는 거의 다 리프레시 토큰 로직이다 — 라벨링이 잘못된 커밋. [[Web API 클라이언트 토큰 재발급 흐름]]의 백엔드 짝

## 🎯 배경 및 요구사항

원래는 로그인하면 JWT 액세스 토큰 하나만 발급하고 끝이었다(`JWT_EXPIRATION` 기본 24시간). 세션을 길게 유지하려면 토큰 수명을 늘려야 하는데, 액세스 토큰 수명을 그냥 늘리면 탈취됐을 때 위험 기간이 길어진다. 그래서 액세스 토큰은 짧게(30분), 대신 DB에 저장하는 리프레시 토큰으로 재발급받는 구조로 바꿨다.

## 🏗 설계 및 구현

### 토큰 수명 변경

```yaml
jwt:
  expires-in: ${JWT_EXPIRATION:1800000}                    # 30분 (기존 24시간)
  refresh-expires-in: ${JWT_REFRESH_EXPIRATION:2592000000} # 30일
```

### 발급 — Rotation 방식

로그인/회원가입 시 `buildAuthResponse()` 하나로 액세스+리프레시 토큰을 같이 만든다. 리프레시 토큰은 JWT가 아니라 그냥 `UUID` 문자열 — DB에 저장해두고 조회하는 방식이라 굳이 서명된 토큰일 필요가 없다.

```java
private AuthResponse buildAuthResponse(User user) {
    String accessToken  = jwtUtil.generateToken(user.getUsername(), user.getRole());
    String refreshToken = UUID.randomUUID().toString().replace("-", "");

    // 기존 refresh token 삭제 후 새로 발급 (rotation)
    refreshTokenMapper.deleteByUserId(user.getId());
    refreshTokenMapper.insert(RefreshToken.builder()
            .userId(user.getId())
            .token(refreshToken)
            .expiresAt(LocalDateTime.now().plusSeconds(refreshExpiresInMs / 1000))
            .build());
    ...
}
```

"Rotation"은 로그인/재발급 때마다 그 유저의 기존 리프레시 토큰을 지우고 새로 하나만 발급하는 방식을 말한다 — 유저당 유효한 리프레시 토큰이 항상 1개뿐이라, 옛날 토큰이 유출돼도 다음 로그인/재발급 시점에 자동으로 무효화된다.

### 재발급 / 로그아웃

```java
@Override
public AuthResponse refresh(String refreshToken) {
    RefreshToken rt = refreshTokenMapper.findByToken(refreshToken)
            .orElseThrow(() -> new AppException(ErrorCode.REFRESH_TOKEN_NOT_FOUND));

    if (rt.getExpiresAt().isBefore(LocalDateTime.now())) {
        refreshTokenMapper.deleteByToken(refreshToken);
        throw new AppException(ErrorCode.REFRESH_TOKEN_EXPIRED);
    }

    User user = userMapper.findById(rt.getUserId())
            .orElseThrow(() -> new AppException(ErrorCode.USER_NOT_FOUND));

    return buildAuthResponse(user);  // 여기서도 다시 rotation
}

@Override
public void logout(String refreshToken) {
    refreshTokenMapper.deleteByToken(refreshToken);
}
```

재발급할 때도 새 리프레시 토큰을 다시 발급(rotation)하기 때문에, 클라이언트는 `/api/auth/refresh` 응답을 받을 때마다 저장해둔 refresh token을 매번 새 값으로 갱신해야 한다 — 프론트(`api-client.ts`)에서 `auto_login`이 켜진 경우에만 새 refresh token으로 교체 저장하는 이유가 이 rotation 구조 때문.

### DB 스키마

```sql
-- V6__add_refresh_tokens.sql
CREATE TABLE refresh_tokens (
    id         BIGSERIAL PRIMARY KEY,
    user_id    BIGINT NOT NULL REFERENCES users(id),
    token      VARCHAR(255) NOT NULL,
    expires_at TIMESTAMP NOT NULL
);
```

유저당 토큰 1개 정책이라 `user_id`에 유니크 제약을 걸 법도 한데, 실제로는 애플리케이션 레벨에서 `deleteByUserId` 먼저 호출하는 방식으로 처리하고 DB 제약은 안 걸었다 — 그래서 동시에 두 요청이 겹치면 이론상 레이스 컨디션 여지가 있음 (트래픽이 적어서 아직 문제된 적은 없음).
