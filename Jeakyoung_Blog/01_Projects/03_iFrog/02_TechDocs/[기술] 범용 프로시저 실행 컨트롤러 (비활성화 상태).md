# [기술] 범용 프로시저 실행 컨트롤러 (비활성화 상태)

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | `Controllers/Database/{SQLServer,PostgreSQL,Oracle}/*QueryController.cs` |
| **적용 범위** | DB 원시 쿼리/프로시저 실행 |
| **관련 모듈** | `DbProcedureRequest`, `SQLServerHelper` 등 |

> 세 컨트롤러 모두 파일 전체가 주석처리돼있음. 지금은 각 도메인 서비스(`ApprovalService`, `WorkStatusService` 등)가 직접 `SQLServerHelper`/`PostgreSQLHelper`를 호출하는 구조로 대체되어 있고, 이 컨트롤러들을 거치는 경로는 없음.

## 🎯 배경 및 요구사항

`CallProcedure` 엔드포인트 하나로 클라이언트가 **프로시저명 + 파라미터를 요청 바디에 실어 보내면 그대로 실행**해주는 범용 구조였음 (SQLServer/PostgreSQL/Oracle 3종 동일 패턴). `SP_WEB_LOGIN`처럼 로그인 프로시저까지 이 경로로 예시가 남아있음.

## 🏗 설계 및 구현

```
List<DbProcedureRequest> (procedureName, isChangeProcedure, parameters)
  → new {SQLServer|PostgreSQL|Oracle}Helper(connectionString, logger)
  → helper.CallProcedureAsync(dbProcs)
  → JsonHelper.ConvertDbResultToJsonObject(result)
```

`SQLServerQueryController`/`PostgreSQLController`는 엔드포인트마다 `[Authorize]`가 붙어있는데 `OracleQueryController`엔 하나도 없음 — 다만 셋 다 지금은 비활성화라 실제 인가 여부는 의미 없음.

> [!warning] 프로시저명을 그대로 받아 실행하는 구조의 위험
> 클라이언트가 임의의 프로시저명을 지정해서 호출할 수 있는 구조라, 활성화 상태였다면 인가되지 않은 프로시저 호출(권한 상승, 데이터 유출)에 취약할 수 있음. 지금 도메인별 서비스가 프로시저명을 코드에 고정해서 호출하는 방식으로 바뀐 것과 대비됨 — 비활성화된 이유가 실제로 이거였는지는 확인 필요.
