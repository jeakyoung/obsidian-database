# [기술] 보안코드 기반 멀티테넌시 커넥션 구조

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | `Context/TickerContext`, `Services/EnvService/*` |
| **적용 범위** | 전체 API (미들웨어 단) |
| **관련 모듈** | `TickerMiddleware`, `SecurityCodeMapper`, `TickerContext`, `IEnvService` |

> 배포본 하나로 여러 회사(DBG/SYN/ATC)·여러 환경(Dev/Stg/Prd)을 동시에 서비스해야 해서, 요청 헤더값 하나로 커넥션을 갈아끼우는 구조를 만듦.

## 🎯 배경 및 요구사항

- 원래는 업체마다 서비스 코드를 커스터마이징해서 그 업체 서버에 따로 캐스팅하는 방식이었음 — 이걸 단일 백엔드로 통합하는 게 [[I-Frog 서버 통합]] 작업의 목표였고, 이 문서는 그 중 커넥션 분리 부분
- ATC/동방/송연 DB를 하나로 통합하면서, 회사마다 커넥션 문자열이 다 다름
- 배포는 하나인데 요청마다 어느 회사·어느 환경(Dev/Stg/Prd) DB에 붙을지가 달라야 함
- 처음엔 `9f7f3e9`처럼 ATC 커넥션을 임시로 하드코딩해서 붙여보다가, 이 방식으로는 회사가 늘어날 때마다 배포를 새로 해야 해서 헤더 기반으로 바꾸기로 함

## 🏗 설계 및 구현

### 흐름

```
SECURITY_CODE 헤더 (4자리+)
  └ 앞 2자리 → SecurityCodeMapper.GetTicker → "10"=DBG "20"=SYN "40"=ATC
  └ 뒤 2자리 → SecurityCodeMapper.GetEnv    → "00"=Dev "02"=Prd
        ↓
TickerMiddleware.InvokeAsync
        ↓
TickerContext.Initialize(ticker) / EnvInitialize(env)   ← 요청당 1회, scoped
        ↓
IEnvService.GetConnectionString() 등
```

> [!warning] appsettings.json이 아니라 Postgres 설정 테이블에서 읽어온다
> 처음엔 `ConnSettings:{Ticker}:MsSql{Env}Connection` 식으로 appsettings.json 키를 조합해서 읽는 구조로 짐작했는데, 실제 `EnvService.cs`를 보면 다르다.
>
> - MSSQL 연결 문자열, FTP URL, 이미지 URL, 사원카드 URL은 전부 **Postgres의 `public.tgi000_01_list` 프로시저**로 조회해서 앱 기동 후 최초 1회 `static Dictionary<Ticker, Dictionary<Env, Dictionary<ConfigKey, Value>>>` (`_holder`)에 캐싱해두고 그 이후로는 메모리에서만 읽는다 (`EnvService.Load()`, 이중 체크 락).
> - appsettings.json에서 직접 읽는 건 **Postgres 커넥션 문자열 하나**(`ConnectionStrings:Postgre{Env}Connection`)뿐이다 — 이걸로 tgi000_01_list를 조회해서 나머지 전부를 채워넣는 구조.
> - appsettings.json에 남아있는 `ConnSettings`/`MsSqlDevConnection` 같은 키들은 지금 코드 어디서도 참조하지 않는다 (주석처리된 레거시 `Database/*QueryController`에서만 남아있음) — 죽은 설정값일 가능성이 높다.
> - `_holder`는 `static` + `_isLoaded` 플래그로 앱 프로세스당 딱 한 번만 로드된다. **운영 중에 `tgi000_01_list` 데이터를 바꿔도 앱을 재시작하기 전까진 반영 안 됨.**
> - `tgi000_01_list` 프로시저 자체의 로직(어떤 조건으로 값을 내려주는지 등)은 DB 저장 프로시저 안에 있어서 이 저장소 코드만으로는 안 보인다.

### 왜 굳이 "한 번만 초기화" 인가

`TickerContext.Initialize`/`EnvInitialize`는 이미 세팅된 상태에서 다시 부르면 `InvalidOperationException`을 던진다. 요청 스코프 안에서 미들웨어가 한 번만 값을 정하고, 그 뒤로는 아무도 값을 바꿀 수 없게 만들어서 — 컨트롤러/서비스 어디선가 실수로 다른 티커를 넣어버리는 사고를 막으려는 목적.

### 단점 / 주의할 점

- `IEnvService`/DB 관련 코드는 미들웨어 파이프라인을 거치지 않은 곳(예: 백그라운드 잡, 유닛 테스트)에서 쓰면 `InvalidOperationException`이 남 → SECURITY_CODE 헤더 없이는 절대 동작 안 함
- 앱이 살아있는 동안 설정을 한 번만 로드하는 static 캐시라서, 새 회사(Ticker)를 추가했을 때 배포 없이 DB 테이블만 채워 넣으면 되긴 하는데, 앱 재시작 없이는 반영이 안 되는 점은 여전히 주의 대상

> [!note] 한때는 환경별로 클래스가 나뉘어 있었음
> `a7122a1`/`9fee22e` 시점 커밋을 보면 `DevEnvService`/`StgEnvService`/`PrdEnvService`로 환경별 구현체가 따로 있었는데, 지금(HEAD) `Services/EnvService/` 폴더엔 `EnvService.cs` 하나로 합쳐져 있고 나머지 세 파일은 존재하지 않는다. 언제/어느 커밋에서 합쳐졌는지는 별도 확인 필요.
