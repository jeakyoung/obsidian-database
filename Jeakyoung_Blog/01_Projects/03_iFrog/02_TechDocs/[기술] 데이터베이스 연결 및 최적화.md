# I-Frog 데이터베이스 연결 및 최적화 가이드

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | I-Frog 백엔드 (`F1Soft.Starmap.Service`) |
| **적용 범위** | 데이터베이스 |
| **관련 모듈** | `Helper/{SQLServerHelper,PostgreSQLHelper,OracleHelper}.cs`, `Services/EnvService/*`, `Context/TickerContext` |

> 이전 버전 문서가 `Common/Database/*`, `InputListService`, `SP_APP_INPUT_LIST` 같은 걸 언급했는데, 이 저장소엔 없는 경로/서비스임. 실제 코드(`Helper/` 폴더, Groupware 서비스들) 기준으로 다시 씀.
>
> ⚠️ 아래 내용은 전부 **C# 서비스 코드 쪽에서 보이는 것까지만** 적은 것이다. 실제 조회/집계/최적화 로직 대부분은 MSSQL 저장 프로시저(SP) 안에 있는데, 이 저장소엔 SP 소스가 없어서 프로시저 내부 로직은 확인할 방법이 없다. "최적화"라는 제목과 달리 지금은 C# 쪽 커넥션/트랜잭션 처리 방식 정리에 가깝다.

## 🎯 배경 및 요구사항

하나의 서비스가 여러 회사(Ticker) × 여러 환경(Dev/Stg/Prd)의 DB를 함께 바라본다. 연결 문자열은 코드에 고정할 수 없고 요청마다 결정된다.

## 🏗 설계 및 구현

### DB 접근 계층

`IDatabaseHelper` 구현이 셋 있고 모양이 거의 같다 (`CallProcedureAsync`/`ExecuteSqlCommandAsync`).

| 구현 | 드라이버 | 비고 |
|:--|:--|:--|
| `SQLServerHelper` | `Microsoft.Data.SqlClient` | 그룹웨어/ERP 주력, 대부분의 도메인 서비스가 사용 |
| `PostgreSQLHelper` | `Npgsql` | 통합서버 + `EnvService`의 설정 테이블(`tgi000_01_list`) 조회용 |
| `OracleHelper` | `Oracle.ManagedDataAccess.Core` | 헬퍼는 있지만 `Database/Oracle/OracleQueryController`는 현재 비활성화 상태([[[기술] 범용 프로시저 실행 컨트롤러 (비활성화 상태)]]) |

호출 형태는 서비스마다 동일하다 (예: `WorkStatusService.GetWorkProgress`).

```csharp
public class SomeService
{
    private readonly string _connectionString;

    public SomeService(IEnvService envService, ILogger<SomeService> logger)
    {
        // 연결 문자열은 반드시 IEnvService로 받는다. IConfiguration에서 직접 읽으면 멀티테넌트가 깨진다.
        _connectionString = envService.GetConnectionString();
    }

    public async Task<object> DoSomethingAsync(SomeRequest request)
    {
        using var helper = new SQLServerHelper(_connectionString, _logger);

        var dbRequest = new DbProcedureRequest
        {
            ProcedureName = "SP_XXX_01_LIST",
            Division = "xxx",
            Parameters = new Dictionary<string, object> { { "PARAM", request.Value! } }
        };

        var result = await helper.CallProcedureAsync(new List<DbProcedureRequest> { dbRequest });

        if (!result.Result)
            throw new Exception(result.ErrorMessage ?? "실패");

        // result.ResultList[0].DataTable 에서 필요한 컬럼만 뽑아 반환
    }
}
```

### 커넥션 수명

- 헬퍼는 생성자에서 `Open()`하고 `IDisposable`로 닫는다. 항상 `using var`로 받는다.
- 커넥션 풀은 ADO.NET 기본 풀을 그대로 쓴다. 별도 풀 라이브러리는 없다.
- 헬퍼 인스턴스를 필드로 들고 재사용하지 않는다 — 호출 단위로 새로 만든다.

### 트랜잭션과 오류 처리

`CallProcedureAsync`는 이렇게 동작한다 (`SQLServerHelper` 기준):

1. `BeginTransaction()`으로 시작
2. 요청 목록을 순서대로 실행 — 파라미터는 문자열이면 실제 길이만큼 `VARCHAR` 크기를 잡아서 추가
3. `DbException`이 나면 롤백하고 예외를 던지지 않는다. 대신 `DbResult.ErrorMessage`에 담아 돌려준다
4. 오류가 없으면 커밋

> [!warning] 반환값을 반드시 확인할 것
> DB 오류는 예외로 올라오지 않는다. `result.Result`를 확인하지 않고 `result.ResultList![0].DataTable!`로 바로 들어가면 엉뚱한 지점에서 `NullReferenceException`이 난다.

### 설정 테이블 로딩 (EnvService 관점)

`EnvService`는 앱 프로세스당 딱 한 번, Postgres `tgi000_01_list`를 호출해서 Ticker/Env/설정키별 값을 `static Dictionary`에 캐싱한다. 자세한 내용은 [[[기술] 보안코드 기반 멀티테넌시 커넥션 구조]] 참고 — DB 커넥션 자체를 "최적화"한 지점이라기보단, 설정 조회를 캐싱해서 매 요청 DB 왕복을 없앤 지점이라고 보는 게 맞다.

## ✅ 검증

- [ ] SP 이름을 일부러 틀리게 해서 `Result=false`와 `ErrorMessage`가 채워지는지
- [ ] 변경 프로시저 실행 중 오류 시 앞 단계가 롤백되는지
- [ ] `tgi000_01_list` 캐시 미스 시(`GetConfigValue`에서 `allowEmpty=false`) 어떤 예외 메시지가 나가는지
