# I-Frog 데이터베이스 연결 및 최적화 가이드

## 📋 개요

| 항목         | 내용                                                            |
| :--------- | :------------------------------------------------------------ |
| **대상 시스템** | I-Frog 모바일 백엔드 (`F1Soft.Starmap.Service`)                     |
| **적용 범위**  | 데이터베이스                                                        |
| **관련 모듈**  | `Common/Database/*`, `Common/Env/*`, `Contexts/TickerContext` |

## 🎯 배경 및 요구사항

하나의 서비스가 **여러 회사(Ticker) × 여러 환경(Dev/Prd)** 의 DB 를 함께 바라본다.
그래서 연결 문자열을 코드나 단일 설정값으로 고정할 수 없고, 요청마다 결정해야 한다.

- 회사·환경별로 배포본을 따로 만들지 않는다.
- 어느 DB 를 쓸지는 **요청 헤더 하나**로 정해진다.
- DB 종류가 섞여 있다 (MSSQL 주력, PostgreSQL, Oracle).

## 🏗 설계 및 구현

### 연결 문자열이 정해지는 경로

```
요청 (SECURITY_CODE 헤더)
  → TickerMiddleware
  → SecurityCodeMapper (Ticker / Env 판정)
  → TickerContext (요청 스코프에 1회 저장)
  → EnvService.GetConnectionString()
  → "ConnSettings:{Ticker}:MsSql{Env}Connection" 설정값
```

`SECURITY_CODE` 는 4자리 이상이며 앞 2자리가 회사, 다음 2자리가 환경이다.

| 위치 | 값 | 의미 |
|:--|:--|:--|
| 0~1 | `10` | DBG |
| 0~1 | `20` | SYN |
| 2~3 | `00` | Dev |
| 2~3 | `02` | Prd |

매핑에 없는 값이면 `UnauthorizedAccessException` 이 나고 미들웨어가 **401** 로 끊는다.
컨트롤러까지 가지 않는다.

### DB 접근 계층

`IDatabaseHelper` 구현이 셋 있고, 모양은 거의 같다.

| 구현 | 드라이버 | 용도 |
|:--|:--|:--|
| `SQLServerHelper` | `Microsoft.Data.SqlClient` | 주력 |
| `PostgreSQLHelper` | `Npgsql` | 통합서버 |
| `OracleHelper` | `Oracle.ManagedDataAccess.Core` | 일부 연동 |

호출 형태는 서비스마다 동일하다.

```csharp
public class InputListService : IInputListService
{
    private readonly string _connectionString;
    private readonly ILogger<InputListService> _logger;

    public InputListService(ILogger<InputListService> logger, IEnvService envService)
    {
        // 연결 문자열은 반드시 IEnvService 로 받는다.
        // IConfiguration 에서 ConnSettings 를 직접 읽으면 멀티테넌트가 깨진다.
        _connectionString = envService.GetConnectionString();
        _logger = logger;
    }

    public async Task<List<Dictionary<string, object?>>> GetInputListAsync(InputNoRequest request)
    {
        using var helper = new SQLServerHelper(_connectionString, _logger);

        var dbRequest = new DbProcedureRequest
        {
            ProcedureName = "SP_APP_INPUT_LIST",
            Parameters = new Dictionary<string, object>
            {
                { "FACTORY_CODE", request.FactoryCode! },
                { "FROM_DATE",    request.FromDate! },
                { "TO_DATE",      request.ToDate! }
            }
        };

        var result = await helper.CallProcedureAsync(new List<DbProcedureRequest> { dbRequest });

        if (!result.Result)
            throw new InvalidOperationException(result.ErrorMessage ?? "SP 실행에 실패했습니다.");

        // ...
    }
}
```

### 커넥션 수명

- 헬퍼는 **생성자에서 `Open()`** 하고 `IDisposable` 로 닫는다. 항상 `using var` 로 받는다.
- 커넥션 풀은 ADO.NET 기본 풀을 그대로 쓴다. 별도 풀 라이브러리를 두지 않는다.
- 헬퍼 인스턴스를 필드로 들고 재사용하지 않는다. **호출 단위로 새로 만든다.**

### 트랜잭션과 오류 처리

`CallProcedureAsync` / `ExecuteSqlCommandAsync` 는 모두 이렇게 동작한다.

1. `BeginTransaction()` 으로 시작
2. 요청 목록을 순서대로 실행
   - `IsChangeProcedure = true` → `ExecuteNonQueryAsync()`, 변경 행 수를 `ReturnValue` 에
   - `false` → `ExecuteReaderAsync()` 로 읽어 `DataTable` 로 변환, 행 수를 `ReturnValue` 에
3. `DbException` 이 나면 **롤백하고 예외를 던지지 않는다.** 대신 `DbResult.ErrorMessage` 에 담아 돌려준다
4. 오류가 없으면 `Commit()`

> [!warning] 반환값을 반드시 확인할 것
> DB 오류는 예외로 올라오지 않는다. `result.Result` 를 확인하지 않고
> `result.ResultList![0].DataTable!` 로 바로 들어가면 엉뚱한 지점에서
> `NullReferenceException` 이 난다. 호출한 쪽에서 `Result` 를 먼저 보고
> `ErrorMessage` 를 예외로 바꿔 던지는 것이 이 코드베이스의 관례다.

컬럼명이 겹치면 `DataTable` 변환 단계에서 `이름_1`, `이름_2` 로 자동 접미사가 붙는다.
SP 에서 같은 컬럼명을 두 번 내보내면 조용히 이름이 바뀌므로 주의한다.

### 여러 서비스를 묶는 쓰기

`InputSaveService` 처럼 DB 저장과 이미지 업로드를 함께 처리할 때는
`System.Transactions.TransactionScope` 로 감싼다.
이때 하위 단계를 **`Task.WhenAll` 로 병렬 실행하지 않는다.**
커넥션이 둘 이상 동시에 열리면 트랜잭션이 MSDTC 로 승격되기 때문이다. 순차로 돌린다.

## ✅ 검증

- [ ] `SECURITY_CODE` 없이 호출 → 401 과 `errorMessage` JSON 이 오는지
- [ ] 잘못된 보안코드(`9999...`) → 401 인지
- [ ] 정상 보안코드로 Dev / Prd 를 바꿔 호출했을 때 서로 다른 DB 를 보는지
- [ ] SP 이름을 일부러 틀리게 해서 `Result=false` 와 `ErrorMessage` 가 채워지는지
- [ ] 변경 SP 실행 중 오류 시 앞 단계가 롤백되는지
