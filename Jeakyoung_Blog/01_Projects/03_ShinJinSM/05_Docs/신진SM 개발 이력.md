# 신진SM 개발 이력

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **프로젝트** | 신진SM ERP · MES |
| **기간** | 2026-04-28(첫 업무 미팅) ~ 진행중 |
| **역할** | MES 개발 담당 |
| **기술 스택** | Sencha Ext JS, Java 서블릿, MSSQL, 더존 ERP 연동 |

> [[신진SM 프로젝트 개요]]가 "지금 상태" 스냅샷이라면, 이 문서는 정기 업무 미팅([[01_Projects/03_ShinJinSM/03_Meetings|회의록]])과 작업 기록([[01_Projects/03_ShinJinSM/01_Tasks|작업 목록]]) 날짜를 따라 "어떤 순서로 문제를 발견하고 대응해왔는지" 정리한 문서. 실제 코드 변경으로 이어졌거나 반복됐던 항목 위주로 남겼고, 화면 캡처·로그 덤프 위주의 세부 논의는 뺐다.

## 🎯 목표 및 범위

2026-04-28 첫 업무 미팅 이후 매주~격주 단위로 미팅이 이어지고 있고([[01_Projects/03_ShinJinSM/03_Meetings|회의록]] 18건, 04.28~09.15), 그 사이사이 실제 코드/SQL 변경으로 이어진 작업 기록이 [[01_Projects/03_ShinJinSM/01_Tasks|작업 목록]]에 남아있다. 아래는 그 둘을 엮은 타임라인이다.

## 🏗 진행 내용

### 1. 프로젝트 착수 (2026-04-28 ~ 05월 초)

첫 업무 미팅(04-28) 이후 신진SM ERP/MES 파악 단계. [\[완료\] 성능최적화 및 로깅](<../02_TechDocs/[완료] 성능최적화 및 로깅.md>)의 배경이 된 "정상 2-3초, 가끔 10초 이상" 응답 지연 이슈가 05-06 미팅 즈음부터 이미 논의 대상이었다.

### 2. 포장 중복 문제 발견 — MES는 정상, 더존만 틀어짐 (2026-05-22)

[[신진SM 중복 포장문제 ( 05.22 )]]에서 핵심 관찰: "MES 상 중복 포장 문제는 프로시저 레벨에서 이미 제한 완료(우리쪽 DB엔 중복 없음), 그러나 더존 ERP 연동부에서 중복이 다수 발생". 이 시점부터 문제의 초점이 "MES 코드"에서 "MES↔더존 연동부"로 옮겨간다.

### 3. 기술 검토 미팅 — 실제 SP·설정 원문 공유 (2026-05-28 회의록 / 문서 내부 날짜 06-05)

이 미팅에서 `SP_WMA624_01_IUD` 전체 소스, nginx 라우팅 설정 원문, 더존 저장 방식 스크린샷이 그대로 회의록에 첨부됐다 — [\[SQL\] SP_WMA624_01_IUD](<../04_References/[SQL] SP_WMA624_01_IUD.md>)와 [\[배포\] NginX 라우팅설정](<../04_References/[배포] NginX 라우팅설정.md>)의 원출처. 이 시점 제안은 "`SP_WMA624_01_IUD` 저장 시 더존 `UP_PU_ITR_UPDATE`를 같이 호출"하는 단순한 형태였다.

### 4. 실제 구현은 제안보다 복잡해졌다 — 헤더/라인 분리 + 배치 채번

현재 `jvWMA624_01_IUD.java`를 보면 06-05에 논의된 "UPDATE 한 번 더 호출" 방식이 아니라, 더존의 `NEOE.CP_GETNO`로 배치당 공용 IO_NO를 미리 채번하고 `NEOE.UP_PU_MM_QTIOH_INSERT`(헤더, 1회) + `NEOE.UP_PU_ITR_INSERT`/`UP_PU_CGI_INSERT`(라인, 레코드당)로 나눠 INSERT하는 구조로 바뀌어 있다. 더존 쪽이 헤더-라인 구조를 요구해서 자연스럽게 이렇게 진화한 것으로 보인다. 다만 이 구조에서도 **MES 커밋과 더존 반영은 여전히 원자적이지 않다** — 자세한 구조 분석은 [\[완료\] 포장중복문제 분석](<../02_TechDocs/[완료] 포장중복문제 분석.md>).

### 5. 정기 미팅 지속 (2026-06-12 ~ 08-18) — 후속 재검토로 항목화됨

이 구간의 18건 중 11건(06.12~08.18)을 전수 재검토해 추가로 문서화했다. 대부분 재고조정 화면 개선·도면가공 프로세스 세부설계 논의였고, 그중 코드 변경으로 이어질 만한 구체적 항목은 아래로 정리:

- **더존-MES 사업장 코드 매핑** (06-26): 재고조정 화면의 사업장 `1000` 하드코딩 문제를 계기로 12개 사업장 전체 매핑을 검증 쿼리로 확인 — [[신진SM 더존-MES 사업장 코드 매핑]]. 다만 이 매핑이 실제 코드(상수/설정)로 반영됐는지는 확인 안 됨.
- **포장 단독 생산 시 창고코드 오류** (07-28): `ProdSLService.java`의 창고코드가 `SL_ETC`(이전 실적 유무) 분기 없이 무조건 출하창고로 고정되는 버그가 보고됐으나, 2026-09-18 기준 코드 확인 결과 **아직 수정되지 않았다** — [[신진SM 포장 단독 생산 시 창고코드 오류 (미해결)]].
- **실적 등록 날짜 이월(자정·야간조) 처리**: 06-12에 요청, 06-26에 조치했다고 기록됐으나 08-04·08-18에 같은 "이틀 밀림" 증상이 재보고됨 — 미해결 또는 회귀로 추정. [[신진SM 실적 등록 날짜 이월 처리 (자정·야간조)]]
- **포장 중복 조회 기능(에러리스트 페이지)** (09-01, 6번 항목에서 이어짐): 사용자가 직접 중복 발생 건을 조회할 수 있는 화면 요청 — 아직 착수 전. [[신진SM 포장 중복 조회 기능 요청 (에러리스트 페이지)]]
- 07-03 회의록은 도면가공 창고코드를 `3000/3400/6000/7000` 체계로 설계했으나, 실제 09-14 구현(8번 항목)은 `018/016/225`, 더존 ETC `4200/7000` 체계로 바뀌었다 — 설계가 굳어지기 전 여러 차례 창고 번호 체계 자체가 바뀐 것으로 보임.

07.07 라벨등록 API, 07.14 도면번호 체계, 08.13 로그/화면 캡처 위주 논의는 구체적인 코드 변경까지 이어지지는 않았다.

### 6. 더존 월말 재고 집계 불일치 발견 (2026-08-31 ~ 09-10)

[[신진SM ERP 기말 재고 오류]](08-31)에서 더존 `MM_OHSLINVM`(월별 집계)이 `MM_OHSLINVD`(일별 상세)와 어긋나는 사례를 발견 — 3번 항목의 "포장 중복→더존 재고 어긋남"과는 별개의 집계 레이어 문제. 09-10에 [[신진SM ERP 기말 재고 오류 ( 입 출고 내역에 이상이 없을경우 )]]로 탐지/정정 절차를 표준화(Step 1 탐지 → Step 2 세부 확인 → Step 3 UPDATE, **프로시저 재실행 금지** — `MM_PINVN` 이중 반영 위험). 관련해서 같은 날 [[신진SM MES 품목 정보 조치 방안]]으로 `SP_WMA624_01_LIST`의 `TCO403`/`TMA922` 사업장 코드 불일치 문제도 수정(2026-09-04 적용).

### 7. 현장 화면 개선 (2026-09-08)

[[신진SM MES 수정사항 (26.09.08)]]: WPR559(생산실적등록) 화면에 도면가공 구분 필터·출하량 컬럼·행 색상 표시 추가, `WMA624`(재고조정 엑셀 업로드) 붙여넣기 처리를 개별 병렬 요청에서 1회 배치 요청으로 변경(HTTP 2N회 → 1회).

### 8. 더존 문서 중복 생성 방어 + 도면가공 체계 신규 동기화 (2026-09-14)

같은 날 등록된 두 작업:

- [[신진SM - 더존 중복 문서처리 방어]]: `SP_WPR559_02_IUD_TEST`에 `@ISEXISTS_OUT` OUTPUT 파라미터를 추가하고, `ProdReportService`/`ProdSLService`가 이 값을 보고 더존 문서 재생성을 생략하도록 수정. 2번 항목의 "포장 중복" 문제와 같은 부류지만 **다른 코드 경로**(WPR559 생산실적 저장 vs WMA624 계정대체)에 대한 방어책이라는 점이 중요 — 자세한 내용은 [\[완료\] 포장중복문제 분석](<../02_TechDocs/[완료] 포장중복문제 분석.md>).
- [[신진SM 도면가공 체계 MES 동기화 작업]]: POP 시스템에만 있던 도면가공(WORK_CODE=008) 1차/2차 포장 분기 처리를 MES에 이식하는 작업. `TPR601.PLATE_COMPLETE_FLAG` 상태값을 기준으로 창고(018 도면가공창고 ↔ 016/225 출하창고)와 더존 전표 목적창고(4200 ↔ 7000)를 자동 분기하도록 설계 완료, DB 스크립트 일부·Java 반영은 진행 중. 배포 순서(DB 스크립트 3개 선적용 → Java 배포) 제약이 명시적으로 걸려 있다 — 자바가 먼저 나가면 SP 파라미터 개수 불일치로 전체 저장이 즉시 실패하는 구조.

## ✅ 결과 및 회고

- **"MES/더존 비원자적 커밋"이 반복적으로 다른 이름의 문제를 만들어냈다.** 포장 중복(5월), 더존 월말 집계 불일치(8월), 더존 문서 중복 생성(9월)이 표면적으로는 다른 문제로 보고됐지만, 근본에는 "MES는 먼저 커밋되고 더존 반영은 best-effort"라는 같은 구조가 있다. 아직 이 셋을 하나의 원인으로 묶어서 근본적으로 해결하는 작업은 없고, 발생할 때마다 개별 가드(`ISEXISTS_OUT`)와 수동 정정 쿼리로 대응해왔다.
- **회의록에서 제안된 설계와 실제 구현이 다른 경우가 있다.** 06-05 미팅의 "UP_PU_ITR_UPDATE 같이 호출" 제안은 실제로는 헤더/라인 분리 INSERT 구조로 바뀌어 구현됐다 — 회의록은 "그 시점의 생각"으로 남겨두고, 실제 동작 기준 문서([\[통합\] 더존ERP 동기화](<../04_References/[통합] 더존ERP 동기화.md>))를 따로 유지해야 한다는 교훈.
- **관측 인프라가 거의 없다.** 응답시간 자동 집계, 재시도, 대시보드 모두 미구현 — 성능 이슈든 더존 미반영이든 발견 경로는 사용자 신고 또는 로그 파일 수동 확인이다.
- **배포 순서 제약이 암묵적이다.** 도면가공 작업에서 드러났듯, DB 스크립트와 Java 배포 순서가 어긋나면 전체 저장 기능이 즉시 깨질 수 있는 구조(파라미터 개수 불일치) — 이런 제약이 코드에 문서화돼 있지 않고 담당자 기억에 의존한다.
- **하드코딩된 사업장/창고 코드가 반복적으로 문제의 근원이 된다.** 06-26의 사업장 `1000` 하드코딩, 07-28의 창고코드(`016`/`225`) 하드코딩이 같은 패턴이다. 사업장 매핑은 검증까지만 됐고([[신진SM 더존-MES 사업장 코드 매핑]]), 창고코드 버그는 이후 도면가공 작업에서 별도 우회 경로(`WAREHOUSE_CODE_OVERRIDE`)만 추가됐을 뿐 근본 수정 없이 남아있다([[신진SM 포장 단독 생산 시 창고코드 오류 (미해결)]]) — "MES/더존 비원자적 커밋"과 함께 이 프로젝트의 두 번째로 반복되는 구조적 패턴이다.
