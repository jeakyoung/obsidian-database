# 포장 중복 문제 상세 분석 및 해결 방안

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | 신진SM ERP/MES (`iPlusERP_SJ`) + 더존(DZ) ERP |
| **적용 범위** | 제품창고 - 절단/포장 공정, 계정대체 입출고(WMA624), 생산실적 등록(WPR559) |
| **관련 모듈** | `jvWMA624_01_IUD.java`, `ProdReportService.java`, `ProdSLService.java`, `SP_WMA624_01_IUD`, `SP_WPR559_02_IUD_TEST` |

## 🎯 배경 및 요구사항

제품창고 절단공정 처리 중 타임아웃 → 롤백 → 동일 작업 재진행 시 포장/수불 데이터가 중복 생성되는 문제. [[신진SM 중복 포장문제 ( 05.22 )]]에서 최초로 "MES 쪽(TMA536)은 중복 없음, 더존 ERP 연동부에서 중복 다수 발생"으로 범위가 좁혀졌다.

## 🏗 설계 및 구현

### 구조적 원인 — MES와 더존은 원자적으로 묶여 있지 않다

`jvWMA624_01_IUD.java`는 레코드마다 `SP_WMA624_01_IUD` 실행 직후 **MES 커넥션(`conn`)을 먼저 커밋**하고, 그 다음에 더존 커넥션(`connDZ`)으로 창고/품목 매핑 조회 후 `NEOE.UP_PU_MM_QTIOH_INSERT`(헤더) / `NEOE.UP_PU_ITR_INSERT`(입고) / `NEOE.UP_PU_CGI_INSERT`(출고)를 호출한다. 더존 쪽에서 예외가 나도 MES(`conn`)는 이미 커밋된 뒤라서 되돌릴 수 없다 — [\[통합\] 더존ERP 동기화](<../04_References/[통합] 더존ERP 동기화.md>) 참고. 05.22 태스크에서 관찰된 "MES는 정상, 더존만 틀어짐" 현상과 정확히 일치하는 구조다.

> [!note] 더존 연결 실패는 예외가 아니라 경고 로그다
> `connDZ` 생성이 실패해도 서블릿은 멈추지 않고 `log.warn("더존 DB 연결 실패 (MES 저장은 계속 진행)")`만 남긴 뒤 계속 진행한다. 클라이언트에는 "저장 성공"으로 보이지만 더존에는 아무것도 안 들어갔을 수 있다.

### IO_NO 채번 레이스 컨디션 (더존 미연결 시 폴백 경로)

더존 연결이 안 될 때 `SP_WMA624_01_IUD`는 자체적으로 IO_NO를 채번한다:

```sql
SELECT @IO_NO = @DATE + RIGHT('0000'+LTRIM(STR(ISNULL(MAX(SUBSTRING(IO_NO,9,4)), 0) + 1)),4)
FROM TMA536 WITH(NOLOCK)
WHERE SUBSTRING(IO_NO,1,8) = @DATE
```

`NOLOCK`으로 MAX를 읽고 잠금 없이 +1 하는 구조라, 같은 요청이 타임아웃 후 재시도되어 겹치는 시간대에 두 번 실행되면(원 요청이 아직 안 끝난 채 재시도가 들어오는 경우) 같은 IO_NO를 두 트랜잭션이 동시에 계산할 여지가 있다. `SERIALIZABLE` 격리수준 지정이나 `UPDLOCK` 힌트는 이 채번 쿼리에 없다.

### 실제 진행 중인 방어책 — WPR559 경로의 ISEXISTS_OUT 가드

WMA624와는 다른 경로지만 같은 부류의 문제(더존 문서 중복 생성)에 대해, [[신진SM - 더존 중복 문서처리 방어]] 작업(2026-09-14)에서 다음과 같은 가드를 적용 중이다:

- `SP_WPR559_02_IUD_TEST`에 `@ISEXISTS_OUT INT = 0 OUTPUT` 파라미터 추가
- `ProdReportService.processProdReport()`(IRU='I' 분기)와 `ProdSLService.processSLCrossMove()`(자체생산/일반포장 분기)가 이 OUTPUT 값을 확인해서 **이미 더존 문서가 생성된 경우 재생성을 생략**
- `ProdReportService`/`ProdSLService`의 SP 호출을 `CallableStatement`로 전환해 38번째 파라미터로 이 OUTPUT을 받음

미적용 범위(손 안 댄 곳, 해당 작업 노트에 명시): `ProdReportService`의 IRU='U'/'D' 분기, `ProdSLService`의 삭제(IRU='D') 경로 2곳 — 이 경로들은 여전히 같은 부류의 중복 위험에 노출돼 있을 수 있다.

## ✅ 검증

- [x] MES(TMA536) 자체에는 중복 데이터가 없음을 확인 (05.22)
- [x] 더존 연동부에서 중복 발생 지점을 코드로 특정 (MES/DZ 비원자적 커밋 구조)
- [ ] WMA624 경로의 IO_NO 레이스 컨디션에 대한 실제 재현/수정 — 미착수 (구조만 특정된 상태)
- [~] WPR559 경로 ISEXISTS_OUT 가드 — 주요 분기 적용, IRU='U'/'D' 분기는 미적용
- [ ] 두 경로(WMA624 vs WPR559) 간 공통 원인인지, 별개 문제인지 최종 정리 — 미착수
