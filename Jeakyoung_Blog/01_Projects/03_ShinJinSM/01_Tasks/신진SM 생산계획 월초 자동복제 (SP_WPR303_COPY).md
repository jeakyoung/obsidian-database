# 신진SM 생산계획 월초 자동복제 (SP_WPR303_COPY)

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **요청자** | 미확인 — 관련 회의록/티켓이 확인되지 않아 코드 주석과 작업 중 스크래치 쿼리 기록만 근거로 문서화함 |
| **요청일** | 작업 기간 2026-10-29 ~ 2026-11-04 (코드 작성 → 성능 개선 → 복제 기준 재검토 → 데이터 정리) |
| **대상 시스템** | ERP (`iPlusERP_SJ`) 생산계획 |
| **관련 화면·프로그램** | WPR303(생산계획), `SP_WPR303_01_LIST`(생산계획등록 조회 화면), `SP_WPR303_EXCEL01_IUD`(엑셀업로드) |

> 정남사업장(PLANT_CODE='000001') 생산계획 중 등록자가 '송병덕'인 건에 한해, 매월 1일·2일자 계획을 전달 동일 일자에서 복제해오는 배치 SP(`SP_WPR303_COPY`)를 신규 작성함. Windows 작업 스케줄러가 파라미터 없이 월 1회 EXEC 호출하는 구조. 최초 작성(10/29~11/2) 이후 14,000여 건 규모에서 처리시간이 비정상적으로 길어지는 문제로 세트 기반으로 재작성했고, 그 과정에서 "복제 기준이 생산계획등록 화면이 보여주는 것과 다르다"는 더 근본적인 문제를 발견해 소스 판단 기준 자체를 바꿈.

## 🔍 현상 및 원인

### 배경

정남사업장에서 특정 등록자('송병덕')의 생산계획이 매월 1일·2일자에 반복적으로 등록되는 패턴이 있어, 전달 동일 일자 데이터를 그대로 복제해 수동 재입력을 없애는 자동화 배치를 작성함. (최초 요구사항이 어떤 경로로 들어왔는지는 이번 문서화 범위에서 확인하지 못함)

### 확인된 전제

- **PLANT_CODE `000001` = 정남사업장**: `TPR201`/`TSA307` 실데이터 분포와 `SP_WPR303_01_LIST` 호출 로그로 교차 확인 (2026-10-29, `_scratch_find_plant_code.sql`)
- **단일회사 운영**: `FACTORY_CODE`가 코드 전반에서 `'000001'` 고정으로 쓰이고 있음을 확인
- **등록자 식별 방식**: 처음엔 `TPR301.OPMAN_CODE`로 '송병덕'을 찾으려 했으나(`_scratch_find_opman_name.sql`), 실제로는 `TPR201.PLAN_EMP` → `TIN114.EMPLOYEE_NO`/`BASE_NAME` 체인으로 식별해야 한다는 걸 확인하고 필터링 기준을 이쪽으로 확정함

### 발견 1 — 처리 성능 (11/3)

@TEST_MAX_ROWS=100 규모 테스트에서 72초가 걸려 원인을 분석한 결과, 커서로 품목 1건당 INSERT 5번 + MAX+1 스칼라 서브쿼리 3번을 반복하는 구조였음. 10월 2일자 '송병덕' 등록 건이 11,898건(전체 소스 데이터의 대부분)이라, 이 구조로는 매달 자동 실행 시간이 비정상적으로 길어질 수 있다고 판단해 세트 기반으로 재작성함 (아래 조치 내용 참고).

### 발견 2 — 복제 기준이 화면 조회 기준과 다름 (11/3~11/4)

10월 1일자 소스 건수를 `TPR301.PRODPLAN_DATE` 기준으로 세면 19건인데, 생산계획등록 화면에서 같은 기간을 조회하면 **0건**으로 나오는 불일치를 발견함. 원인을 추적한 결과:

- 생산계획등록 화면(`SP_WPR303_01_LIST`)은 `TPR201.PLAN_DATE`로만 날짜를 검색함 (`TPR301.PRODPLAN_DATE`는 조회 조건에 전혀 쓰이지 않음)
- 엑셀업로드(`SP_WPR303_EXCEL01_IUD`)가 `@PRODPLAN_NO`를 빈 값이 아닌 상태로 넘겨받으면 기존 `PRODPLAN_NO`를 재사용함 — 이때 `TPR201.WAREHOUSE_CODE`/`HIST_SEQ`/`SALE_PLAN_QTY`는 매번 `UPDATE`로 갱신되지만 **`PLAN_DATE`만 갱신 대상에서 빠져있어** 최초 생성 시점(예: 9월, 심지어 6월)에 고정된 채로 남음
- `TPR301.PRODPLAN_DATE`는 매달 새 날짜로 정상적으로 바뀌기 때문에, 화면(TPR201 기준)과 TPR301 기준 데이터가 서로 어긋나는 현상이 생김

전사 규모로 확인한 결과: 전체 `PRODPLAN_NO` 686,665건 중 5,509건(0.80%)이 이 패턴이고, 가장 오래된 건은 **2023년 11월**부터 재사용되어 왔음. 재사용 건은 '송병덕'(3,705건)과 '관리자'(1,756건) 두 계정에만 집중되어 있고 다른 등록자는 없음 — 범용적인 화면 버그가 아니라 이 두 계정이 쓰는 특정 입력 경로(매크로/반복 작업)에서만 발생하는 것으로 추정.

### 발견 3 — 조인 과정에서 생기는 "줄 수" 뻥튀기 (11/4)

화면 조회 건수(12,340건)와 `TPR201` 단순 카운트(11,893건)도 차이가 있어 추가로 확인함. 원인은 생산계획(`TPR201`) 1건이 주문연결(`TPR202`)을 2개 이상 물고 있는 경우(443건)가 있어서였고, 화면은 `TPR202` 단위로 줄을 나눠 보여주기 때문에 줄 수가 더 많이 나온 것으로 확인함 (데이터 손실이 아니라 집계 단위 차이). 나머지 4건 차이는 `TPR301`/`TPR301R`에 남아있던 **깨진 고아 행**(아래 데이터 정리 참고) 때문이었음.

## 🔧 조치 내용

| 구분 | 대상 | 변경 내용 |
|:--|:--|:--|
| SP | `dbo.SP_WPR303_COPY` (신규 작성 후 재작성) | 전달 1일·2일 생산계획 중 등록자가 '송병덕'인 건을, 화면 조회와 동일한 기준·단위로 이번달 동일 일자에 복제 |
| 데이터 | `TPR301`/`TPR301R` 고아 레코드 2건 | 날짜/SEQ가 비어있는 깨진 행 삭제 (복제 작업과 무관한 엑셀업로드 쪽 실패 흔적) |

### 트리거 및 멱등성

- Windows 작업 스케줄러 → `sqlcmd` 등으로 파라미터 없이 `EXEC dbo.SP_WPR303_COPY` 1회 호출만 수행 (운영 호출은 전부 기본값: `@FACTORY_CODE='000001'`, `@PLANT_CODE='000001'`, `@OPMAN_CODE='0000'`, `@TEST_MAX_ROWS=NULL`)
- **대상 일자에 이미 송병덕 명의 생산계획(`TPR201.PLAN_DATE` + `PLAN_EMP`)이 있으면 그 날짜는 스킵** → 같은 달에 재실행해도 중복 생성되지 않음
- 최초 버전은 `TPR301` 전체 존재여부로 멱등성을 판단했으나, 엑셀업로드로 들어온 무관한 데이터(발견 2) 때문에 영구 스킵될 위험이 있어 `TPR201.PLAN_DATE` 기준으로 변경함

### 처리 흐름 (현재 버전)

1. `@Days` 테이블변수에 `'01'`, `'02'` 두 값을 넣고 `WHILE` 루프로 2회 순회
2. 매 회차마다 `@SRC_PRODPLAN_DATE`(전달 동일 일자) / `@TARGET_PRODPLAN_DATE`(이번달 동일 일자) 계산
3. 대상·원본 일자 둘 다 `TPR201.PLAN_DATE` + `PLAN_EMP`('송병덕') 기준으로 존재여부 확인
4. 해당 일자 전체를 묶는 신규 `ORDER_NO` 1건을 채번해 `TSA307`(`ORDER_GBN='3'` 내부 생산계획용 주문) 1행 생성
5. `TPR201 x TPR202`(LEFT JOIN, 주문연결 단위)로 복제 대상 전체를 `#Rows` 임시테이블에 한 번에 적재 — `ITEM_CODE`/`WAREHOUSE_CODE`/`HIST_SEQ`/`SALE_PLAN_QTY`는 `TPR201` 자체 값을 그대로 씀 (엑셀업로드가 재사용 시에도 이 값들은 매번 갱신되므로 신뢰 가능, `PLAN_DATE`만 예외)
6. `ROW_NUMBER()`로 매긴 순번(RN)으로 `PRODPLAN_NO`/`PRODPLAN_SEQ`/`ORDER_SEQNO`를 한 번에 계산 (채번 시작값은 날짜당 1회만 조회)
7. `TPR201`/`TPR202`/`TSA308`/`TPR301`/`TPR301R` 각각 `INSERT...SELECT` 1문장씩, 총 5문장으로 전체 건수를 일괄 처리 (커서 없음)
8. 전체를 `BEGIN TRY ~ BEGIN TRAN ~ COMMIT TRAN`으로 묶고, 실패 시 `ROLLBACK` 후 `THROW`로 재던짐

### 주요 설계 변경 (최초 버전 → 현재 버전)

| 항목 | 최초 버전 | 현재 버전 |
|:--|:--|:--|
| 처리 방식 | 커서로 품목 1건당 순회 (INSERT 5번 + MAX+1 서브쿼리 3번씩 반복) | `#Rows` + `ROW_NUMBER()`로 날짜당 INSERT 5문장 일괄 처리 |
| 소스/멱등성 판단 기준 | `TPR301.PRODPLAN_DATE` | `TPR201.PLAN_DATE` + `PLAN_EMP` (화면 조회와 동일 기준) |
| 복제 단위 | `TPR301` 작업 1줄당 1건 | `TPR201 x TPR202` 조인, 화면이 보여주는 "줄 수" 단위 |
| 창고/HIST_SEQ 조회 | 매 품목마다 `TPR301R→TPR202→TPR201` 체인 재조회 | `TPR201` 자체 값 직접 사용 (체인 조회 불필요) |
| 테스트 기능 | 없음 | `@TEST_MAX_ROWS` 파라미터로 소스 데이터 안 건드리고 건수 제한 테스트 가능 (운영 호출엔 영향 없음, 기본값 NULL=무제한) |

### 데이터 정리

화면-TPR201 건수 차이(12,340 vs 12,336) 4건을 추적하다 발견한, 엑셀업로드 실패로 보이는 고아 레코드 2건을 정리함:

- `TPR301`: `PRODPLAN_NO='202610010128'`, `COL_SEQ=2`, `PRODPLAN_DATE`/`PRODPLAN_SEQ`가 비어있는 행 — 같은 품목(`0000118554`)에 대해 35초 뒤 정상 행이 다시 생성된 걸로 봐서 입력 실패 후 재시도한 흔적으로 판단, 삭제
- `TPR301R`: `PRODPLAN_DATE`/`PRODPLAN_SEQ`가 비어있고 `ORDER_NO`도 빈 값인 고아 행 — "주문 없음" 상태인 아무 `TPR202`에나 잘못 들러붙어 조인 뻥튀기를 일으키고 있어 삭제 (이 행 하나가 별개로 보였던 또 다른 뻥튀기 사례의 원인이기도 했음)

둘 다 '송병덕'·'관리자' 쪽 데이터가 아니라 각각 다른 등록자(`S20231001`, `S20170503`) 건이었음 — 이번 복제 작업과는 무관하게 엑셀업로드 쪽에서 발생한 기존 문제.

## ✅ 검증 및 결과

운영 DB(`iPlusERP_SJ`)에서 대부분 `BEGIN TRAN ~ ROLLBACK` 안에서 실행해 운영 데이터는 변경하지 않고 검증함.

- [x] `PLANT_CODE='000001'` = 정남사업장 교차 확인 (`_scratch_find_plant_code.sql`, 2026-10-29)
- [x] 등록자 식별 기준을 `OPMAN_CODE`가 아닌 `TPR201.PLAN_EMP → TIN114.BASE_NAME`으로 확정 (`_scratch_find_opman_name.sql`)
- [x] 동일 `PRODPLAN_NO`에 등록자가 2명 이상 걸리는 충돌 케이스가 없는지 확인 (`_scratch_check_prodplan_no_collision.sql`) — 당시엔 충돌로 보였으나 실제로는 `PLANT_CODE` 조인 누락 버그로 인한 오탐이었음을 재확인
- [x] `BEGIN TRAN ~ ROLLBACK`으로 실제 `EXEC`: 복제 후 대상 일자 생성 건수가 소스의 '송병덕' 건수와 일치하는지, 등록자가 송병덕이 아닌 행이 섞여 들어오지 않는지 확인 (`_scratch_test_songbyungdeok_filter.sql`)
- [x] `@TEST_MAX_ROWS=100` 규모 실측: 72초 — 대부분 등록자 판별용 조인 비용이고 INSERT 자체는 빠름을 확인 (`_scratch_test_100rows_batch.sql`)
- [x] 실제 운영 `EXEC` 1회 수행 (최초 TPR301 기준 버전): 11/1=19건, 11/2=11,898건 신규 생성(+기존 33건=11,931) — 소스 집계와 정확히 일치
- [x] 화면 조회 건수(12,340)와 코드 복제 기준(12,336) 비교 — 차이 4건의 원인을 `TPR301`/`TPR301R` 고아 레코드 2건으로 특정, 정리
- [ ] TPR201 기준 재작성 버전의 실제 운영 `EXEC` 재실행 및 결과 검증 (지금까지의 실제 실행은 TPR301 기준 구버전으로 수행됨)
- [ ] 실제 운영 스케줄러(Windows Task Scheduler)에 최신 버전 등록 완료 여부 확인
- [ ] 다음 달 1일 실제 자동 실행 1회차 결과 확인 (로그/PRINT 메시지 기준)
- [ ] (별도 이슈) 엑셀업로드 `PRODPLAN_NO` 재사용 버그 자체의 수정 여부 — 전체 5,509건 중 2건만 수동 정리함, 근본 수정은 미착수
