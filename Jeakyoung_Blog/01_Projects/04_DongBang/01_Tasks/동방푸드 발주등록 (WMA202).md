## 🔍 현상 및 원인

입고등록 화면에서는 발주 내용과 상관없이 담당자가 자재를 임의로 추가해서 입고 처리(강제/임의등록)할 수 있다. 이렇게 등록된 항목이 발주현황(WMA202) 조회에 정상 발주 건과 함께 섞여 나와서, 실제 발주 건만 걸러볼 방법이 없었다.

> [!note] 원본 메모의 TMA108/TMA206 트리거/SP_WPR313_03_IUD 언급
> 조사 과정에서 "TMA108 칼럼에 자동 발주 코드가 있다", "TMA206 → 트리거 → TMA108", "SP_WPR313_03_IUD" 같은 메모를 남겼지만, 코드로 검증한 결과([\[기술\] 발주-입고 강제등록 구분 처리 (WMA202)](<../02_TechDocs/[기술] 발주-입고 강제등록 구분 처리 (WMA202).md>) 참고) 코드베이스 전체 grep에서 `TMA108`(무관한 컬럼명 한 건 제외)/`TMA206`/`SP_WPR313_03_IUD` 모두 확인되지 않았다. DB 트리거는 원래 이 SVN 워킹카피에 소스가 없는 DB 객체라 검증 자체가 불가능하고, 실제로 구현에 쓰인 것은 `SP_WMA202_01_LIST`의 `DT_ORDER_FLAG` 파라미터였다 — 조사 초기에 다른 경로(트리거)를 의심했다가 실제로는 조회 SP의 플래그 파라미터 추가로 해결된 케이스로 보인다.

## 🔧 조치 내용

발주에서 저장된 건은 `DT_ORDER_FLAG = 0`, 입고에서 강제(임의)로 등록된 건은 `1`로 구분해서, `SP_WMA202_01_LIST` 조회조건에 `DT_ORDER_FLAG`를 파라미터로 추가했다. 화면(WMA202)에는 "입고품목추가제외" 체크박스(`cfOrderFlag`)를 추가해서 이 값을 조회 시 넘기도록 했다.

- `jvWMA202_01_LIST.java` — `DT_ORDER_FLAG`를 서버 파라미터로 추가해 `EXEC SP_WMA202_01_LIST` 호출부 끝에 포함
- `WMA202_VW.js`/`WMA202_CT.js` — `cfOrderFlag` 체크박스 추가, 체크 여부를 `'1'`/`'0'`으로 변환해 전송

상세 코드 흐름과 검증은 [\[기술\] 발주-입고 강제등록 구분 처리 (WMA202)](<../02_TechDocs/[기술] 발주-입고 강제등록 구분 처리 (WMA202).md>) 참고 — 화면 그리드에 `DT_ORDER_FLAG`를 직접 표시하는 컬럼은 없고 조회조건 필터링에만 쓰인다.

## ✅ 검증 및 결과

- WMA202 입고품목추가제외 체크박스 → `DT_ORDER_FLAG` 파라미터 전송 흐름, 코드로 확인 완료
- SP 내부에서 `DT_ORDER_FLAG`를 실제로 어떤 조건식으로 쓰는지는 DB 접근 없이 미확인
- [[동방푸드 DB 재반영, 테스트 (WRD203, WPR512, WMA202)]]에서 재반영 후 "입고품목 추가 제외 CHECKBOX 동작 이상 없음(정상)"으로 테스트 완료 기록됨
