# 샘플요청서 담당자 조회조건 (WRD203)

## 📋 개요

| 항목 | 내용 |
|:--|:--|
| **대상 시스템** | iPlusERP (`iPlusERP_DONGBANG`) |
| **적용 범위** | 영업관리 - 프로젝트관리 - 샘플요청서(WRD203) |
| **관련 모듈** | `jvWRD203_01_LIST.java`, `jvWRD203_01_IUD.java`, `WRD203_VW.js`, `WRD203_CT.js`, `SP_WRD203_01_LIST` |

> 샘플요청서 조회조건에 담당자(연구담당자/영업담당자) 필터를 추가하는 작업. 코드 검증 과정에서 서버 쪽에 담당자 관련 파라미터를 한 이름으로 잘못 받는 문제를 발견했다.

## 🎯 배경 및 요구사항

원본 작업노트: "영업관리 - 프로젝트관리 - 샘플요청서" 화면 조회조건 작업. FE는 `WRD203_VW`/`WRD203_CT`, BE는 `jvWRD203_01_list`(조회), SQL은 `SP_WRD203_01_LIST`를 대상으로 했다는 작업범위 메모가 남아 있다.

## 🏗 설계 및 구현

### 조회조건 화면

`WRD203_VW.js`에서 확인되는 조회조건 필드들:

| itemId/name | fieldLabel | 비고 |
|:--|:--|:--|
| `tfProjectName` | 프로젝트명 | |
| `dtFromdate` | 샘플요청일 | |
| `tfEmployeeName` | 영업담당자 | `EMPLOYEE_NAME` 파라미터 |
| `combo_01` | 회사명 | |
| `combo_02` | 파트 | `TEAM_CODE` 파라미터 |
| `combo_03` | 연구담당자 | `RND_EMP_CODE` 파라미터 |
| `combo_04` | 영업담당자 | `SALES_EMP_NO` 파라미터 (상세 등록 영역) |
| `cbPROC_STATUS` | 상태 | `PROC_STATUS` 파라미터 |

### 클라이언트 조회 파라미터 — `WRD203_CT.js`

조회 함수(103~126행 부근)가 실제로 보내는 파라미터:

```js
{
    // ...날짜류 생략
    PROJECT_NAME: me.getView().down('#tfProjectName').getValue(),
    EMPLOYEE_NAME: me.getView().down('#tfEmployeeName').getValue(),
    PROJECT_NO: me.getView().down('#tfProjectNo').getValue(), // 조회 함수에 따라 '' 또는 값
    CUSTOMER_CODE: me.getView().down('#tfCustCode').getValue(),
    MATERIAL_NAME: me.getView().down('#tfMaterialName').getValue(),
    TEAM_CODE: me.getView().down('#combo_02').getValue(),
    RND_EMP_CODE: me.getView().down('#combo_03').getValue(),
    PROC_STATUS: me.getView().down('#cbPROC_STATUS').getValue(),
    SALES_EMP_NO: me.getView().down('#combo_04').getValue(),
    PROC_GBN: '',
}
```

`RND_EMP_CODE`, `PROC_STATUS`, `SALES_EMP_NO`는 각각 다른 UI 컴포넌트(`combo_03`, `cbPROC_STATUS`, `combo_04`)에서 값을 읽어 서로 다른 파라미터명으로 보낸다. `PROC_GBN`은 조회 시점에는 항상 빈 문자열 리터럴로 고정 전송된다(상세 등록 폼의 `PROC_GBN` 콤보와는 별개).

### 서버 - `jvWRD203_01_LIST.java`

```java
String PROC_STATUS = request.getParameter("PROC_GBN");
String SALES_EMP_NO = request.getParameter("PROC_GBN");
String PROC_GBN = request.getParameter("PROC_GBN");
```

`SP_WRD203_01_LIST`는 17개 파라미터로 호출되며, 그중 `PROC_STATUS`/`SALES_EMP_NO`/`PROC_GBN` 세 개가 전부 `request.getParameter("PROC_GBN")`에서 값을 읽는다.

> [!warning] 클라이언트가 보낸 PROC_STATUS·SALES_EMP_NO 값이 서버에서 버려진다
> 클라이언트는 `PROC_STATUS`, `SALES_EMP_NO`, `PROC_GBN`을 각각 다른 파라미터명으로 정확히 보내고 있다(위 코드 참고). 그런데 서버는 세 변수를 전부 같은 요청 파라미터 이름(`"PROC_GBN"`)으로 읽는다 — 즉 클라이언트가 실제로 보낸 `PROC_STATUS`/`SALES_EMP_NO` 값은 서버에서 조회되지 않고, 대신 클라이언트가 보낸 `PROC_GBN`(조회 시 항상 `''`) 값이 `SP_WRD203_01_LIST`의 `@PROC_STATUS`/`@SALES_EMP_NO`/`@PROC_GBN` 세 파라미터에 전부 그대로 들어간다.
>
> 결과적으로 화면에 "상태"(`cbPROC_STATUS`) 콤보와 상세 등록 영역의 영업담당자(`combo_04`) 콤보가 있어도, 조회 시점에는 이 두 값이 SP에 전달되지 않는 것으로 보인다. 이 문서 대상인 "담당자 조회조건" 작업이 `RND_EMP_CODE`(연구담당자, `combo_03`)만을 의미했다면 영향이 없지만, 영업담당자(`SALES_EMP_NO`)까지 포함한 것이었다면 실제로는 동작하지 않고 있을 가능성이 있다 — 원본 작업노트에 이 버그에 대한 언급이 없어 의도된 것인지 놓친 것인지는 미확인.

`jvWRD203_01_IUD.java`(같은 `WRD200` 디렉토리)는 저장(Insert/Update/Delete) 전용 서블릿이라 이 조회조건 기능과는 별개다.

## ✅ 검증

- [x] `WRD203_VW.js`/`WRD203_CT.js`의 담당자 관련 조회조건 필드(`combo_02/03/04`, `tfEmployeeName`, `cbPROC_STATUS`) 확인
- [x] `jvWRD203_01_LIST.java`에서 `PROC_STATUS`/`SALES_EMP_NO`/`PROC_GBN`이 동일 파라미터명(`"PROC_GBN"`)으로 읽히는 것 확인 — 실제 코드 결함으로 판단되나 의도 여부는 미확인
- [ ] `SP_WRD203_01_LIST` 내부에서 `RND_EMP_CODE`/`TEAM_CODE` 등을 어떻게 필터링하는지 — DB 접근 없이 미확인
- [ ] 위 PROC_STATUS/SALES_EMP_NO 이슈가 실제 운영에 영향을 주는지 재현 테스트 — 미착수
